Sprint 2026-11-01: semantic knowledge base

Branch sprint-2026-11-01 Base ec966c5 Code tip b7a3eda Iteration WCL App Q4 2026 (Shortcut 161) Not merged to main · not pushed

The agent can now search what the app already knows before it calls Warcraft Logs: stored report data, the grounded class guides and the workspace's earlier chats. In the background, every stored fetch, published guide and saved chat exchange is cut into short, readable chunks and embedded with Vertex gemini-embedding-001 (768 dimensions) into pgvector. A new search_knowledge tool runs up to five queries in parallel. Each query combines vector and full-text search, fused by RRF, with typed filters that the server resolves, and visibility is checked inside the SQL. Three exact-lookup tools read stored fights and tables directly. The raw-store probe is now cheap and fails fast, private reports no longer leak through Redis, and the cache stats show hit/miss counters and the local-answer rate. All 33 points are delivered and Under Review. The live checks are batched for team-lead.

How a question flows now

Report fetched→stored (039)→ background →fight and table chunks as text→Vertex embedding, 768-d, normalised
Chat turn saved→ background →one chunk per exchange, workspace-scoped (RLS)
Later question→search_knowledge: 1–5 queries, enum filters→vector top N + ts_rank_cd top N, RRF, visible only→soft filters relax if < k→compact hits (≤ 6,000 chars)
"Which fights are stored for X?"→list_stored_fights / get_stored_fight_table / list_stored_reports_for_character→"not stored locally" → WCL tools

Embedding never runs inside a chat turn. When embeddings are unavailable, search falls back to keyword-only and says so. A deleted chat, stored fetch or guide takes its chunks with it (FK cascade).

sc-304 Shared name resolver2Under Reviewbackend/app/services/name_resolver.py resolves class, class+spec, spec-only pairs, difficulty, encounter and character. sc-114 Parallel hybrid search tool P75Under Reviewsearch_knowledge runs 1–5 concurrent queries with enum filters. Each query fuses vector and ts_rank_cd results by RRF, then the queries are fused and deduplicated. Visibility is checked in SQL through fetch_visible_clause, plus a check that the chunk's report code is one the fetch names. Hard and soft filters relax in a fixed order. Output is capped at 6,000 characters, with an "untrusted" notice and a keyword-only fallback. A process-wide 5-session pool with a 3 s statement timeout came from P7.

Decisions & risks

Three chains, one developer each (#2)

sc-131 went with the raw-store QA work, because sc-295 rewrote the read path it sits on. No feature waited on another longer than one milestone merge.

Contracts fixed up front (#15)

Ilse fixed four contracts: the resolver module, the embedder protocol, fetch_visible_clause (one definition of the 039 rule for both the probe and search), and the tool names. Parallel work never had to guess an interface.

Image pg17-trixie (#82)

The steer said pg17. Ansel found that plain pg17 is Debian 12 and causes a collation mismatch on the owner's volume. A deviation with a reason, posted on the board.

report_code implies wcl (#117)

A hard report filter that let guide and chat hits through would read as a widened result.

PERF-007: keep probing (#66)

After sc-295 a miss costs one statement. Revisit with 7 days of counters (sc-332).

Joiners load for themselves (#134)

The SEC-001 fix reads the rule from what the store returned (unshareable), not from who asked. Public loads stay shared.

Risks to watch

  • Search at scale (sc-318): about 1 s per query at 60k chunks, extrapolated to the 3 s statement timeout around 100–250k. Count kb_chunks after the backfill to see where the owner's corpus sits.
  • Stale chunks after a dropped job (sc-320): the indexer queue is bounded, so heavy load or a restart can leave an old report or guide version searchable.
  • Eval quality unmeasured until live check 044(6) records real embeddings.
  • Single-process assumptions: the tombstone and the search pool are per process. That's fine with one uvicorn worker (the Dockerfile has no --workers).
