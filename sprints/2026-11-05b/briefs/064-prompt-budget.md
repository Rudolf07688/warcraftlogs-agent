## Story (acceptance criteria verbatim)

### Every chat request starts at about 23k prompt tokens before any report data (sc-367, 2 pts)
Found in team-lead's live pass, sprint 2026-11-02, model claude-haiku-5-5. The recent-raid kickoff peaked at 37,474 prompt tokens, above the "under about 35k" in feature 050's SC-004. A one-tool question took 26,344 tokens; turns with no tool call logged 22,700. So the fixed part of each request (instruction plus tool schemas) is roughly 22-23k tokens. It is paid on every request of every turn, and a multi-round turn pays it each round.
Idea: measure what the fixed part is made of (instruction sections, guide text, tool schemas, profile context), then cut or lazy-load the biggest pieces. Add a size test that builds the request offline and estimates tokens as chars/4, like the 046 table test.

**AC sketch:** the fixed part of a chat request is measured in a test with a budget; the recent-raid kickoff stays under about 35k prompt tokens live.

## How I want it done
1. **Measure first** and post the table on the board (`decision`, key `plan:064`): chars/4 per instruction section, per tool schema (name + description + parameters as the provider sees them), capability summary, profile context. Both providers' request shapes if they differ (Anthropic and Gemini are both live).
2. **Cut the biggest pieces that carry least**: duplicated rules between instruction and tool descriptions, long examples, verbose tool docstrings, rarely-used tools' schemas. Prefer shortening over lazy-loading unless one piece dominates; lazy-loading adds behaviour that needs its own tests.
3. Set a budget that the test enforces, with headroom of about 10%, and a target of at least ~25% off the fixed part (so ~17k or less). If you can't reach it without removing behaviour the specs require, stop at what's safe and say why in the hand-off.
4. Don't change what the agent does: no tool removed, no rule's meaning changed. Every rule cut must exist elsewhere or be dead. List each cut with its reason in the hand-off so the live pass can watch for regressions.
5. Live check suggestion for team-lead: the recent-raid kickoff prompt token peak (Tempo / `app_llm` metrics) and one guide question, both still answered correctly.
