What the owner will see

Click "send" in the app→Faro span in the browser→"chat turn" on the backend→ADK agent and model calls→Postgres→one trace in Tempo

Build layer (the agent team)

Each team-board entry lands in Loki and links to the trace of the turn that wrote it. "Claude Code: Overview" (D1) and a new "Claude Code: Agent Team" (D2) show cost by model, agent and role. Cost per board seat comes per sprint from the wrap-up stats. Every cost panel says "estimated, list price".

Runtime layer (the app)

Rate, errors and latency per API route come from traces, with exemplars. ADK token and agent metrics, WCL cache hit and miss, knowledge-base retrieval and time to first token all reach Mimir. Three runtime dashboards cover the API (D6), agents and LLM (D7, with cost per hour) and the knowledge base (D8). Page loads report Web Vitals.

The ticket assumed an HTTP chat route. Chat actually runs over a WebSocket, which can't carry custom headers and which Faro's fetch tracing doesn't reach. I changed the acceptance on the ticket and re-estimated it from 2 to 3 points.

Key decisions

  • Three tier-M streams, no scrum master. Shared infra files (Alloy config, compose) are split by section, with owners and contracts posted on the board before launch.
  • Pricing moved to the end of the build stream, as its ticket says. The token metric already exists, so it doesn't wait on the runtime stream, and each stream ends with its own drop candidate.
  • D2 is its own dashboard, not folded into "Agent Team: Improvement", which is fed per sprint. D7 grows from the starter runtime dashboard. D6 and D8 are new files, so "cut to D7" is a clean drop.
  • Seat cost is per sprint, from the wrap-up stats. Live metrics carry no seat, so live per-seat cost moves to Telemetry 3.
  • The cost rule is adapted to native histograms and the real label names. The spec's literal formula would return nothing.
  • The board stores the full traceparent. The trace id belongs to the lead's turn and is shared by sub-agents; the span id identifies the author.

Risks and what I'd drop

  • 1Pricing and cost rules (3 pts) go first if anything slips; D7's cost panel then goes too.
  • 2Next, the runtime dashboards are cut to D7 only.
  • 3Two streams edit the same Alloy and compose files. Mitigation: owners per section, rebase at merge, and the shared test scripts run on separate compose projects and ports.
  • 4Browser input reaches backend spans. Mitigation: validation in one place, edge cases tested first, and an independent security review before merge.
  • 5The proofs that need live data (populated panels, the end-to-end trace) wait for team-lead's live pass on the merged tip.
