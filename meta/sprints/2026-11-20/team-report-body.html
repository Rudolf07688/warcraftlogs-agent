Live checks: pre-checks while building, one pass at the tip

  • Seven pre-checks from four developers, each answered within one to five minutes. Two answers changed the work. Tomas's pre-check showed the wrong Gravebound figures were real Deaths-table fields the model picked badly (pre-mitigation and overkill), not the empty event lookups, so that ticket became field labelling. It also showed the raid player list error was our own playerDetails(fightIDs: null) query, which was fixed within the hour. Vera's before/after numbers measured caching at −47% (fresh chat) and −75% (repeat within five minutes) of a turn's input cost.
  • The traces had expired. Tempo no longer held the 11-07 trace ids written on the tickets. I recovered every tool call's args and results from the ADK events table instead, by session. Lesson: tickets filed from a live chat should carry the tool args and the key result fields, not only a trace id.
  • Tip pass, Claude (Haiku): 12 turns, every ticket PASS. Turn stats showed 85–99% of prompt tokens read from cache on the long turns. One real FAIL: "The Ula'tek heart" never reached the mechanics lookup, 2 out of 2.
  • Tip pass, Gemini (3.1 Pro preview): 7 turns. The heart question PASSED there, so the routing was model-dependent. Two turns ended with "couldn't put an answer together": Gemini returned STOP with 0 output tokens. That code is older than this sprint, so it's deferred as a ticket.
  • Fix round re-check: the heart question now passes on both providers. The thinking line shows in every gap between tool groups and never after the answer starts. A reloaded chat equals the live one on every chat, including those with retracted progress text.
  • My checker bugs: the reload comparison read role "assistant" (the API says "agent") and didn't model interim retraction. One regex missed "23.59 million". All were caught on the first read of the output and cost one cheap re-run. Lesson: dry-run new judge logic on one turn before the full pass.
