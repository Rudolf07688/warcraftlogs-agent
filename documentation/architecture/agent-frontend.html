1. Agent runtime

Tech google-adk>=2.0.0 uv.lock: 2.10.0 requires-python >=3.14 sqlalchemy[asyncio]>=2.0.0 asyncpg>=0.29.0 httpx>=0.27.0

What it does and where it lives

  • Agent factory. wcl_agent/agent.py → build_agent(model, retry) returns one Google ADK Agent(name="wcl_agent") with: instruction=build_instruction (an ADK instruction provider), tools=TOOLS (+ web_search on Gemini), before_model_callback=make_before_model_callback(policy) and planner=BuiltInPlanner(ThinkingConfig(include_thoughts=True)). The model is wrapped in RetryingGemini or RetryingClaude (see Models).
  • Runner. backend/app/agent_runner.py caches one ADK Runner per model id, all over one shared session service. The lifespan in backend/app/main.py installs ADK's DatabaseSessionService(db_engine=engine): it reuses the app's own async SQLAlchemy engine and connection pool on the same Postgres database, so a conversation's model context survives restarts; the CLI and tests fall back to InMemorySessionService. The ADK session id is the conversation UUID; the ADK user id is the tenant id.
  • Turn loop. stream_response() runs _run_turn() as a producer task feeding an asyncio.Queue, so rate-limit status records (pushed by the model wrapper through the current_turn ContextVar) reach the client while the producer sleeps in a backoff. _run_turn() iterates runner.run_async(..., RunConfig(streaming_mode=StreamingMode.SSE)) and maps ADK events to records: function_call → tool_start, function_response → tool_end (with the call's args, result and elapsed ms), partial text → token. Parts marked thought are dropped, so reasoning never reaches the user. (StreamingMode.SSE is ADK's internal model-streaming mode; the browser transport is a WebSocket.)
  • System prompt (Barnaby). _INSTRUCTION_BODY in wcl_agent/agent.py. Tag-delimited sections, in order: EVIDENCE_CONTRACT, SOURCE_AUTHORITY, TOOLS, EVIDENCE_PLAN, CONTEXT_RESOLUTION, VALIDATION_BEFORE_ANALYSIS, ANALYSIS_ROUTING, BENCHMARK_POLICY, COACHING_POLICY, PERCENTILE_POLICY, COACHING_BRIEFS, TOOL_FAILURES, CITATIONS, CHARTS, OUTPUT, PERSONALITY, CURRENT_TIME. build_instruction() fills the UTC time on every model request; the time block is last so everything before it is a stable, cacheable prefix. The contract is specs/009-grounded-coaching-prompt/contracts/prompt.md, enforced by backend/tests/test_prompt_contract.py.
  • Per-request context. The before-model callback (wcl_agent/llm/model_retry.py) does three things on every model request: (1) context_trim.trim_old_tool_results() (wcl_agent/llm/context_trim.py) replaces large tool results older than WCL_CONTEXT_KEEP_TURNS (default 2) with _elided stubs, in the request only; (2) inject_preamble() prepends the turn's KNOWN PLAYER CONTEXT to the latest user message, never storing it in ADK history; (3) counts model requests and, once the turn has used WCL_TURN_ROUND_CAP lookup rounds (default 6), appends WRAP_UP_INSTRUCTION and, for Gemini only, sets function calling to NONE.
  • Tool registry and parallel calls. TOOLS in wcl_agent/agent.py lists 20 function tools (full list in §4). Every tool is an async def over the native async WCL client (wcl_agent/client/wcl_client.py), so when the model emits several function_call parts in one response, ADK awaits them concurrently on the event loop. The prompt's TOOLS and EVIDENCE_PLAN sections tell the model to batch independent lookups into one parallel round. Each full result is also written to a per-turn scratch file (backend/app/scratch.py).
  • Background lane. All WCL requests share one LaneLimiter in wcl_agent/client/wcl_client.py: WCL_MAX_CONCURRENCY slots (6), of which background work (guide resolution, patch lookups, the recent-raid refresh, wrapped in background_lane()) may hold at most WCL_BACKGROUND_CONCURRENCY (2), and only while no chat lookup is waiting. Chat tools run in the default interactive lane, so a player's turn is never queued behind background refreshes.
  • Web-search sub-agent. _build_web_search_tool() wraps a grounding-only ADK Agent(name="web_search", tools=[google_search]), on the same Gemini model id, in an AgentTool(propagate_grounding_metadata=True). It is only added for Gemini models; Claude runs with the WCL tools only. The runner emits one grounding record per turn with the source titles and links.
  • Other model calls that are not the chat agent: the new-chat greeting (backend/app/greeting.py, runs the same agent with retry=False), follow-up suggestions (backend/app/suggestions.py, direct google-genai call on WCL_SUGGEST_MODEL, default gemini-3.6-flash, 4 s cap), generated chat titles (backend/app/services/conversation_titles.py, same cheap model), and the guide pipeline (§2).

Why it was built this way

InferredGoogle ADK as the agent framework. Reason not recorded: ADK predates the specs (specs/001-streaming-chat-frontend/plan.md calls it "existing agent", documentation/ai_guide.md §2 just lists it). Plausible trade-off: ADK is Google's own framework, so Gemini on Vertex, Google Search grounding, session services and turning plain Python functions into tools come built in. It also has an LLM registry that runs Claude on Vertex. The cost is coupling to ADK internals, which the retry wrapper and the context trimming already depend on.

Driving ADK's Runner.run_async with streaming and mapping function_call / function_response / partial text to frames reuses the event loop already proven in wcl_agent/cli.py, just redirected from print() to WebSocket frames.specs/001-streaming-chat-frontend/research.md §2

One Runner per model id: ADK accepts a model id string, so adding a model is configuration only, and caching runners avoids rebuilding the agent each turn. Alternatives: one hard-coded agent (no model switching); LiteLLM multi-provider (deferred).specs/001-streaming-chat-frontend/research.md §3

ADK's DatabaseSessionService restores real model context (tool history and turns), not just the transcript, after a restart, using ADK's built-in persistence instead of bespoke replay logic. Alternatives: in-memory sessions re-seeded from messages (loses tool and grounding context); ADK VertexAiSessionService (ties sessions to a managed Vertex Agent Engine resource).specs/002-agent-enhancements/research.md §3

One prompt, one persona: the single PERSONALITY block in wcl_agent/agent.py drives every model variant (DRY). Alternatives: per-model persona overrides (needless divergence).specs/003-chat-followups-ux/research.md R4

Tag-delimited sections work for both Gemini and Claude; the OUTPUT structure applies only to analytical questions because the same agent also writes greetings, guide documents and summaries. Persona last: decide facts, confidence and fixes first, then voice them.specs/009-grounded-coaching-prompt/research.md R13

Instruction provider for the live time: ADK calls the provider on every request and skips {state} substitution, so the time is correct however long the process runs (the old f-string was evaluated once at import). Alternatives: time in the preamble (empty for users without a profile); static_instruction + dynamic instruction (changes prompt caching for no gain).specs/015-grounded-class-guides/research.md R4

Async tools over one httpx client replace requests plus worker threads: real cancellation, no GIL contention, parallel tool calls overlap their I/O on the loop. Alternatives: the original design ran sync tools via asyncio.to_thread and relied on Gemini parallel function calling (specs/001-streaming-chat-frontend/research.md §4), recorded as "improve later".specs/013-welcome-recent-raids/research.md R7

One lane limiter on a single asyncio.Condition (about 40 lines, no dependency) lets background work give way to queued chat work, and every rule is directly testable. Alternatives: two separate semaphores (background could still take interactive slots while chat waits); asyncio.PriorityQueue dispatch (needs a dispatcher task).specs/013-welcome-recent-raids/research.md R8

Web search as a sub-agent tool: some Gemini generations reject the built-in google_search tool combined with many function tools in one request; the sub-agent keeps every WCL tool intact and matches the owner's "web-search subagent as a tool" wording. Native grounding was the clarified choice. Alternatives: a dedicated external search API such as Tavily or Bing (rejected in clarification; adds a credential).specs/002-agent-enhancements/research.md §4

Preamble per request, not in history; old tool results stubbed in the request only: keeps the prompt from growing with every turn while the stored history keeps full results. The turn stats log line records prompt and cached tokens to measure it.documentation/ai_guide.md §17 (Performance fixes, QA sweep 2026-10-14)

Round cap and "wrap up" instruction: a before_model_callback fires exactly once per model request, so it is the natural counter; prompt steering plus a cap is the smallest change that cuts model requests without removing capability.specs/011-agent-rate-limit-relief/research.md R5, R7

Native thinking planner (BuiltInPlanner): it fits Gemini 3.x thinking models, unlike ADK's ReAct text planner, which fights them; thoughts come back as separate parts the backend filters out. Recorded only as a code comment, not in a spec.wcl_agent/agent.py (comment on build_agent's planner argument)

2. Grounded class guides and the review step

Tech google-genai (not declared; comes with google-adk, uv.lock 2.25.0) pydantic-settings>=2.4.0 httpx>=0.27.0

What it does and where it lives

Coaching briefs are the verified, patch-specific guidance per (class, spec, content_type), with content type Raid or Mythic+. They are produced outside the chat agent by a plain async pipeline in backend/app/services/guide_pipeline/ (contract specs/015-grounded-class-guides/contracts/guide-pipeline.md):

  1. briefing (briefing.py): live date; the exact live build from Blizzard's launcher version endpoint (WOW_VERSION_URL, product wow only); the latest hotfix from the "Hotfixes:" articles on the WoW news page (WOW_NEWS_URL); raid tier / Mythic+ season; roster;
  2. data sheet (datasheet.py): measured WCL evidence from top rankings;
  3. research (research.py): a version-filtered fact sheet from grounded search (google_search + url_context). SOURCE_TIERS ranks domains: Blizzard official (tier 1, fetchable), Warcraft Logs (tier 2), guide sites (tier 3; only Icy Veins, Archon and Murlok may be fetched), forums, Reddit and video (tier 4, never citable). Third-party pages are fetched only when WCL_GUIDE_RESEARCH_FETCH_ENABLED is on (default off, pending a terms review); otherwise research uses search-grounded snippets only;
  4. author (authoring.py): tool-less structured claims citing evidence ids, on WCL_GUIDE_MODEL (default gemini-3.7-flash);
  5. checks (checks.py): deterministic consistency checks;
  6. review (review.py): a different, stronger model, WCL_GUIDE_REVIEW_MODEL (default gemini-3.1-pro-preview), marks each claim confirmed / contradicted / unconfirmed against the cited evidence only;
  7. revise: fix or drop failed claims; steps 5 to 7 repeat up to WCL_GUIDE_MAX_REVIEW_ROUNDS (default 3);
  8. render (render.py) and persist: publish, hold for review, or fail.

The agent only ever sees published briefs. At startup backend/app/main.py registers a loader with wcl_agent/guides/guide_meta.py (set_brief_loader). get_coaching_brief and get_cooldown_usage read through it, and briefs_for_turn() in backend/app/services/guide.py inlines whole briefs of the turn's content type into the preamble (≤ 6000 chars each, ≤ 12000 per turn, never truncated). The backend warns at boot if the reviewer and author models are the same. A maintainer accuracy check lives in backend/evals/guides.

Plain async functions on google-genai, not ADK agents: the old path ran guides through the full analyst agent (Barnaby's prompt, ~20 WCL tools, a web-search sub-agent that summarises results second-hand), which FR-004 forbids. Structured output makes claims checkable (Constitution IV); plain functions are the simplest loop (III); ADK 2.10 deprecates LoopAgent/SequentialAgent; a second ADK agent would need its own runner and session plumbing. Alternatives: a second ADK Agent with output_schema; ADK url_context tool; load_web_page (needs bs4/lxml); ADK Workflow graph runtime (too much machinery for a 3-round loop).specs/015-grounded-class-guides/research.md R3

The reviewer must be a different and stronger model than the author, get the same briefing and evidence sheets, and judge each claim against that evidence, not its own memory.specs/015-grounded-class-guides/spec.md FR-045, FR-046

Brief delivery by an injected loader keeps the dependency direction backend → wcl_agent, and replaces a boot-time registry that went stale across instances. Alternatives: a warm registry with periodic reload; importing backend DB code into wcl_agent (forbidden direction).specs/015-grounded-class-guides/research.md R7

The launcher version endpoint is the only source of the exact build, and reading only product wow keeps PTR builds out; it never blocks generation, because the WCL patch (major.minor) remains the floor. Alternatives: WCL partitions only (not precise enough); scraping patch notes (fragile, slower).specs/015-grounded-class-guides/research.md R1

The allowlist honours the clarified decision (fetch to extract facts, paraphrase, credit) while respecting each site's published crawling rules: Wowhead's robots.txt disallows AI crawlers, so it is never fetched and appears only as a search-surfaced link. WCL and Blizzard stay the substance; publishers add interpretation.specs/015-grounded-class-guides/research.md R14

Which brief goes into a turn is chosen by a deterministic keyword/zone classifier before the model runs (testable, free); get_coaching_brief covers anything it misses. Alternatives: always inject both briefs (double tokens, invites cross-use); tool-only (an extra round every coaching turn); an LLM classifier (cost and latency on every turn).specs/015-grounded-class-guides/research.md R8

3. Models and rate limits

Tech google-adk>=2.0.0 anthropic[vertex]>=1.11.0 uv.lock: anthropic 1.11.0 google-genai (via google-adk, uv.lock 2.25.0) redis>=6

Providers and where they run

  • Gemini on Vertex AI through ADK's Gemini model class (google-genai under the hood), with gcloud ADC credentials; GOOGLE_GENAI_USE_VERTEXAI=FALSE plus an API key is the AI Studio fallback.
  • Claude on Vertex (Anthropic in Model Garden) through ADK's google.adk.models.anthropic_llm.Claude, registered with ADK's LLMRegistry at import of wcl_agent/agent.py, using the anthropic[vertex] SDK. Any id containing claude is routed there (is_anthropic_model).
  • One location for every model call. wcl_agent/llm/vertex.py → model_location() reads WCL_MODEL_LOCATION (default global). Chat, web search, guides, reports, greeting, suggestions and discovery probes all use it, so GOOGLE_CLOUD_LOCATION can stay regional for everything else.

Live Model Garden discovery

wcl_agent/llm/models.py → discover_models() runs once at backend startup, off the event loop. In catalog mode (WCL_MODEL_DISCOVERY, the default) it lists the REST v1beta1/publishers/{google|anthropic}/models catalog, keeps GA and public-preview entries, sorts them into classes with anchored regexes (Gemini pro / flash / flash-lite, Claude haiku / sonnet / opus), probes the newest keep + 2 per class in one concurrent wave with a one-token call that carries a dummy function declaration, and keeps the newest keep that answer (defaults WCL_GEMINI_CLASSES=pro:2,flash:2,flash-lite:2, WCL_ANTHROPIC_CLASSES=haiku:1,sonnet:1,opus:1). The result is cached 6 h in the model_catalog cache family. If nothing passes, a documented fallback set is served with degraded=true. static mode probes only WCL_GEMINI_MODELS / WCL_ANTHROPIC_MODELS. The set lives on app.state and is read only through backend/app/model_state.py; GET /api/models (backend/app/api/models.py) returns {models, default, degraded}. The default is WCL_DEFAULT_MODEL if served, else the newest flash. The full plan and live findings are in documentation/live_model_probe.md.

Claude alongside Gemini: the owner asked for it. "The available models must be dynamically fetched from the available gemini and anthropic models on vertex."specs/002-agent-enhancements/spec.md (Input, item 4)

Vertex with ADC: no API key in the repo, and the same ADC code path works locally and on Cloud Run with an attached service account (no key files).documentation/ai_guide.md §2–§3; specs/001-streaming-chat-frontend/research.md §9

Live catalog instead of a fixed .env list: every model release needed an .env edit and a restart before players could pick it. Only the REST listing returns launchStage; the probe carries a function declaration because the chat agent always sends tools, so a tool-incapable model would otherwise fail on the first turn. Alternatives: genai models.list (no stage, Google only); httpx with a hand-refreshed token; regional catalogs (they differ); a plain "hello" probe (misses tool-incapable models); reusing the 90 s chat retry loop for probes (too slow for boot).documentation/live_model_probe.md (Context); specs/016-live-model-discovery/research.md R1, R3

Model calls at global: tested live on 2026-10-18, europe-west1 serves only Gemini 2.5 and no current Claude; global serves all of them.documentation/live_model_probe.md (Regions); wcl_agent/llm/vertex.py docstring

429 handling (feature 011)

wcl_agent/llm/model_retry.py. RetryingGemini and RetryingClaude override ADK's generate_content_async and run one shared retry loop, generate_with_retry(); the SDKs' own retries are off (Gemini HttpRetryOptions(attempts=1), Anthropic max_retries=0). is_rate_limited() treats genai APIError 429/503 or status RESOURCE_EXHAUSTED/UNAVAILABLE, and Anthropic RateLimitError, OverloadedError or any status 429/503/529 as "wait and retry". RetryPolicy defaults: 5 attempts, 2 s initial, ×2, ≤ 30 s per wait, 1 s jitter, 90 s total budget per request; a numeric Retry-After wins. Each wait sends a model_retry frame first. Nothing is retried once text has streamed. Helper calls (greeting) pass retry=False and fail fast. Settings: WCL_MODEL_RETRY_ATTEMPTS, _INITIAL_S, _MAX_S, _BUDGET_S, WCL_TURN_ROUND_CAP in backend/app/config.py.

Fallback to a second model of the same class (feature 021)

When a chat request still fails after the retries (ModelRateLimited) and nothing was streamed, generate_with_fallback() switches the turn once to its sibling: sibling_model() in wcl_agent/llm/models.py picks the served models with the same publisher and class, newest first; the newest falls back to the second, any other to the newest. backend/app/model_state.py → fallback_model_for() applies it, and only the chat socket passes it, so the web-search sub-agent and helper calls are untouched. The switch sends one model_fallback frame; this request and every later request of the turn go to the sibling. For Gemini, earlier parts of the turn get Google's documented "skip thought signature" value so the sibling accepts them. With the default classes, Gemini has a sibling in every class; Claude classes serve one model each, so a Claude turn ends with the plain rate-limit message.

Own retry loop instead of SDK retries: a native retry is invisible to the app, so nothing could show "busy, retrying" or count retries, and the two SDKs back off on different schedules with no shared budget. Overriding ADK's single model-call seam gives one loop for both providers. Alternatives: native SDK retries only (kept as the fallback if the wrapper breaks across ADK upgrades); ADK on_model_error_callback (cannot re-issue a request); re-running runner.run_async (duplicates the user message in the session).specs/011-agent-rate-limit-relief/research.md R1

Fallback per model request, inside the wrapper: the ADK session already holds the turn's user message, tool calls and streamed text, so switching one request re-runs nothing and never duplicates text; it reuses the retry loop and its status frames on the sibling. Alternatives: a turn-level re-run in stream_response (duplicates the user message, needs session surgery, repeats tool calls).specs/021-ratelimit-fallback/research.md R1

Sibling by naming rules over the served set: discovery already serves each class newest first and app.state.models is the single source of truth; no new state, works in static mode too. Alternatives: storing catalog.classes on app.state; a configured sibling map.specs/021-ratelimit-fallback/research.md R3

A separate typed model_fallback frame instead of reusing model_retry, whose attempt counters mean something else; Constitution IV asks for typed frames.specs/021-ratelimit-fallback/research.md R6

4. Agent ↔ app boundary

Tech google-adk>=2.0.0 fastapi>=0.115.0 sqlalchemy[asyncio]>=2.0.0

This section is source material for sc-204 (a generated self-description in the agent's context). It states what the agent reads and changes today, checked against the code on this branch, and what epic-203 plans to add.

What the agent can read today

  1. System instruction: build_instruction() (static text + current UTC time). It names the tools but says nothing about the app around the agent (profile page, raids, PDF reports); that gap is what sc-204 fills.
  2. KNOWN PLAYER CONTEXT preamble, built per turn by _build_turn_preamble() in backend/app/api/ws.py → build_preamble() in backend/app/services/profile_context.py, and injected into every model request of the turn (never stored):
    • the user's own characters (up to 10, MAX_OWN_CHARACTERS), friends, and main guild: name-server (region), class/spec and effective raid role;
    • the guild's recent-progression summary when ready (trimmed to 1500 chars);
    • whole published coaching briefs of the turn's content type for each profile character's spec, plus an index line per spec;
    • a RECENTLY SEEN (this account) block, capped at 1500 chars: the 10 most recent tracked raids, up to 15 known players, 10 known encounters and 10 known guilds captured from earlier tool results.
    The preamble is empty when the tenant has no profile and no captured metadata.
  3. This conversation's history: the ADK session (session id = conversation id, user id = tenant id), with tool results older than 2 turns stubbed in the request.
  4. Tool results: public Warcraft Logs data, plus published coaching briefs through the brief loader.

Not visible to the agent today: other conversations' messages; the welcome page's recent-raids and Mythic+ store (backend/app/api/recent_raids.py); PDF reports; draft or held guides; users, invitations and admin data; which page or chat the user has open; chart artifacts as data (only its own create_chart calls in this session).

What the agent can change today

No agent tool writes app data. There is no tool for profile, friends, guild, conversations, pins, raids or guides. The writes that do happen are side effects the WebSocket layer derives from successful tool results in _handle_tool_end() (backend/app/api/ws.py), in a short tenant-scoped transaction:

Alternatives: seeding ADK session state at session creation (goes stale); rebuilding the instruction per turn (fights the per-model runner cache).specs/005-guild-context-artifacts/research.md R1

Dependency direction backend → wcl_agent only: wcl_agent must not import backend code; data from the app reaches tools through an injected loader (set_brief_loader).specs/009-grounded-coaching-prompt/research.md R7; specs/015-grounded-class-guides/research.md R7

InferredDesign notes for sc-204/205 (not decided anywhere). (1) The same injection pattern fits profile tools: register backend callbacks at startup, and keep tenant and user identity in a ContextVar set per turn, as set_refresh_actor() and current_turn already do. 5. Stream protocol (FastAPI → browser)

Tech fastapi>=0.115.0 uvicorn[standard]>=0.30.0 plotly>=7.1.0 frames typed with Pydantic (via fastapi)

One WebSocket, /ws/chat (backend/app/api/ws.py). The handshake checks Origin and the __Host- session cookie before accept, and every turn re-validates the session. One turn runs at a time per socket. Frames are Pydantic models in backend/app/schemas.py, mirrored by the Frame union in frontend/src/api/wsClient.ts. Interrupted replies (socket closed or agent error) are saved as status="partial"; a rate-limit failure saves nothing, so the player can resend.

Same flow as text
  1. Browser sends ChatTurn. ws.py re-checks the session, validates the model against the served set, resolves or creates the conversation, saves the user message and sends meta.
  2. It builds the preamble (profile, published briefs, RECENTLY SEEN) and calls stream_response() with the turn's same-class fallback model.
  3. Per round: the model returns function calls → tool_start per call → tools run concurrently → captures in Postgres → tool_end (+ raid_tracked / artifact / encounters).
  4. The final round streams text → token frames. The agent message is saved, then done is sent.
  5. In the background: conversation_title (first reply of an auto-named chat) and suggestions (≤ 3 follow-up questions).

WebSocket rather than SSE or polling: the owner asked for WebSockets; it is bidirectional, fits incremental token delivery, and one long-lived connection avoids per-chunk HTTP overhead, with room for client→server control frames later. Alternatives: Server-Sent Events (simpler, one-way); plain HTTP + polling (no real streaming).specs/001-streaming-chat-frontend/research.md §1

Kept the WebSocket when the UI moved to the "spellcasting" stream design: the existing frames already map 1:1 to that design's events, so an SSE-over-POST rewrite would be pure rework. Only tool_end.summary/ms and an optional tool_progress frame were added.specs/004-raid-sourcing-ux/research.md R6

Follow-up suggestions come from a separate, non-streaming call after the answer: it keeps the streamed answer clean (no in-band delimiters to strip), the shape can be enforced (max 3), and first-token latency is unaffected. Alternatives: an in-band trailing <suggestions> block; ADK structured output on the main turn.specs/003-chat-followups-ux/research.md R1

done before suggestions, and suggestions as a cancellable background task with a per-socket send lock, so the composer is never held up.documentation/ai_guide.md §17

Charts as one typed ChartSpec from create_chart, turned into Plotly JSON on the server: the agent decides when to chart, using data it already fetched; no Plotly in wcl_agent; the same spec also feeds the PDF renderer. Alternatives: auto-promoting every get_report_graph result to a chart; building Plotly JSON inside the tool; Plotly static export (kaleido) for the PDF.specs/005-guild-context-artifacts/research.md R3; specs/005-guild-context-artifacts/plan.md (Complexity Tracking)

Generated titles reach the client as a typed conversation_title frame, on which the client refetches the list, so the list stays the one source of truth. Alternatives: polling the list after done; patching state in place from the frame.specs/019-sidebar-conversations/research.md R8

Authenticating the WebSocket at the handshake (session cookie + Origin check, before accept()) keeps one session model for HTTP and WS; the Origin check is the WS analogue of CSRF, and re-validating each turn makes a revoked session take effect mid-connection. Alternatives: a query-string token (leaks into logs); a separate WS auth message (reinvents the cookie).specs/006-multi-tenancy/research.md R6

All frames are typed Pydantic models because data that crosses a boundary must be an explicit typed model..specify/memory/constitution.md Principle IV

Why it was built this way

React + Vite + TypeScript to start with: it met the first UI requirement with the least machinery and was easy to extend.specs/001-streaming-chat-frontend/research.md §7

React 19, Tailwind v4, shadcn/ui, motion, Streamdown, use-stick-to-bottom and tsparticles were a user-directed "full adoption" of the chat-UI skill stack. Streamdown (no broken markdown mid-stream), motion (declarative spell-card lifecycle) and stick-to-bottom (chat scroll) each solve a problem the hand-rolled code handled poorly; Tailwind v4 + shadcn provide the token architecture the theme needs. Alternatives: a curated subset or CSS-only (offered, declined by the user); staying on React 18 (fights current peer dependencies of motion, shadcn and Streamdown).specs/004-raid-sourcing-ux/research.md R7

shadcn/ui through the shadcn MCP is a constitution rule: one registry-backed implementation per control keeps screens consistent and accessible (Principle I applied to the UI). Hand-built components need a recorded reason, as for the spell cards, cast bars and rune spinner..specify/memory/constitution.md Principle VII; specs/010-shadcn-ui-adoption/plan.md

Components come in through the shadcn CLI, which brings the radix-ui unified package and the icon-library mapping; the CLI quirks (lucide imports, the cn alias) are recorded for the next shadcn add. Alternatives: copying component sources by hand; writing our own primitives.specs/010-shadcn-ui-adoption/research.md R1

KaTeX math through Streamdown's plugin pipeline: math is an additive change, KaTeX only typesets complete delimiters (safe mid-stream), and remark-math leaves currency like $5 alone.specs/005-guild-context-artifacts/research.md R5

Plotly in the browser: interactive, hoverable, zoomable charts were the user's explicit goal; a static image fails that. The risk is contained by plotly.js-dist-min and lazy loading.specs/005-guild-context-artifacts/plan.md (Complexity Tracking)

react-router-dom: public auth routes, the guarded app shell and the admin page could not be expressed by the single-App conditional render without a hand-rolled router.specs/006-multi-tenancy/plan.md (Complexity Tracking)

Profile as a guarded /profile route with tabs mirrors the existing routing pattern, and reuses StreamMarkdown for guide content instead of a second markdown renderer.specs/008-profile-class-pages/research.md Decision 8

One CharacterList markup for own characters and friends (Principle I); no new registry component was needed.specs/012-multi-character-profile/research.md R8

The welcome page is the no-conversation state, not a new route: no navigation change, and it reuses the new-chat and greeting flow. It learns about new raids by polling, with no new transport. Alternatives: Server-Sent Events or pushing over the chat WebSocket (more work for no visible gain at a 3 s cadence).specs/013-welcome-recent-raids/research.md R11, R6

Pins as one nullable pinned_at column (answers both "is it pinned" and "in which order", covered by existing RLS); the shadcn Toggle for the pin control. Alternatives: a boolean plus an order column; a per-user pins table; the @shadcn/sidebar system (rewrites the sidebar); a dropdown menu per entry; drag-to-reorder.specs/019-sidebar-conversations/research.md R1, R9

Mythic+ runs on the welcome page reuse the shared report-summary query (keystone fields added to REPORT_SUMMARY_FIELDS), keeping one query.specs/022-welcome-mplus/research.md

The Vite proxy (and nginx in production) keeps the app same-origin, which is what makes the __Host- cookie, SameSite=Lax and header CSRF the simplest correct session design, with no credentialed CORS.specs/006-multi-tenancy/research.md R3
