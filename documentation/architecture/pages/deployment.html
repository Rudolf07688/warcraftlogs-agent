Deployment & config

How the app runs today: four Docker Compose containers on a developer machine plus an always-on telemetry collector, configured from one root .env. This page covers the images, the proxying, every place configuration comes from, the checks that stop an unsafe start, the scripts and command-line tools, and how far the cloud deployment plan has got.

What runs, and where it lives

docker-compose.yml defines five services that start by default (the app's four and Alloy) and four more behind the observability profile, with six named volumes: pgdata, alloy-data, loki-data, tempo-data, mimir-data and grafana-data. docker compose up --build brings up the app and Alloy; docker compose --profile observability up -d adds the storage backends and Grafana.

Why

One docker compose up gives a full local stack, and secrets come only from the root .env through env_file. The owner asked for exactly this: "locally testable with a docker compose file that injects our root .env file".specs/001-streaming-chat-frontend/research.md §6 · specs/001-streaming-chat-frontend/spec.md (Input)

Postgres and Redis bind to loopback only (QA finding SEC-001). Redis has no auth, so it must not face the LAN.docker-compose.yml (comments on the db and redis ports)

Redis runs without persistence and with LRU eviction. It is a disposable cache, so recreating the container just empties it.specs/014-redis-wcl-cache/research.md R11 · docker-compose.yml

The database image is pgvector/pgvector:pg17-trixie: the same major version and on-disk format as postgres:17, so an existing pgdata volume starts as is. The trixie tag matches the glibc of postgres:17; the plain pg17 tag would leave a collation-version mismatch on an existing database.docker-compose.yml (comment on db.image) · backend/migrations/versions/0019_kb_chunks.py (docstring)

There are two database roles. The owner runs migrations, and the app connects as a runtime role without BYPASSRLS, so row-level security actually constrains it. The role is created by a migration rather than a mounted init script, because init scripts only run on a fresh volume and are fragile across platforms.specs/006-multi-tenancy/research.md R4 · docker-compose.yml (comment on db.environment) · backend/migrations/versions/0004_rls.py

Alloy is always on and the storage backends sit behind a profile, so the app and Claude Code can send telemetry from day one and a plain docker compose up stays light. Alloy queues on disk until the backends run.specs/telemetry_spec.md §14.1 (decision 8) · docker-compose.yml (comments on alloy)

ADC is mounted read-only rather than shipping a key, so the same code path works unchanged on Cloud Run with an attached service account.specs/001-streaming-chat-frontend/research.md §6 · documentation/deployment.md (Decisions)

Images & proxying

Techrequires-python >=3.14uv (uv.lock)uvicorn[standard]>=0.30.0vite ^5.4.2nginx:1.27-alpine

What it does, and where it lives

  • Backend image (backend/Dockerfile): python:3.14-slim, plus the runtime libraries the PDF reports need (Pango and HarfBuzz for WeasyPrint, freetype and libpng for matplotlib) and the DejaVu, Noto CJK and Noto Color Emoji fonts. It installs uv with pip, copies pyproject.toml, uv.lock, wcl_agent/ and backend/, runs uv sync --frozen --no-dev and starts uv run uvicorn backend.app.main:app --host 0.0.0.0 --port 8000. One uvicorn process, no --workers flag. See PDF reports for why the fonts matter.
  • Frontend image (frontend/Dockerfile): a deps stage on node:22-slim runs npm install. Target dev runs npm run dev -- --host 0.0.0.0 on 5173 (what Compose uses). Target build runs npm run build, and target prod copies dist/ into nginx:1.27-alpine on port 80.
  • Dev proxy (frontend/vite.config.ts): Vite proxies /api and /ws (with ws: true) to VITE_BACKEND_URL, default http://localhost:8000 on bare metal.
  • Prod proxy (frontend/nginx.conf): same paths. /api/ goes to http://backend:8000 with X-Forwarded-For and a 300 s read timeout for slow PDF reports. /ws upgrades the connection, passes Origin through and allows 3600 s read and send timeouts, because one chat socket stays open across many turns. /assets/ is cached for a year as immutable; every other path falls back to index.html with no-cache (client-side routes). Gzip is on for text types.

Why

The browser only ever talks to one origin (Vite or nginx), which proxies the API and the socket. That is what makes the __Host- session cookie and same-origin CSRF design work without credentialed CORS (see Auth & multi-tenancy).specs/006-multi-tenancy/research.md R3

The frontend Node stages use a glibc (Debian) base, not Alpine: Tailwind v4's native binaries and rollup/esbuild ship glibc prebuilts and crash on musl. The prod target exists so production serves a minified, code-split bundle (PERF-011).frontend/Dockerfile (header comment)

Python 3.14 and uv are fixed by the constitution's stack section (uv sync/uv add/uv run, a committed uv.lock). The constitution states the standard but gives no reason for it..specify/memory/constitution.md (Technology Stack & Standards)

InferredNo recorded reason for a single uvicorn process. It matches what the code assumes today: the login and investigate rate limiters, the kickoff pre-fetch cooldown, the background-task de-duplication and the model state on app.state are all per process. More workers would need those moved to shared state first; the recent-raids refresh already coordinates through a database row.

Configuration & secrets

Techpydantic-settings>=2.4.0python-dotenv>=1.0.1Google ADC

What it does, and where it lives

  • All secrets and settings come from the root .env (gitignored). .env.example is the tracked template, with every setting explained.
  • backend/app/config.py reads them into one typed Settings(BaseSettings), exposed as the module-level settings (cached by get_settings()). Unknown variables are ignored (extra="ignore").
  • The same module also calls load_dotenv() at import, because wcl_agent/ and ADK read some variables straight from os.getenv (for example WCL_LLM_PROVIDER, ANTHROPIC_API_KEY, WCL_MAX_CONCURRENCY, WCL_MODEL_LOCATION). WCL_LOAD_DOTENV=0 switches off both load_dotenv() and the settings' env file; the test suite sets it so a checkout's .env never reaches a test (sc-336).
  • Model roles (chat default, report, guide, guide review, fast, greeting) are blank in Settings and filled per provider by the _resolve_roles validator, so switching provider is one .env line (feature 032). Details on Models & providers.
  • Google auth is ADC everywhere. No Google key file is in the repo or in .env. The one API key the app can use is ANTHROPIC_API_KEY, read only when WCL_LLM_PROVIDER=anthropic.

Start & DB-init scripts

Techbashalembic>=1.13.0uv

What it does, and where it lives

  • bin/00_init_migrate_db.sh: sources .env, runs uv sync --all-extras (creating .venv if that fails, then syncing again), starts only db, then runs alembic -c backend/alembic.ini upgrade head. If that upgrade fails, it tries the fresh-database path: upgrade to 0002_auth_tenancy, run backend.cli.bootstrap_admin, then upgrade to head.
  • bin/01_start_app.sh [--build]: runs the init script, exports WCL_GIT_SHA (the short commit, the backend's service.version, since the image has no .git), then docker compose up -d (passing the flag through), prints docker compose ps and follows the logs. Ctrl+C or exit runs docker compose down, so the stack stops with the script.
  • bin/claude-otel [claude arguments...]: starts Claude Code with OpenTelemetry pointed at the local Alloy. It is not part of the app's start-up; see Observability.
  • backend/cli/init_db.py does the same migrate → founder → migrate sequence as one idempotent Python command: upgrade to 0002_auth_tenancy, create the founder only if no active platform admin exists, then upgrade to head. Safe to run on every deploy.
  • Alembic connects as the owner role (settings.owner_database_url, set in backend/migrations/env.py) and leaves ADK's own tables (sessions, events, app_states, user_states) out of autogenerate. The migrations are on Database & migrations.

Why

The founder must exist before 0003_tenant_columns backfills existing rows to the founder's tenant, which is why init is a three-step sequence.backend/cli/init_db.py (docstring) · specs/006-multi-tenancy/research.md R8

InferredNo recorded reason for the bin/ scripts (added without a spec). They wrap the quickstart steps into one command for local bring-up. They duplicate the logic of backend/cli/init_db.py in shell, and any failure of the first upgrade head (not only a fresh database) sends them down the bootstrap path, which stops with an error when the BOOTSTRAP_ADMIN_EMAIL user already exists. init_db checks for an admin first instead.

Cloud deployment plan Planned, not built

Technone yet (Cloud Run, Cloud SQL, Secret Manager in the plan)

Status

documentation/deployment.md is the design-for-later plan, and "Deployment / Hosting Plan" (sc-146) is still an open item in todo.md. The plan: backend on Cloud Run with an attached service account (ADC), Cloud SQL for PostgreSQL 17, secrets from Secret Manager as environment variables, session affinity for WebSockets, and CPU always allocated so in-process background work is not throttled. The frontend would be the static build on a CDN or a second Cloud Run service. Nothing in the repo provisions any of this: there is no CI, Terraform or Cloud Build config.

Things a production deployment must set or decide, taken from the code:

  • A strong SECRET_KEY and a real SITE_URL (the backend refuses to start otherwise), SESSION_COOKIE_SECURE=true with HTTPS, and TRUSTED_PROXIES set to the proxy's address so per-client rate limits work behind it.
  • A Postgres with pgvector 0.8 or newer (migration 0019_kb_chunks checks the version), and an owner role that may CREATE EXTENSION and CREATE ROLE, or a runtime role created by hand first.
  • A Redis, or none: without REDIS_URL every WCL lookup goes to the store or WCL. No managed Redis is planned yet.
  • One backend instance, or shared state for what is per process today (see Images, Why).

Drift: parts of documentation/deployment.md are out of date. It still says access is "public + unauthenticated for v1" and that tables are made by create_all; feature 006 replaced both with invite-only login and Alembic. It also predates Redis, pgvector, the Anthropic provider and the raw store. In .env.example, BLIZZARD_CLIENT_ID/BLIZZARD_CLIENT_SECRET are listed but no code reads them, and the provider comment still says suggestions, titles, reports and guides call Gemini "until feature 035", which has shipped.
