Architecture · User-facing

Frontend

A React single-page app: the streaming chat with Barnaby, the sidebar of chats and raids, the welcome page, the profile and class-guide pages, and the admin and sign-in screens. It talks to the backend on the same origin through a proxy, over one WebSocket and a small typed REST client.

Build and serving

Techvite ^5.4.2@vitejs/plugin-react ^4.3.1tailwindcss ^4.3.3@tailwindcss/vite ^4.3.3vitest ^3.2.7jsdom ^26.1.0@testing-library/react ^16.3.3node:22-slimnginx:1.27-alpine

What it does, and where it lives

  • Scripts (frontend/package.json): dev runs Vite, build runs tsc -b && vite build, test runs Vitest. Tests (14 *.test.tsx files) run in jsdom from frontend/vitest.config.ts, kept apart from the build config.
  • Dev server (frontend/vite.config.ts): port 5173, plugins @vitejs/plugin-react and @tailwindcss/vite. It proxies /api and /ws (with WebSocket upgrade) to VITE_BACKEND_URL, default http://localhost:8000, so the browser sees one origin.
  • Image (frontend/Dockerfile): a deps stage on node:22-slim (glibc, because Tailwind v4's native binaries crash on musl), a dev target running the Vite dev server (what docker compose uses locally), and a prod target that serves the built files with nginx:1.27-alpine.
  • Production proxy (frontend/nginx.conf): the same paths as the dev proxy, to backend:8000. /api/ has a 300 s read timeout (PDF generation can take a while); /ws upgrades the connection and allows 3600 s, as a chat socket stays open across many turns. Hashed /assets/ are cached for a year; every other path falls back to index.html.
  • Code splitting. The chat (App) loads eagerly. Every other page, KaTeX (with its CSS and fonts), Plotly and the particle engine are separate chunks loaded on first use.

State

What it does, and where it lives

  • No state library. App.tsx holds the chat state in useState (models, conversations, raids, active chat, messages, status line, live spell cards, boss selection, loose proposals) and mirrors what the socket handler needs in refs, so the frame handler and the send callbacks stay stable. AuthProvider is the only context.
  • Streaming text lives outside React. Tokens go into lib/streamStore.ts, a tiny external store read with useSyncExternalStore. Only LiveMessage subscribes, so a token re-renders the live message and nothing else; Sidebar, Composer and MessageList are memoised.
  • Per-turn buffers. Charts, proposals and bosses that arrive during a turn are kept in refs and attached to the answer on done. A proposal belongs to the chat that made it: if the player has switched chats, it is not shown in the other one (sc-243). The same holds for the answer itself: the done frame appends it only to the chat that asked, and the backend has it saved for when the other chat is reopened.
  • A dropped socket ends the turn here. A new socket has no turn running, so no done or error frame will ever come for the old one. ChatSocket reports every connection change to handleStatus in App.tsx. A drop while a turn streams keeps the text received so far as a message (only if the chat that asked is still open), shows "Connection lost, the answer may be incomplete.", unlocks the composer and clears the live cards and buffers; unplaced proposals become loose ones. It remembers the chat and the partial text in dropRef. When the socket is back up, reloadAfterDrop replaces the chat's messages with what the backend saved (after a network blip: the saved partial answer; after a backend restart nothing was saved, so the local partial text is kept). The reload does nothing if another chat is open, a newer turn has begun (turnSeqRef) or a turn is streaming; if the request fails the drop is kept for the next reconnect, until a new turn or opening a chat makes it stale. Frames that only make sense during a streaming turn (token, tool_start, tool_end, done) are ignored while no turn is streaming here; an error frame is still shown.
  • Wire contract. How frames update this state is on Stream protocol.

Streaming renderer

Techstreamdown ^2.7.0remark-math ^6.0.0rehype-katex ^7.0.1katex ^0.19.0unist-util-visit ^5.1.0motion ^14.0.0

What it does, and where it lives

  • Markdown. components/StreamMarkdown.tsx wraps Streamdown, which renders GFM safely mid-stream (no flashing ** or broken tables) and memoises finished blocks. The live reply uses streaming mode with incomplete-markdown parsing; finished messages use static mode.
  • Smoothing. hooks/useSmoothText.ts releases the streamed text on requestAnimationFrame at an adaptive rate (at least 4 characters per commit, faster when behind) and commits at most every 33 ms, so the socket's uneven bursts don't look jittery.
  • Ink-in. lib/rehypeWordSpans.ts wraps each word of the live reply in a span.ink that a CSS animation fades in (skipping code and pre). Finished messages skip it, as the effect has played and a span per word is costly on long answers. An ember caret trails the stream and a one-shot sheen marks the finished reply.
  • Maths. KaTeX loads the first time a reply contains maths ($$, \(, \[ or $…$), through Streamdown's plugins.math slot (lib/mathPlugin.ts). remark-gfm is declared in package.json but not imported; Streamdown brings GFM itself.
  • Message furniture (components/MessageList.tsx): the spellbook of tool cards, charts, confirmation cards, a per-reply "Report" PDF button, "Used web search" and "Answered by …" notes, "Interrupted — partial response" for partial messages, and on the latest answer only, the boss picker (EncounterPicker) and follow-up buttons (FollowUps). Ticked bosses are appended to the next question as "(Focus on: …)".

Markdown safety

What it does, and where it lives

Model output can echo text from combat logs and web pages, so the renderer treats it as untrusted. The rules live in components/StreamMarkdown.tsx:

  • No images at all. Streamdown's harden step is re-run with allowedImagePrefixes: [], so every markdown image becomes a "[Image blocked: alt]" text span (sc-157). data: images were already dropped by Streamdown's URL transform.
  • No img, source or srcset after sanitising. A final rehype pass (rehypeNoImages) removes every <img> and <source> and strips srcSet. Harden only checks img src, a <picture><source srcset> would be fetched before the image (QA BUG-001), and an allowed same-origin image such as ![](/api/…pdf) fired an authenticated, costly GET the moment it rendered (sc-272).
  • Links need a click. Links keep harden's default (any http or https), plus Streamdown's placeholder protocol for a half-streamed link, and always open in a new tab with rel="noopener noreferrer", so following a Warcraft Logs source never loses the chat.
  • The same "no remote images" rule holds in the PDF, enforced separately on the server (PDF reports).

Tool labels and spells

Techmotion ^14.0.0react-icons ^5.7.0 (gi)

What it does, and where it lives

  • Status labels (frontend/src/toolLabels.ts): 24 tool names map to a friendly phrase for the thinking line ("Pulling rankings", "Searching what we already know"); any other tool shows "Searching Warcraft Logs". The same file words the rate-limit retry and model-fallback status lines.
  • Spells (frontend/src/lib/spells.ts): 25 entries (the same 24 tools plus web_search), each with a game-icons.net icon, a magic-school hue, a verb and rotating flavour lines. Unknown tools get DEFAULT_SPELL, so a card never renders blank.
  • Cards (components/SpellCard.tsx, RuneCircle.tsx, CastBar.tsx): casting (rune circle, cast bar, flavour) → resolved (a compact chip with the summary and duration) or fizzled. Each card stays at least 600 ms so fast or cached tools don't flicker. On a finished message the cards fold into a "📖 N spells cast" disclosure.
  • Drift: create_chart and get_coaching_brief are agent tools but have no label and no spell, so they show the generic "Searching Warcraft Logs" and the default spell, although the comment in spells.ts says every tool must be mapped.

Theme

What it does, and where it lives

  • One fixed theme, "Tavern Hearth" (ember gold over dark oak). Its tokens are oklch() values on :root in frontend/src/index.css, read by Tailwind's @theme inline block, by the shadcn components and by the hand-written rules in styles.css. There is no theme or background switcher. index.html sets data-theme="dark", which turns on Tailwind's dark: variant.
  • Fonts. Cinzel (display) and Alegreya Sans (body) are loaded from Google Fonts by an @import at the top of index.css; this is the app's one third-party request from the browser. The PDF uses bundled copies of the same fonts.
  • Ambient world (components/Ambient.tsx): slow blurred gradients, grain and vignette in CSS over the fixed backdrop image (--bg-image, from frontend/public/assets/), plus a capped particle field (AmbientParticles.tsx, lazy). Particles and drift are off under reduced motion, and the engine pauses when the tab is hidden and while a reply streams.
  • Colour bridge. The PDF copies these tokens as hex in backend/app/services/report_theme.py, which must be kept in step by hand.

Scrolling

Techuse-stick-to-bottom ^1.1.6

What it does, and where it lives

  • MessageList is a StickToBottom container: while the player is at the bottom, new content keeps the view pinned there, with smooth resize. Scrolling up releases it, and a "Back to bottom" button appears.
  • Scroll to the question (sc-140): when an answer completes and the player was following the stream, the view scrolls so the question that produced it sits at the top, so reading starts at the beginning. It releases the stick-to-bottom lock to do that, and re-engages it when the next turn starts (BUG-006). Reopening a chat, follow-ups, a failed turn or a player who scrolled away leave the view alone. Reduced motion makes the scroll instant.

Talking to the API

What it does, and where it lives

  • Same origin. The browser only ever calls its own origin; the Vite proxy (dev) or nginx (production) forwards /api and /ws to the backend. Requests send the session cookie with credentials: "include".
  • CSRF. AuthProvider receives the per-session CSRF token from login, invitation accept or GET /api/auth/me and hands it to setCsrfToken; it lives in memory only, never in storage. Every POST, PATCH and DELETE adds it as X-CSRF-Token. The WebSocket needs no token: its handshake is checked by cookie and Origin.
  • Errors. send() in api/restClient.ts turns a failed response into an ApiError with status, code and message from the backend's error envelope. A rejected WebSocket handshake (close code 1008) sends the browser to /login.
  • PDF downloads are a plain fetch of the report URL, turned into a blob and saved through a temporary link.

Browser telemetry

Tech@grafana/faro-react 2.13.0@grafana/faro-web-tracing 2.13.0

What it does, and where it lives

  • Off unless configured. initTelemetry() in telemetry/faro.ts does nothing, and loads none of the Faro packages (they are dynamic imports), unless VITE_FARO_URL is set. Compose sets it for the dev server to http://localhost:12347/collect, the Faro receiver in Alloy; an empty value switches it off. The other settings are VITE_FARO_API_KEY, VITE_FARO_APP_VERSION and VITE_FARO_ENVIRONMENT.
  • What it reports. Web Vitals, uncaught errors, route changes (through the router instrumentation), chat events and browser traces for page loads and fetch and XHR calls; the app is named web in namespace wcl-agent. Console output is not captured.
  • Route as the view. faro.ts maps the router's location to the matched route template (/app/*, unmatched when none) and sets it as Faro's view through setRoute() in context.ts, on start and on every navigation, so each signal carries it as view_name and never a raw path.
  • Error boundaries. TelemetryBoundary (telemetry/ErrorBoundary.tsx) wraps the whole router (name shell) and, in App.tsx, the sidebar, the message list and the composer. A panel that throws shows PanelFallback, a plain "Something went wrong in this part of the page" with Retry and never the error text (it can carry model or WCL text); the other panels keep working. The panel boundaries reset when the conversation changes (their reset key is the conversation id). The report is an error named React ErrorBoundary <type> whose stack is the component stack, with the boundary's name and the route as context, pushed through reportError() in context.ts, which is a no-op while Faro is off. React Router's data router catches a route render error before the shell boundary around it can, and would show its own page with the message and stack, so the root route in routes.tsx has an errorElement (RouteErrorFallback) that reports as the shell and shows the same fallback; its retry reloads the page.
  • Chat events. ChatSocket starts a TurnEvents object (chatEvents.ts) per sent turn, and each event fires at most once: agent_message_sent at the send, agent_first_token_rendered (ttft_ms) when LiveMessage in MessageList.tsx has put the first text on screen, agent_response_completed (duration_ms) on the done frame and stream_aborted (reason: connection_lost, or closed when the app closed the socket) when the connection closes mid-turn. An error frame ends the turn without either of the last two. Attributes are the model and whole milliseconds, never message text or ids, through pushTelemetryEvent(). There is no feedback event: the app has no feedback feature.
  • Click to database. Tracing adds a W3C traceparent to same-origin REST calls only, and restClient.ts adds x-faro-session-id. On the chat socket, a send opens a "chat send" span in ChatSocket and puts its traceparent and the session id into the message, because a browser WebSocket cannot set headers; the backend's "chat turn" span becomes its child (Stream protocol, Observability). A session that Faro did not sample sends no traceparent.
  • Privacy. The signed-in user is reported as a salted SHA-256 prefix of the account id (identifyUser in AuthProvider), never the email. A beforeSend hook (scrub.ts) cuts the query and fragment off every URL in every item, so an invite or password-reset #token= never leaves the browser.
  • Where it goes. To Alloy's faro.receiver, which stamps and redacts what it gets like any other signal (Alloy).

Why

Each chat panel has its own boundary and the route tree has its own errorElement, because a data router handles route render errors itself and a boundary outside it never sees them; without them one broken panel would blank the chat or show a stack trace.frontend/src/telemetry/ErrorBoundary.tsx (RouteErrorFallback comment) · frontend/src/routes.tsx

The Faro key ships in the bundle and is not a secret, so the receiver's CORS list, size cap and rate limit are the protection, and the browser's payload is never trusted to name its own service.observability/alloy/config.alloy (comment above faro.receiver)

Why

React, Vite and TypeScript to start with: the first UI requirement met with the least machinery, and easy to extend.specs/001-streaming-chat-frontend/research.md §7

React 19, Tailwind v4, shadcn/ui, motion, Streamdown, use-stick-to-bottom and tsparticles were a user-directed full adoption of the chat-UI skill stack: Streamdown (no broken markdown mid-stream), motion (declarative spell-card lifecycle) and stick-to-bottom (chat scroll) each solve a problem the hand-rolled code handled poorly. Alternatives: a curated subset or CSS only (declined by the user); staying on React 18 (fights the peer dependencies).specs/004-raid-sourcing-ux/research.md R7

One fixed theme with tokens on :root and no switcher: the owner wanted "one good theme we set", and one theme is simpler than a multi-theme engine. Alternatives: a theme switcher with View Transitions; a theme plus background toggle.specs/004-raid-sourcing-ux/research.md R8

Smoothing on requestAnimationFrame, CSS-only word ink-in, a spell registry keyed by tool name with a default fallback, and a minimum card display time, so the stream reads smoothly at 60 fps and per-tool presentation stays data-driven.specs/004-raid-sourcing-ux/research.md R9

shadcn/ui through the shadcn MCP is a constitution rule: one registry-backed implementation per control; hand-built components (spell cards, cast bars, rune circle) need a recorded reason..specify/memory/constitution.md Principle VII

Components come in through the shadcn CLI, which brings the unified radix-ui package and the icon-library mapping. Alternatives: copying sources by hand; writing our own primitives.specs/010-shadcn-ui-adoption/research.md R1

Plotly in the browser: interactive, hoverable charts were the user's explicit goal; the weight is contained by plotly.js-dist-min and lazy loading.specs/005-guild-context-artifacts/plan.md (Complexity Tracking)

react-router-dom: public auth routes, the guarded chat and the admin page could not be expressed by the single-App render without a hand-rolled router.specs/006-multi-tenancy/plan.md (Complexity Tracking)

The same-origin proxy is what makes the __Host- cookie, SameSite=Lax and a header CSRF token the simplest correct session design, with no credentialed CORS.specs/006-multi-tenancy/research.md R3

The welcome page is the no-conversation state, not a route, and learns about new raids by polling: no navigation change and no new transport at a 3 s cadence.specs/013-welcome-recent-raids/research.md R6, R11

Streaming text outside React state, memoised shell components and lazy chunks for KaTeX, particles and non-chat pages: a token used to re-render the whole app.documentation/ai_guide.md §17

No images in model markdown: a crafted log or web page could make the model emit an image URL that leaks data the moment it renders, and a same-origin image fired an authenticated, costly request; the app itself never puts images in markdown.frontend/src/components/StreamMarkdown.tsx (sc-157, sc-272 and QA BUG-001 comments)

Scroll to the question when the answer completes, so the reader starts at the beginning of a long answer instead of its end.frontend/src/components/MessageList.tsx (ScrollToQuestion comment, sc-140)
