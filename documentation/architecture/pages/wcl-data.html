WCL client, cache & store

Every piece of Warcraft Logs data the app uses goes through one async API client. In front of it sit two local layers: a shared Redis cache of typed values, and a Postgres store that keeps every raw response and answers repeat queries from it. A lookup tries Redis first, then the store, then Warcraft Logs, and the store only serves what the asking workspace is allowed to see.

What it does, and where it lives

The wcl_agent package holds the client and the cache and has no database code, so the CLI and the evals run without Postgres (and without Redis). The backend plugs the store in at start-up through two hooks on the client: a fetch sink that receives every response, and a fetch source that may answer a query before the network is used.

One lookup, end to end

The read order is Redis → store → Warcraft Logs. Redis is asked by the caller (get_or_load); the store is asked inside the client, so every query, cached family or not, gets the store check and every network answer is persisted.

  1. A tool, a background job or the pre-fetch calls get_or_load with a typed family and key.
  2. It reads the key from Redis (memoised families first check the process memo).
  3. On a hit it decodes the model and returns it. Done.
  4. On a miss it takes a per-key lock. A lock loser in another process polls for the winner's value for up to 2 s.
  5. The loader calls AsyncWCLClient.query.
  6. The client joins an identical in-flight request from the same workspace, or starts one, and waits for a lane slot.
  7. Inside the slot it asks the fetch source for a stored body (first attempt only).
  8. The store source reads the row through the visibility and freshness rules, bounded by 400 ms and a breaker.
  9. Postgres returns the body, or nothing.
  10. On a hit the body goes back with no token, no network call, no sink offer and no grant. The flow continues at step 14.
  11. On a miss the client gets an OAuth token and POSTs the GraphQL query with an injected cost field.
  12. A 429 or 5xx is retried up to twice with backoff, outside the slot.
  13. The raw response is offered to the FetchWriter. This never blocks; a full queue drops it from storage only.
  14. The body is parsed (off the loop above 256 KB) and the loader builds the family's Pydantic model.
  15. The model goes to Redis with its TTL and jitter (unless the answer was grant-only), and the lock is released.
  16. The model goes back to the caller.
  17. Later, the writer's own task upserts the response into raw_fetches, with grants and report statuses, in a batch.

Why

The store is asked from inside query() because every read passes there. Redis-cached families call it from their loaders, so the order Redis → store → WCL and the Redis back-fill come for free, and the heavy uncached calls (tables, events, graphs) gain most. Rejected: asking it from a place shared by callers of different workspaces, which would serve one workspace's visibility decision to another.specs/039-local-first-data/research.md R5 · specs/045-local-data-reads/research.md R3

Warcraft Logs API client

What it does, and where it lives

  • wcl_agent/client/wcl_client.py: AsyncWCLClient on an httpx.AsyncClient (timeout 60 s, connect 5 s, at most 16 connections), one per event loop (get_async_client(), which needs WCL_CLIENT_ID and WCL_CLIENT_SECRET). It posts to https://www.warcraftlogs.com/api/v2/client. The app's fixed queries live in wcl_agent/client/queries.py; wcl_agent/client/aio.py has gather_settled for fan-out inside one tool.
  • One chokepoint. query() does single-flight: one shared task per sha256 of the query plus its sorted variables, cancelled only when its last waiter leaves. With a fetch source installed the flight key also carries the source's scope (the workspace id), so callers of different workspaces never share a flight. _fetch does the rest: the 75 s overall timeout (WCL_QUERY_TIMEOUT_S, slot wait included), the store probe, OAuth, the POST, retries, cost logging and the sink.
  • OAuth. A process memo per client id (shared across loops), then the shared oauth_token Redis entry, then https://www.warcraftlogs.com/oauth/token. Tokens are renewed 60 s before expiry (3600 s assumed when the answer has no expires_in); an asyncio.Lock makes concurrent first calls fetch one. A 401 refreshes once, never reuses the rejected token, and retries.
  • Lanes (LaneLimiter, one per loop). WCL_MAX_CONCURRENCY (6) caps requests in flight. Work inside background_lane() (guides and their data sheets, the patch lookup, recent raids, the kickoff pre-fetch's boss tables) holds at most WCL_BACKGROUND_CONCURRENCY (2, clamped to 1…total−1) slots, and never takes one while a chat lookup waits. Waiters are served first in, first out. A flight carries a LaneTicket: when a chat caller joins a background flight, promote() moves it to the interactive lane, so a chat turn never waits on the background cap for a warm-up that shares its query.
  • Retries. 429 and 5xx get up to 2 retries: 0.5 s · 2^n plus up to 0.25 s jitter, or Retry-After capped at 10 s. Backoff waits outside the slot and is skipped when it would outlast the query timeout. A 429 whose Retry-After is longer than 10 s means the hourly budget is spent: the client answers every later call with a synthetic 429 until then. With a store installed, the probe still runs first, so stored answers keep working while WCL refuses us.
  • Cost. Every query without fragments gets _cost: rateLimitData { limitPerHour pointsSpentThisHour pointsResetIn } inserted into its top-level selection. Each response logs wcl_cost op=<operation> points_this_hour=… delta=…, and the latest snapshot answers acheck_rate_limit() for 30 s without a request of its own. Callers never see _cost; the store strips it too.
  • Errors. A body with GraphQL errors raises RuntimeError after the gone check below. Bodies above 256 KB are parsed in a thread.
  • Fetch sink (set_fetch_sink, feature 020). After a successful network call _fetch hands the sink a FetchedResponse (query key, query, variables, raw bytes, fetched_at, requested_at), or a ReportGone instead when the answer says the report is gone (below). The sink must be O(1); a failing sink never fails the fetch. It is unset in the CLI, evals and tests.
  • Fetch source (set_fetch_source, a FetchSource protocol with __call__ and scope(), feature 039/045). It returns a StoredFetch(content, shared) or None; any exception is a miss. The answer's origin is network, shared (every report public) or private (visible through a grant). In each caller's own context, network marks the chat turn and the cache load as external; private marks the cache load unshareable, so it stays out of shared Redis and the memo.
  • Report-code parsing, which the store trusts: report_codes(), the strict exact_report_codes() (None for comments, a report( field whose code it can't read, or a padded code) and returned_report_code() (a plain one-report query whose response really holds that report). Hand-written queries (run_wcl_graphql) can't earn a grant or delete a report through them.

Why

A native async httpx client replaced requests plus threads: real cancellation, no GIL contention (QA measured 35 ms average and 157 ms worst-case loop lag), and no new dependency. Alternatives: aiohttp (a new dependency); threads with cancel flags.specs/013-welcome-recent-raids/research.md R7

Lanes keep background work out of the chat's slots in about 40 lines. Alternatives: two semaphores (background could still take interactive slots); a priority-queue dispatcher.specs/013-welcome-recent-raids/research.md R8

A chat turn that joins a background flight promotes it, because the kickoff turn's identical queries otherwise waited on the 2-slot background lane (QA PERF-001).specs/046-big-report-turns/research.md R4 (As built)

Retries and cost injection at the one chokepoint cover every call, uncached and agent-written ones included. Alternative: a separate rateLimitData query per call (doubles requests).specs/014-redis-wcl-cache/research.md R6

The token memo sits in front of Redis, so a Redis outage never turns into an OAuth request per WCL call.specs/014-redis-wcl-cache/research.md R5

Redis cache

Techredis>=6 (redis.asyncio)redis:8-alpinepydantic models as JSONfakeredis>=2.30 (tests)

What it does, and where it lives

  • wcl_agent/cache/cache.py: get_or_load(family, key, model, loader, ttl=…, force_refresh=…) is the only way code reads or writes cached data; get_many_or_load is its batched form (one MGET, one loader call for all misses, one pipelined write, no lock) for background batches. Values are Pydantic models from cache_models.py, stored as JSON. All keys are built in the keys class, and no wcl: key holds a user, tenant or conversation id: everyone shares one entry.
  • Loads. A loader returning None caches a {"_missing":true} marker for WCL_NEG_CACHE_TTL (60 s). TTLs are stretched by a random 0–10 % (WCL_CACHE_JITTER), except the OAuth token. A value that fails validation is deleted and loaded again. Values above 256 KB are decoded in a thread.
  • Locks and joiners. Concurrent callers of one key in one process share one load (a per-loop single-flight). Across processes, the first caller takes SET lock:<key> NX PX (WCL_CACHE_LOCK_MS, 90 s, longer than the 75 s query timeout); losers poll every 100 ms for up to WCL_CACHE_LOCK_WAIT_MS (2 s), then load themselves without writing. force_refresh never joins a flight. Grant-only rule: when the shared load was served by the store through the first caller's grant (marked unshareable), a joiner never takes its value; it runs its own lookup and gets what it would get alone (QA SEC-001).
  • Process memo. char_id, world_zones and game_classes are also kept in-process (up to 1024 entries) in front of Redis, so they stay cheap when Redis is slow or absent. Memoised values are shared instances (read-only).
  • Fail-open. One Redis client per event loop with 250 ms socket timeouts; after a Redis error that loop leaves Redis alone for 5 s (a circuit). Without REDIS_URL, or with WCL_CACHE_ENABLED=false, the loader is simply called and nothing is counted. A Redis problem never reaches the caller.
  • Finished reports (wcl_agent/cache/normalize.py, FINAL_AFTER): a report is finished once its end time is at least 2 h old. The three report families keep their family TTL only then; a report still being logged gets WCL_CACHE_UNFINISHED_TTL (120 s) (_report_ttl in wcl_agent/tools/report_tools.py). The store uses the same rule.
  • Report eviction (evict_report): when a report is found gone, the writer first sets wcl:v1:gone:<code> (for WCL_CACHE_LOCK_MS), then SCANs and deletes wcl:v1:report:<code>:* (the code glob-escaped). Every report-family write checks for that marker after its SET and deletes its own key, so a load that read old data can't write it back.
  • Forced refresh. The character rankings tools may force a reload at most once per user per character per minute (chat:refresh:<user>:<char_id>, the one key with a user id, outside the wcl: space).
  • Compose (docker-compose.yml): redis:8-alpine with maxmemory 256mb, allkeys-lru, no persistence, port bound to 127.0.0.1 only (it has no auth). The backend container gets REDIS_URL=redis://redis:6379/0.

Raw store: writing every response

Techasyncio queue + one consumerPostgreSQL JSONBSQLAlchemy Core upserts

What it does, and where it lives

  • Offer (FetchWriter.offer, installed by start()): O(1), never awaits, hops threads with call_soon_threadsafe. It reads the tenant from current_identity in the fetching task's context, so the item remembers which workspace's turn fetched it (None outside a turn).
  • Bounds. At most WCL_FETCH_PERSIST_QUEUE_MAX (500) fetches and WCL_FETCH_PERSIST_QUEUE_MB (64) MB wait. Beyond that the newest fetch is dropped and counted in a warning at most once a minute. A ReportGone is never capped, and a dropped summary of our own query that holds a private or null report is parsed in a tracked task so its gone codes still queue (sc-353).
  • Batches. One consumer takes up to 20 items and 8 MB per transaction, with a 10 s timeout. On any error, a timeout included, each item is retried alone (10 s each), so one bad item loses only itself and a gone signal is never lost with a batch. Failure logs carry only the exception class and SQLSTATE, never the statement's parameters.
  • Upsert (upsert_raw_fetch): one row per query key; only a newer fetched_at replaces a row. The hash is sha256 of the body without _cost; an unchanged body only moves fetched_at and sets own_summary, without sending the payload. Postgres decodes the JSON and drops data._cost (CAST AS jsonb #- '{data,_cost}'), so no multi-MB parse runs on the loop. Operation names are cut to 120 characters, a code over 32 characters leaves report_code empty (it stays in report_codes), and \u0000 escapes are stripped.
  • Report statuses. Only our own summary queries (REPORT_SUMMARY and the batch ReportsBatch, which select code visibility endTime) record what WCL showed about each report in raw_reports; an older observation never wins. own_summary is set on exactly those rows (same query text, exact codes, exactly their own variables).
  • Grants come from what WCL returned, never from the query text alone: a summary grants each code whose report object came back; any other query grants its one code only when it is plain and its body holds that report. A workspace's grant is rewritten only when at least an hour older (GRANT_REFRESH). Grants sit under row-level security, so the writer sets the transaction's app.tenant_id once per tenant.
  • After the commit, each fetch whose stored payload changed goes to the knowledge base indexer (kb_indexer.offer_fetch), and gone codes are evicted from Redis with a 5 s bound, outside the timed DB write.
  • Stop: the sink is removed, then the queue gets 5 s to drain; what is left is dropped and logged.
  • Retention: none by age (the owner's rule). Finished reports are kept for good; a report's rows go only when WCL says it is deleted or private. Size check (specs/039-local-first-data/quickstart.md §3): 
    SELECT relname, pg_size_pretty(pg_total_relation_size(c.oid)) AS total_size,
       c.reltuples::bigint AS approx_rows
FROM pg_class c WHERE relname IN ('raw_fetches', 'raw_reports', 'raw_fetch_grants');

Why

The sink sits at the end of _fetch, which runs exactly once per network call, sees raw responses and covers uncached callers too. Alternatives: hooking get_or_load (misses uncached queries, sees typed models); hooking query() (once per single-flight waiter).specs/020-fetch-persistence/research.md R1

One consumer behind a bounded queue never slows the chat, uses one DB connection and keeps ordering simple. Alternative: a bounded task set (N connections, unordered writes).specs/020-fetch-persistence/research.md R4

Feature 020 wrote one row per transaction; feature 039 batches, because the store grows with every fetch and DB-first reads make it permanent, so it must stay cheap: batched commits, no rewrite of an unchanged payload, odd inputs that never fail an insert. The per-item retry keeps "one bad row loses only itself". The owner chose to refresh the fetch time of an unchanged payload rather than skip it.specs/039-local-first-data/spec.md (User Story 2, Clarifications, FR-008, FR-009) · research.md R8

InferredRefreshing fetched_at matters for freshness: a row first fetched while a report was live only becomes servable for good once it is known to have been fetched after the report finished.backend/app/services/raw_fetch_reads.py (is_fresh)

The database decodes the JSON because parsing in a thread would still leave SQLAlchemy's JSON bind running json.dumps on the loop.specs/020-fetch-persistence/research.md R3

A grant is written when the workspace's own turn fetched the code from WCL, because WCL checked access at that moment. Chat-pasted codes live only in free-text messages, so a union over raids and messages would miss them. Only our own summaries may state visibility, because a hand-written query could alias another field to forge one.specs/039-local-first-data/research.md R2, R3

A lost gone signal lets a private report's data be written back and served to a workspace with a grant, so an attacker must not be able to drop it by flooding the queue. Gone signals are never capped; a dropped summary is salvaged rather than exempting whole summaries from the cap, so memory doesn't grow with body size.specs/051-raw-store-hardening/spec.md (User Story 2) · research.md R3

Raw store: DB-first reads

TechPostgreSQL JSONB + GINrow-level security on grantsasyncio.timeout

What it does, and where it lives

  • The source (StoreSource, the instance read_stored_fetch in backend/app/services/raw_fetch_reads.py). It answers only queries for which exact_report_codes finds at least one report; character, ranking and world queries get None at once, with no database call. Its scope() is the turn's tenant id.
  • Visibility (fetch_visible_clause in backend/app/repositories/raw_fetches.py, the one definition). A row is served to a workspace only when it names at least one report, every code is at most 32 characters, and every code is either public (a raw_reports row with visibility = 'public') or granted to that workspace, each confirmed within RAW_STORE_REVERIFY_DAYS (1 day). No workspace (public-only reads) sees public reports only. The knowledge-base search applies the same clause.
  • Freshness (is_fresh): a row younger than WCL_CACHE_UNFINISHED_TTL (120 s) is fresh. Otherwise it is fresh only when every report it names was seen finished and the row was fetched after that report finished: then it is served for good. Rows naming no report are never served; Redis TTLs govern them.
  • The probe (probe_visible_fetch) uses at most four statements: the row's codes and fetched_at; the codes' statuses for the freshness check; the tenant scope, only when a code isn't publicly confirmed; then the visibility clause (for the tenant and for public-only) and the payload as bytes, pinned to the fetched_at of step one, so a row replaced meanwhile is a miss. Outcomes: hit, miss, not_visible. A hidden row answers exactly like a missing one.
  • Fail-fast. The probe runs in the lane slot of the flight's first attempt (so a fan-out holds at most that many DB connections), before the token and before the spent-budget check, with a RAW_STORE_PROBE_TIMEOUT_MS (400 ms) timeout. A timeout, a connection error or any other error is a miss: a turn never fails because of the store.
  • Back-fill. A hit whose reports are all public back-fills the shared Redis entry through the unchanged loader. A grant-only hit does not (see Redis cache). A report made private can therefore stay reachable by code for at most the re-verify window plus the Redis TTL (about 48 h).

The store breaker

A process-wide Breaker keeps a failing store out of the hot path. It counts outcomes over turns and workspaces, not one turn's burst of timeouts, and it opens for everyone only when more than one workspace sees the store failing (sc-355).

Why

The store answers only what WCL would show this workspace: the app uses client credentials, so WCL never returns a private report to it, and "private or deleted" shows up as a null report on a later fetch. The leaks to prevent are another workspace's unlisted data and data still served after its owner hid it.specs/039-local-first-data/research.md R1

Freshness follows the Redis rule for live reports; finished report data is effectively immutable and is kept and served for good. Non-report data stays with the Redis TTLs.specs/039-local-first-data/research.md R6

Public status and grants count for one day, not seven, because a store hit back-fills shared Redis: the exposure window for a report made private is the re-verify window plus the Redis TTL.specs/039-local-first-data/research.md R4, R9

400 ms and a breaker because a healthy local Postgres answers in 1–5 ms, and a hit is only worth it when fast; a bug shouldn't disable the store for everyone.specs/045-local-data-reads/research.md R1

The breaker counts timeouts per workspace and opens globally only across workspaces, so one account's turns, tabs and pre-fetches can't switch the store off for everyone, while a store slow for most reads still opens it.specs/052-turn-and-startup-hardening/research.md (Breaker rule, Identity)

The probe runs inside single-flight and a lane slot so identical concurrent probes are deduplicated and DB connections are capped at the lane limit; it precedes the spent-budget check so stored answers keep working while WCL refuses us.specs/045-local-data-reads/research.md R3

Deleted and private reports

Techin-process tombstonesRedis gone marker

What it does, and where it lives

  • Detection in the client (_gone_codes): only our own REPORT_SUMMARY query, with one exact code and a body of at most 4 KB, can say a report is gone: reportData.report is null and every GraphQL error (if any) is about the report itself and reads as not-found or permission. The client then offers a ReportGone(codes, seen_at) instead of the response. A null caused by a failing sub-field, a transient error or a hand-written query deletes nothing.
  • Detection in the writer: a stored summary (single or batch) that shows a report as private, or a batch entry that came back null, is a gone finding too (sc-322, sc-353).
  • What happens: the writer deletes every raw_fetches row whose report_codes contains the code (GIN-indexed) and its raw_reports row, then evicts the report's Redis keys. Grants stay: the rows they would unlock are gone, and rows only come back through a fresh WCL fetch. Rows whose query the strict parser couldn't read are filed under every string they contain (stored_codes), so delete-on-gone still finds them.
  • Tombstones (_Tombstones in fetch_persistence.py): the writer remembers each gone code for 10 minutes (at most 1024 codes). A fetch whose request was sent at or before its report was seen gone is not written: not its row, its statuses or its grant. When the cap evicts a young tombstone, a floor time keeps its protection, so a flood of made-up codes can't flush a real one. Only the private findings of a stale summary still count. Tombstones are per process and lost on restart.

Why

Deleting on gone is the owner's retention rule, and only our own summary query decides, because a hand-written query could alias, pad or hide what it really asks for.specs/039-local-first-data/research.md R7 · specs/039-local-first-data/spec.md FR-007

Tombstones close a real race: a table request started before a summary's null answer and finished after it would otherwise re-insert its row, and the kept grant would make it visible again.specs/045-local-data-reads/research.md R6

The overflow floor keeps the memory bound and still protects real tombstones. Alternatives: never evicting young entries (memory then rests on the WCL rate only); tombstoning only codes the store knows (misses a report's first fetch in flight).specs/051-raw-store-hardening/research.md R2

Exact lookups in stored data

TechGoogle ADK function toolspartial GIN index

What it does, and where it lives

backend/app/agent_tools/stored_data_tools.py gives the agent three tools (group "Stored data") that answer from the store without calling Warcraft Logs; the full tool list is on Agent runtime & tools. The data path:

  • Who asks comes only from the authenticated chat turn (current_identity, checked against the ADK user id). Every read runs in a tenant-scoped session, through the same visibility and freshness rules as the probe.
  • list_stored_fights and get_stored_fight_table build exactly the query the WCL tools send, compute its query key and read that one row with read_visible_fetch. Tables are compacted like the live tool's.
  • list_stored_reports_for_character reads up to 200 newest visible summaries (list_visible_summaries) and returns at most 25 reports whose roster names the character. On Postgres the lookup is driven by the workspace's grants and the reports confirmed public within the re-verify window: it reads only own_summary rows naming one of those codes (partial GIN index ix_raw_fetches_own_summary_codes), each body cut down in SQL to code, title, start, zone and actor names, under a 2 s statement timeout (sc-354).
  • Absent, hidden and stale rows all give one not_stored answer, so the agent falls back to the WCL tools and learns nothing about other workspaces' data.

Why

Exact keys plus one not_stored answer keep the visibility rule as the only gate, and identical results never leak that a row exists.specs/045-local-data-reads/research.md R9

The grants-and-public driver is complete: a visible row names at least one code that is public-checked or granted inside the window, so the driver removes only invisible rows while never scanning the whole history. Only own_summary rows count, so hand-written look-alikes can't crowd them out.specs/051-raw-store-hardening/research.md R5

Kickoff pre-fetch

Techbackground taskbackground lane

What it does, and where it lives

Clicking a recent raid (POST /api/raids/{code}/investigate, backend/app/api/raids.py) creates the conversation, commits, then calls kickoff_prefetch.schedule(). The agent's side of the kickoff turn is on Agent runtime & tools; this is the data path.

  • What it warms: the report summary (load_report_summary, through Redis, in the interactive lane) and one raw Summary table per boss (load_report_table, in background_lane()), at most 10 tables: each boss's last kill, else its last pull. It calls the tools' own loaders, so every query is byte for byte the one the turn will send, and the turn then hits Redis, the store or the pre-fetch's own in-flight request.
  • As whom: the clicking user's workspace (current_identity set in a fresh context). The sink therefore grants the report to that workspace exactly as its own turn would, and the store answers only what it may see. It is not a chat turn: no refresh actor, no turn counted.
  • Gates: it starts only after the endpoint's 404 rule (the report is the workspace's own recent or tracked raid), only when store reads are on and the store is installed (otherwise a whole-raid table is kept nowhere the turn could read), not while the breaker would skip this workspace, and once per (workspace, report) per 600 s (in-process). The endpoint itself is limited per user (WCL_INVESTIGATE_PER_MINUTE, 5). At most 11 WCL requests per click; failures are only logged.

Why

Identical tool calls give identical query keys, so the turn's calls become store or single-flight hits; acting as the workspace that passed the 404 rule gives the same grants its own turn would. Rejected: injecting data into the turn (puts WCL text in the prompt).specs/046-big-report-turns/research.md R4

The endpoint commits before it schedules, so a failed commit starts no pre-fetch.specs/052-turn-and-startup-hardening/research.md (Commit before schedule) · backend/app/api/raids.py (investigate_raid)

It is skipped without store reads, or while the store would skip the workspace, because the turn could not read what it fetched: the job would warm nothing.backend/app/services/kickoff_prefetch.py (module docstring)

Counters and cache stats

TechRedis hashes per UTC dayFastAPI

What it does, and where it lives

  • Counting. Outcomes are counted in the process and flushed every 2 s in one pipeline (a hit costs no extra Redis round trip; a failed flush keeps its counts). Keys are wcl:metrics:v1:{name}:{YYYYMMDD}, kept WCL_METRICS_RETENTION_DAYS (35) days. Nothing is counted while the cache is off.
  • Telemetry counter. The same outcomes are also added, once per key lookup, by its final outcome, to the OpenTelemetry counter app.cache.requests in _record(), labelled by family (app.cache.name) and a result of hit (a hit or a negative hit), miss (the loader ran, a lock timeout or a Redis error) or error. A step that another record follows (a corrupt entry before its reload, a batch-level Redis failure before the per-key misses, a failed write after a load) is not counted again; the admin counters below do count every step. It is a no-op while telemetry is off and feeds the runtime dashboards (Observability); the Redis counters below are separate and unchanged.
  • Per family: hit, miss, neg_hit, lock_timeout, error, redis_error, plus load-time sums.
  • Store probes (hash local): store_hit, store_miss, store_not_visible, store_timeout.
  • Store probes per WCL operation (hash store_ops, fields store_<outcome>@<operation>, sc-332). The operation is one of the app's 14 own query names (OWN_OPERATIONS), anything else counts as custom, so the hash can't grow without bound.
  • Local-answer rate (hash local: turns, local_turns). set_refresh_actor in backend/app/api/ws.py opens and closes a chat turn; a turn is local when it made no network WCL call (failed calls count as network), and waiting on another caller's WCL load counts as network too. A turn whose setup failed is closed uncounted (abandon_turn).
  • GET /api/admin/cache-stats?days=1..35 (default 7; platform admins only; backend/app/api/cache_stats.py, model CacheStats): per-family hits, misses, hit rate, average load time and status (ok, review, no_data), Redis health from INFO (keyspace hit rate, evicted keys, memory), the store totals and hit rate, store_by_operation, and the local-answer rate. An unreachable or disabled Redis gives the same shape with available: false.

Why

Application-level counters per family, not Redis INFO alone, because INFO is server-wide and can't say which family needs a TTL review.documentation/redis_cache_spec.md §4 (Why not just use INFO)

Per-operation store counts live in their own hash with a fixed allowlist of names, so the totals stay unchanged and an agent-written query name can't create unbounded keys.specs/052-turn-and-startup-hardening/research.md (Per-op counters)

Blizzard / Battle.net sources

Techhttpx>=0.27.0html.parser (stdlib)Redis families live_version, hotfix_feed

What it does, and where it lives

The class-guide pipeline needs the exact live build and the newest hotfixes, so a guide never targets the wrong patch. Warcraft Logs only knows the patch as major.minor. Both come straight from Blizzard, in backend/app/services/guide_pipeline/briefing.py. The guide pipeline itself is on Agent runtime & tools.

  • Each call opens a short-lived httpx.AsyncClient (10 s timeout, its own User-Agent). It is not the WCL client: no lanes, no OAuth, no fetch sink, so these pages are not stored in Postgres.
  • Live build (fetch_live_version): GET WOW_VERSION_URL (https://us.version.battle.net/v2/products/wow/versions), the launcher's unauthenticated pipe-separated file. parse_versions() reads only the us row of product wow, so a PTR build can't leak in. Cached in live_version for 15 minutes.
  • Hotfixes (fetch_hotfix_feed): GET WOW_NEWS_URL (https://worldofwarcraft.blizzard.com/en-us/news), find the newest "Hotfixes:" article, read its JSON-LD date and walk its body with html.parser into per-class and per-spec entries. Cached in hotfix_feed for 30 minutes.
  • Best effort. A failure is logged and returns None; it is not cached, so the next call tries again (a parse that finds nothing caches the 60 s "not found" marker). build_briefing then uses WCL's major.minor patch (looked up in the background lane), and without a hotfix feed no spec is marked as touched. Only when both Blizzard and WCL fail is generation postponed (PatchUnknown).
  • Blizzard's official sites are also tier-1, fetchable sources in the research step's SOURCE_TIERS (guide_pipeline/research.py). The class/spec roster comes from Warcraft Logs (wcl_agent/game/roster.py), not Blizzard's Game Data API.

Why

The versions endpoint is the only source of the exact build; it needs no credentials but is undocumented, hence the 15-minute cache and the WCL floor. Alternatives: WCL partitions only (too coarse); scraping patch notes.specs/015-grounded-class-guides/research.md R1

The news "Hotfixes:" articles are the official source and give per-spec detail, so only touched specs go stale; the parse needs only the stdlib.specs/015-grounded-class-guides/research.md R2
