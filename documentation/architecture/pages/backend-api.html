Backend API

One FastAPI process serves the REST API, the chat WebSocket and all background work. This page covers how the app is assembled, every router, the boot sequence behind the readiness gate, error handling, the in-process background tasks and lanes, and the service layer at a glance. The agent itself is on Agent runtime & tools; the socket protocol is on Stream protocol.

The app

What it does, and where it lives

  • backend/app/main.py builds FastAPI(title="WCL Agent Chat API", lifespan=lifespan). Middleware, outermost first: CORSMiddleware (origins from CORS_ORIGINS, credentials allowed), then FaroSessionMiddleware (copies a valid x-faro-session-id header to the session.id attribute of the request's server span; it does nothing without telemetry), then ReadinessGate. CORS is added last so the gate's 503s still carry CORS headers. Then the error handler and the 15 routers.
  • Logging is set up at import: one root handler if none exists, backend.app and wcl_agent at INFO (uvicorn only configures its own loggers), then the RedactionFilter on the root logger, its handlers and the uvicorn loggers (see Auth). When telemetry is on, an OTLP log handler is added to the root logger after that; it carries its own RedactionFilter.
  • Telemetry starts first. The very first statement of main.py after the standard-library imports is configure_telemetry() from backend/app/telemetry/, before FastAPI and ADK are imported: global instrumentation (FastAPI, SQLAlchemy, Redis, httpx) must exist before the app and the engine are created. It is a no-op unless OTEL_EXPORTER_OTLP_ENDPOINT is set; with PYROSCOPE_SERVER_ADDRESS also set it starts the CPU profiler for span profiles. The package's own modules (config, content policy, redaction, providers and exporters) are described on Observability.
  • The code is layered: routers in backend/app/api/ → logic in backend/app/services/ (and kb/, agent_tools/) → queries in backend/app/db/repository.py and backend/app/repositories/ → ORM in backend/app/db/models.py. Boundary types live in backend/app/schemas.py.
  • The standalone wcl_agent/ package holds the WCL client, the Redis cache, the agent and its WCL tools, and the model/provider layer. It has no database imports; the backend plugs persistence in through hooks it sets at startup (the fetch sink, the fetch source, the brief loader). See WCL client, cache & store.
  • Runtime model state (the selectable models, the default, a degraded flag) lives on app.state and is read through backend/app/model_state.py.

Why

FastAPI with asyncio is a constitution rule: all endpoints are async def, and request-path I/O is non-blocking. "A single async framework keeps I/O-bound work (the dominant cost in this app — external API calls) efficient and the backend consistent.".specify/memory/constitution.md Principle V · specs/001-streaming-chat-frontend/spec.md (Input)

Blocking or CPU-heavy work (password hashing, model probes, PDF rendering, large payload parsing) is pushed to threads, not run on the event loop..specify/memory/constitution.md Principle V

Pydantic models are for data that crosses a boundary (API bodies, frames, cached WCL values); frozen dataclasses are for internal value objects such as RequestIdentity and StartupStep. Pydantic itself is not listed in pyproject.toml; it comes in through FastAPI and pydantic-settings..specify/memory/constitution.md Principle IV

Two read paths added for the Raids and Profile pages

  • Raid summary (services/raid_summary.py). GET /api/raids/{code}/summary answers 404 for a code that is not [A-Za-z0-9]{1,32} or not a raid tracked in the caller's workspace, before any query. Otherwise it reads the stored report summary and the player-detail, boss-table and ranking rows the agent's own tools would have stored, only through the store's visibility rule (see the raw store), and returns the participants (at most 100), the duration and the parses of the caller's own characters (at most 50 each). Those are matched to stored players by name, realm and region, never from request input. When a summary is stored but none is visible, it sends at most one report-summary request through the normal WCL client to re-verify, with no database transaction open, in at most 5 s: once per workspace and raid per 10 min and two at once per workspace. Participants, tables and rankings are never fetched. Limit: 60 a minute per user.
  • Portraits (services/portraits.py). GET /api/profile/portraits lists the workspace's own and friend characters with a portrait URL or null. The URL comes from Blizzard's character-media endpoint, read with a client-credentials token kept in process memory; nothing is called when BLIZZARD_CLIENT_ID or BLIZZARD_CLIENT_SECRET is empty. The host is fixed per region (eu, us, kr, tw), the realm slug and name are allow-listed shapes, no redirect is followed, the body is capped at 64 KiB, and only an https URL on render.worldofwarcraft.com is kept, checked on storing and again on serving. Up to 6 lookups run at once, 3 s each, 4 s for the whole call; a slow one is shown as no portrait. Outcomes are cached in Redis: a found portrait for a day, none for 6 h, a failure for 5 min.

Health: GET /health and GET /api/health, one function in main.py. It returns status (booting, ok or error), db (a SELECT 1 with a 2 s timeout) and the startup snapshot.

Boot & readiness

TechFastAPI lifespanpure ASGI middlewaregc.freeze()

What it does, and where it lives

The lifespan in backend/app/main.py does only quick work before the port opens, then runs the slow boot as a background task. StartupTracker and ReadinessGate live in backend/app/startup.py.

  1. check_startup_secrets(settings): refuse a weak SECRET_KEY unless the site is local; warn naming insecure defaults (see Startup checks).
  2. Create a StartupTracker on app.state.startup.
  3. Start the KbIndexer when KB_INDEX_ENABLED (feature 043). It starts first because the fetch writer's commits offer it changed fetches.
  4. Start the FetchWriter when WCL_FETCH_PERSIST_ENABLED (feature 020), which installs itself as the WCL client's fetch sink. When WCL_STORE_READS_ENABLED, also install read_stored_fetch as the fetch source (feature 039: Redis → store → WCL). Both start before boot because the roster step already fetches from WCL.
  5. Start _boot as a task and yield: uvicorn opens the port.
  6. Boot step serializers: build the google-genai serializers eagerly, so ADK can serialise genai types during parallel tool calls.
  7. sessions: ADK's DatabaseSessionService on the app's engine, prepare_tables(), then registered for the agent runner.
  8. roster (optional): load the live class and spec roster from WCL game data; on failure the static roster is used.
  9. guides (optional): register the coaching-brief loader for agent tools and start a background scan for stale guides. Warn if the guide review model equals the author model.
  10. Log the LLM provider and any missing credential, then models: model discovery off the event loop, shared through the model_catalog cache family in catalog mode, into app.state (see Models & providers).
  11. greeting: create an empty greeting cache and start the greeting as a separate task (skipped when the provider has no credential). The step itself finishes at once.
  12. tracker.finish(): the gate opens. Then gc.collect() and gc.freeze().
  13. On shutdown: cancel an unfinished boot, uninstall the fetch source, drain the fetch writer (bounded), stop the indexer (bounded), close every WCL HTTP pool and the cache's Redis clients, dispose the engine.

A failed required step marks the boot failed. The process stays up, the gate keeps answering 503 with backend_failed and the error, and /api/health shows which step failed. An optional step that fails is marked skipped. The frontend polls the health endpoint and shows a boot overlay until ready (see Frontend).

Why

Boot runs in the background so the port opens at once and /api/health can show which step failed instead of a dead port.backend/app/main.py (_boot docstring and except clause) · backend/app/startup.py (module docstring)

After boot, gc.freeze() moves the startup heap out of the cyclic garbage collector's reach. Each collection triggered by parsing a large WCL payload used to walk it, measured at about 80 ms of event-loop stall; frozen, about 3 ms.backend/app/main.py (comment before gc.freeze, feature 013 SC-008)

The gate is pure ASGI and holds back all non-health traffic, so no handler can read half-initialised app.state.backend/app/startup.py (module docstring)

Open point: "the app waits for model discovery before serving anything" is still listed as an open medium QA finding (PERF-001, sc-156) in todo.md. The models step is required, so the gate stays shut until discovery finishes or a cached catalog is found.

Error handling

TechStarlette exception handlers

What it does, and where it lives

  • backend/app/api/errors.py installs one handler for HTTPException. When detail is a dict with a code (auth, admin, guides, rate limits), the response becomes {"error": {"code", "message", "request_id"}}, with request_id taken from an X-Request-ID header if the client sent one. A plain-string detail (most older endpoints, for example "not_found") keeps FastAPI's {"detail": ...} shape.
  • Public auth errors are generic: one invalid_credentials for every login failure, one invalid-token error for invitations and resets, so responses never reveal whether an account exists.
  • Rate limits answer 429 with code: "rate_limited"; login, investigate and the raid summary (60 a minute per user) also send Retry-After.
  • On the chat socket, a failed turn sends an error frame with code agent_error and a short log reference, never the exception text; a spent model retry budget sends rate_limited. The partial answer is saved where it can be. Details on Stream protocol.

Why

The envelope applies only to dict details so the endpoints that existed before feature 006 keep their response shape.backend/app/api/errors.py (module docstring)

InferredNo recorded reason for keeping two error shapes long term. The frontend's REST client reads both (frontend/src/api/restClient.ts), so nothing forces a change; unifying them would touch every older endpoint and its tests.

Background work & lanes

Techasyncio taskscontextvarsLaneLimiter

What it does, and where it lives

All background work runs in the backend process; there is no job queue or worker container. Two kinds exist: fire-and-forget tasks started from a request or turn, and long-lived consumers started by the lifespan.

  • spawn(coro, key) (backend/app/services/background.py) keeps a strong reference to each task so it isn't garbage-collected mid-run, and skips a key already running in this process. Each task runs in a fresh, empty contextvars.Context(), so it never inherits the caller's acting identity, refresh actor or lane (sc-222). Without a running loop it closes the coroutine and does nothing.
  • Lanes (wcl_agent/client/wcl_client.py): at most WCL_MAX_CONCURRENCY (6) WCL requests are in flight per process. Code inside background_lane() may hold at most WCL_BACKGROUND_CONCURRENCY (2) of them and never takes a slot while a chat lookup is waiting. A chat turn that joins a background request in flight promotes it to the interactive lane (048). Details on WCL client, cache & store.

Why

Background jobs are in-process tasks, with a database row as the lock where several instances could race. This needs no job queue (Principle III). The in-memory key set is a cheap first filter; the claim row is the real lock.specs/013-welcome-recent-raids/research.md R4, R5

Lanes: one limiter where background work only takes a slot when no chat lookup waits. Two separate semaphores would still let background work take interactive slots while chat is queued.specs/013-welcome-recent-raids/research.md R8

A fresh context per spawned task, because every context variable in the code defaults to the value that is right for a job (no identity, no refresh actor, lane set by the job). Copying the context and resetting only the identity would keep leaking the others.specs/036-profile-write-hardening/research.md R3

Planned, not built A separate worker container with a NATS queue for long-running jobs (guides, offline profile building) is listed in todo.md as "Worker server" (epic-196). Nothing of it is in the code.
