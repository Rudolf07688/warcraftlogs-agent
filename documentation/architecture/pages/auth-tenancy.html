Architecture · Runtime

Auth & multi-tenancy

Who may use the app and whose data they see. Accounts are invite-only, sessions are opaque server-side tokens in a cookie, and every tenant-owned row is guarded twice: by an explicit tenant_id in every query and by Postgres row-level security. A chat turn carries the same identity into the agent's tools for that turn only.

Accounts & admin

TechFastAPIsecrets.token_bytes (32 bytes)sha256 digests

What it does, and where it lives

  • The first admin is created only from the command line (backend/cli/bootstrap_admin.py, or backend/cli/init_db.py), with their own tenant and owner membership. No HTTP route can create an admin (see Command-line tools).
  • Invitations (backend/app/services/invitation_service.py, routes under /api/admin): a platform admin invites an email. That creates a user with status invited if none exists, revokes any open invitation for the email, and stores the sha256 of a new 32-byte token, valid 24 h. Resend rotates the token and expiry, so the old link stops working; revoke marks it revoked. An email that is disabled or already has a workspace gets a 409.
  • Accepting (POST /api/auth/accept-invitation) runs as one transaction: check the token, set the first password, activate the user, create their workspace (a tenant plus an owner membership), open a session and write the audit trail. Every failure is the same generic error.
  • Link delivery (backend/app/services/link_delivery.py): there is no email provider. The link is returned once in the admin's API response for them to share by hand. It is built from SITE_URL, never the request's Host, and the raw token sits in the URL fragment (/accept-invite#token=…, /reset-password#token=…).
  • Password reset (backend/app/services/password_reset_service.py): an admin triggers it (POST /api/admin/users/{id}/reset), which issues a single-use token valid 1 h. Completing it sets the new password, consumes the token and revokes all of the user's sessions. The admin never sees or sets the password. POST /api/auth/forgot-password exists but only returns a neutral 202 and sends nothing.
  • User admin: list users, disable or enable one. Disabling revokes the user's sessions at once and is refused for the last active platform admin. Membership endpoints are deliberately absent: one workspace per user in v1, although tenant_memberships exists.

Why

documentation/multi_tenancy_guide.md is the governing contract. Feature 006 adopts it and records only app-specific adaptations.specs/006-multi-tenancy/research.md (preamble)

Founder-mediated links behind one delivery seam: there is no email provider at launch, and an email implementation (with self-service reset) can drop in behind the same functions later. The token goes in the fragment because a query string leaks into logs and the Referer header.specs/006-multi-tenancy/research.md R9 · backend/app/services/link_delivery.py (docstring)

The founder is operator-only and must exist before migration 0003 backfills existing rows to their tenant.specs/006-multi-tenancy/research.md R8 · backend/cli/bootstrap_admin.py (docstring)

tenants and tenant_memberships are kept although v1 is one user per tenant. This matches the guide's RLS contract and avoids a second painful migration later.specs/006-multi-tenancy/plan.md (Constitution Check, Principle III) · backend/app/api/admin_users.py (comment on deferred membership endpoints)

Passwords

Techpwdlib[argon2]>=0.2.1anyio.to_thread

What it does, and where it lives

  • backend/app/auth/passwords.py: Argon2id through PasswordHash.recommended(). Hashing and verifying run in a worker thread under a semaphore of PASSWORD_HASH_MAX_CONCURRENCY (4).
  • Policy: 15 to 256 characters, not in a short built-in list of obvious passwords, not one repeated character.
  • Login with an unknown email verifies against a dummy hash computed at import, so the timing matches a real account. A stored hash with outdated parameters is re-hashed on the next successful login.

Why

pwdlib's recommended Argon2id hasher is what the guide prescribes. Running it off the event loop under a semaphore keeps the backend non-blocking and bounds CPU and memory during a login flood. Alternatives: passlib (less aligned with current FastAPI guidance); hashing on the event loop; a new dummy hash per request.specs/006-multi-tenancy/research.md R2 · documentation/multi_tenancy_guide.md (Password hashing)

Sessions & CSRF

Tech__Host- cookieHMAC-SHA256sqlalchemy[asyncio]>=2.0.0

What it does, and where it lives

  • Sessions (backend/app/auth/sessions.py, tokens.py, repositories/sessions.py): a random 32-byte token in the cookie SESSION_COOKIE_NAME (default __Host-session; HttpOnly, Secure, SameSite=Lax, Path=/, no Domain). Only its sha256 digest is stored, in auth_sessions, with the active tenant and a hash of the user agent. A session expires after 7 days idle or 30 days absolute; an expired one is revoked when it is next seen. last_seen_at is written at most every 5 minutes.
  • Identity (backend/app/auth/dependencies.py): authenticate_session resolves the cookie in its own short transaction: live session, active user, and, when the session has an active tenant, an active membership and an active tenant. The result is a frozen RequestIdentity (user_id, tenant_id, membership_role, is_platform_admin, session_id), built only from the session, never from client input. Login picks the user's first membership as the active tenant.
  • Dependencies: require_session (401 without a live session), require_platform_admin (403 unless admin), require_csrf (identity plus the CSRF check on unsafe methods), get_tenant_db (a tenant-scoped transaction; see below).
  • CSRF (backend/app/auth/csrf.py): every unsafe request (anything but GET, HEAD, OPTIONS, TRACE) through require_csrf needs both an X-CSRF-Token header equal to HMAC-SHA256(SECRET_KEY, session id), compared in constant time, and an Origin (or, failing that, Referer) matching SITE_URL. A request with neither header is refused. The token comes back in the login, accept and /me responses. Logout checks CSRF only when a live session is present, so a stale cookie still gets a clean 204.
  • WebSocket (backend/app/api/ws.py): before accept() the handshake must pass the Origin check and carry a valid session with a tenant, else it is closed with 1008. The session is checked again before every turn, so a disabled user or revoked session is cut off mid-connection. No token is ever read from the query string or a frame.
  1. The browser sends the request with the session cookie and X-CSRF-Token to its own origin; Vite or nginx forwards it to the backend.
  2. require_session hashes the cookie and loads the live session, user, membership and tenant (one short transaction that also refreshes last_seen_at when due).
  3. require_csrf checks Origin/Referer against SITE_URL and the HMAC token.
  4. get_tenant_db opens a transaction and sets app.tenant_id and app.user_id transaction-locally.
  5. The handler's queries carry tenant_id; RLS enforces the same value.
  6. Commit ends the transaction and its settings; the response returns.

Why

Opaque server-side sessions in a __Host- cookie, with a header CSRF token. Same-origin deployment through the Vite or nginx proxy makes this the simplest correct design, with no credentialed CORS. Alternatives: JWT (the guide forbids it, and JWTs can't be revoked server-side); double-submit CSRF cookie (weaker); tokens in localStorage (readable by XSS).specs/006-multi-tenancy/research.md R3

The WebSocket reuses the cookie at the handshake, with the Origin check as its CSRF analogue, and re-validates each turn so disabling takes effect mid-session. Alternatives: a query-string token (leaks into logs); a separate auth message (reinvents the cookie).specs/006-multi-tenancy/research.md R6

Drift from research: R3 planned a stored sha256 of a random CSRF token. The code derives it statelessly with HMAC instead, so a reload or another tab recovers the same token; the reason is in the backend/app/auth/csrf.py docstring. .env.example explains when to drop the __Host- prefix and Secure for plain-HTTP development (Safari drops the cookie otherwise).

Rate limits

Techin-process limiteripaddress (stdlib)

What it does, and where it lives

backend/app/auth/rate_limit.py has one InProcessRateLimiter class behind a RateLimiter protocol, and five process-wide instances.

InstanceKeyRuleUsed by
login_limiternormalised email + client sourceProgressive delay from the 5th consecutive failure, doubling, capped at 30 s; never a lockout. Success clears it. 429 with Retry-After.services/auth_service.py
token_limiteraccept:, reset:, forgot: or admin-invite: + client sourceFixed window, 20 per minute (RATE_LIMIT_TOKEN_PER_MINUTE)api/auth.py, api/admin_users.py (create invitation)
guide_limiteruser id10 per minuteGenerate a guide
guide_report_limiteruser id5 per minuteReport a guide inaccuracy
investigate_limiteruser id5 per minute, checked before the endpoint takes a DB connection (sc-352)POST /api/raids/{code}/investigate

Client source (client_source): the direct peer address, unless that peer is in TRUSTED_PROXIES (IPs or CIDRs, parsed once per value). Then it walks X-Forwarded-For from the right and takes the nearest hop that isn't a trusted proxy. Ports are stripped and IPv4-mapped IPv6 counts as IPv4. A hop that isn't an address falls back to the peer (logged once). With no trusted proxies, forwarded headers are ignored, so behind a proxy every client shares the proxy's bucket.

Why

The limiter is in-process at single-process scale, behind an interface so a shared backend can replace it. Alternative: Redis at the time (speculative infrastructure, YAGNI).specs/006-multi-tenancy/research.md R7 · backend/app/auth/rate_limit.py (module docstring)

The nearest untrusted hop is the address our own proxy saw; the leftmost entries are whatever the client wrote, so keying on them would let a client pick its own bucket (sc-158).backend/app/auth/rate_limit.py (client_source docstring) · .env.example (TRUSTED_PROXIES)

Drift from research: R7 says login throttling is backed per account by users.failed_login_count and login_blocked_until. In the code the throttle is in memory only, keyed by account and source together. failed_login_count is incremented and reset but never read for a decision, and login_blocked_until is only ever cleared. The guide also recommends shared limits once there are several workers; Redis exists since feature 014, but every limiter is still per process.

Audit & redaction

Techlogging.Filterappend-only table

What it does, and where it lives

  • backend/app/repositories/audit.py appends to auth_audit_events: event type, outcome, actor, target, tenant, optional request id and metadata. Events written today include login (success and failure), logout, invitation.created/resent/revoked, password_reset.requested, user.disabled and user.enabled. Metadata goes through the redaction helper first.
  • backend/app/auth/redaction.py: values of keys matching password|token|authorization|cookie|set-cookie|csrf (any case, substring) become «redacted», recursively to depth 6. RedactionFilter applies it to log records' dict args and extras; main.py installs it on the root logger, its handlers and uvicorn's loggers.

The table itself is on Database & migrations.

Why

Secrets never reach logs, APM or the audit table: raw tokens leave the server once and are otherwise only stored as digests; the filter is defence in depth for structured log data.backend/app/auth/tokens.py (docstring) · backend/app/main.py (_install_log_redaction docstring) · specs/006-multi-tenancy/research.md (Cross-cutting: audit, redaction, config, tests)

Tenant scoping & row-level security

TechPostgreSQL row-level securityset_config(…, true)sqlalchemy[asyncio]>=2.0.0

What it does, and where it lives

  • Two roles. The app connects as the runtime role (APP_DB_USER, created by migration 0004_rls as NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS, with DML on all tables and default privileges for later ones). Alembic runs as the owner. See Configuration.
  • Scope per transaction (backend/app/tenancy/context.py): set_scope runs one statement, SELECT set_config('app.tenant_id', …, true), set_config('app.user_id', …, true) (one round trip since sc-270). The true makes both settings transaction-local, so they vanish at commit and never leak to the next user of a pooled connection. Entry points: get_tenant_db / tenant_session(identity) for requests, tenant_scope(tenant_id, user_id=…) for sockets, tools and jobs, and commit_and_rescope after a mid-handler commit (otherwise the next query would see no tenant and RLS would return nothing). On SQLite (tests) the call is skipped and the app-level filters are what the tests check.
  • App-level filter. Every tenant-owned repository function takes a keyword-only tenant_id, and lookups combine id and tenant in one predicate, so a foreign row is a 404.
  • RLS. 17 tenant-owned tables have row-level security enabled and forced (migrations 0004, 0005, 0010, 0014, 0016, 0018, 0019). 16 use the policy tenant_isolation: tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid for both USING and WITH CHECK. profile_proposals uses tenant_user_isolation, which also requires user_id to match app.user_id (migration 0017, sc-222). Global tables (guides, the raw WCL store, kb_chunks) have no RLS by design; the table list is on Database & migrations.
  • Global-data routes such as /api/guides use the non-tenant get_session but still require a session, CSRF on writes and per-user caps.
  • Outside Postgres tables: ADK's session tables are isolated by ADK user_id = tenant id, not by RLS. The Redis WCL cache is shared by all tenants and its keys never hold a user or tenant id; a load answered from a report visible only through one tenant's grant is marked unshareable and kept out of the shared cache (045). The per-turn scratch store is per conversation.

Why

RLS plus a separate non-owner runtime role is defence in depth for the feature's worst risk, cross-tenant leaks. The tenant id is set transaction-locally, because a session-level SET leaks across pooled connections. Alternatives: app-level scoping only (a single point of failure); one superuser role (bypasses RLS).specs/006-multi-tenancy/research.md R4

An explicit tenant_id argument on every repository function, with one combined id-and-tenant lookup that returns 404 for a foreign row. Alternative: a global SQLAlchemy event that injects filters, rejected as too implicit and easy to bypass.specs/006-multi-tenancy/research.md R5

The database itself enforces "same user" on proposals, so a future background job or query can't read or act on another user's proposal in the same tenant.specs/036-profile-write-hardening/spec.md (User Story 2, sc-222)

Guides are a global library without RLS, because they are generic class advice, not user data.specs/008-profile-class-pages/research.md Decision 1 · backend/app/api/guides.py (docstring)

Drift from research: 006 R5(d) put a tenant prefix on WCL cache keys. Feature 014 removed it when the cache moved to shared Redis (014 research R10); private data is now kept per tenant by the raw store's grants and the unshareable flag instead (see WCL client, cache & store).

Turn-scoped agent identity

Techcontextvars.ContextVarADK ToolContext

What it does, and where it lives

  • current_identity (backend/app/tenancy/context.py) is a ContextVar[RequestIdentity | None], default None. The chat socket sets it just before streaming a turn and resets it in the turn's finally (backend/app/api/ws.py). ADK's producer task copies the context, so tools see it inside the turn and nowhere else.
  • Backend agent tools act as that user and fail closed without it: propose_profile_changes (agent_tools/profile_tools.py), search_knowledge (agent_tools/kb_tools.py) and the stored-data lookups (agent_tools/stored_data_tools.py) all return a plain "unavailable" error unless the identity exists and its tenant_id equals the ADK tool_context.user_id. They then open their own tenant_scope (with user_id where proposals are involved).
  • The WCL data path reads the same variable: the fetch writer records which tenant fetched a response (for that tenant's grant on private reports), and DB-first reads answer only what that tenant may see. Without an identity (greeting, guide jobs) only public data qualifies.
  • Every task started with background.spawn gets a fresh, empty context, so it never inherits a turn's identity. The one job that acts for a user, the kickoff pre-fetch, sets the clicking user's identity inside its own task.
  • Alongside, the turn sets the cache's refresh actor to the user id at turn start and clears it at the end (set_refresh_actor), which also closes the turn for the local-answer metrics (sc-276, 045).

Why

Tools need to know who they act for, but the identity must exist only during the chat turn, so a later task on the same socket or a spawned job can't act as the wrong user.specs/036-profile-write-hardening/spec.md (User Story 2, sc-222) · backend/app/tenancy/context.py (comment on current_identity)

A fresh context per spawned task rather than copying and resetting only the identity, which would keep leaking the other context variables.specs/036-profile-write-hardening/research.md R3

InferredNo recorded reason for the extra tenant_id == tool_context.user_id check. It ties the identity to the ADK session the tool runs in, so a tool can't act if the two ever disagree (for example a tool called from a disposable greeting or guide session).
