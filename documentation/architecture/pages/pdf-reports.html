Architecture · User-facing

PDF reports

A player can download a whole chat, or a single answer, as a PDF. The backend does not print the transcript: a model first rewrites the chat into a findings document, which is then turned into sanitised HTML and laid out by WeasyPrint in the chat's own dark look, with the turn's charts drawn as vector graphics.

What it does, and where it lives

  • _synthesize_and_render in reports.py is shared by both routes. It runs the findings rewrite (backend/app/services/report_synthesis.py) and the chart drawing (backend/app/services/charts.py) at the same time, then builds a typed ReportDocument and hands it to render_report_pdf (backend/app/services/pdf_report.py).
  • One render thread. Chart drawing and layout are CPU-bound and hold the GIL, so parallel renders only slow each other down. A dedicated single-thread pool (pdf-render) runs them in turn; each chart is its own job, so a waiting render gets in after at most one chart. The chat path never waits behind a report in the default executor.
  • The renderer does no database access and no network fetches: the endpoint gathers plain data (GraphSource, ChartSource dataclasses) before anything reaches the thread.
  1. The browser requests the report URL with its session cookie.
  2. require_session and get_tenant_db resolve the identity and set the tenant for row-level security.
  3. The endpoint loads the messages, captured_graphs and artifacts, and for the whole-chat report the tracked raid that points at this chat (for the title).
  4. Rows come back. A foreign or unknown chat, or a message that is not an agent answer of this chat, is a 404.
  5. The figure list is capped at 20 (captured graphs first, then the agent's charts), then synthesize_findings starts.
  6. It calls the report-role model through the provider-neutral generate_text, with a 60 s cap.
  7. At the same time each chart is drawn on the render thread as its own job; a chart that fails or runs out of the shared 60 s budget becomes "Chart unavailable" instead of failing the report.
  8. The findings Markdown comes back from the model.
  9. It is returned to the endpoint. An error, a timeout or empty output fails the report.
  10. The SVG figures come back.
  11. The endpoint builds a ReportDocument (title, scope, time, findings, question, partial flag, figures, count of omitted figures) and sends it to the render thread, with a 90 s cap.
  12. Findings Markdown → HTML with maths as SVG → nh3 → report components → WeasyPrint with the report stylesheet and bundled fonts.
  13. The PDF bytes come back; one log line records scope, pages, figures and milliseconds.
  14. The endpoint returns application/pdf as an attachment, or 500 pdf_generation_failed.

Findings rewrite

What it does, and where it lives

  • What it asks for. synthesize_findings in report_synthesis.py sends one prompt: "what was discovered, not a transcript", organised by topic or encounter, with sections At a Glance (3 to 6 - **Label:** value (context) bullets), Summary, Key Findings, Results by Encounter / Player and Recommendations (a numbered list of bold action titles). It also asks for tables for 3+ items, one > [!TIP] callout, > [!WARNING] only for data caveats, and timelines as bullets starting with a backticked mm:ss. A chat with no analysis gets a short "No substantive findings" document.
  • Which model. The report role of the active provider (ModelRole.REPORT, override WCL_REPORT_MODEL), called through wcl_agent/llm/generation.py; see Models & providers. No web search.
  • Bounds. Input capped at 24,000 characters, dropping the oldest content first; output capped at 16,384 tokens (thinking included on thinking models); one attempt, so a rate limit fails the report cleanly; 60 s timeout.
  • Charts are not rewritten. They are attached unchanged after the findings.

Markdown to safe HTML

What it does, and where it lives

findings_to_html in pdf_report.py. Model output is untrusted, so every step assumes it could contain HTML, images or links planted by a log or a web page.

  1. Cap. The body is cut at 60,000 characters (with a "Report shortened" note) and each table at 200 rows (with a "… N more rows not shown" row).
  2. Parse. markdown-it-py, CommonMark plus GFM tables and strikethrough, the tasklists plugin and dollarmath configured so "$5 and $10" is never maths. Raw HTML is parsed (html=True) so it can be sanitised rather than shown as text.
  3. Maths. Each equation is typeset with matplotlib mathtext as an SVG and parked in a private-use placeholder; it is put back only after sanitising, so the only images WeasyPrint sees are the renderer's own. Equations over 300 characters, or past the 60th, and any mathtext cannot parse, fall back to readable italic text.
  4. Sanitise. nh3 with an allow-list: headings, paragraphs, emphasis, code, lists, quotes, tables, a, img, span, div, sup/sub. script, style, iframe, object, embed, svg and math are dropped with their content. Links may be http, https or mailto. Attributes: href, src/alt, ol start, table-cell style only for text alignment, and class only for markdown-it's task-list classes.
  5. Images become text. Every <img> left in the model's HTML is replaced by its alt text or URL, whatever its scheme (remote, data: SVG or raster).
  6. Components and wrapping. The report components below are applied, then long tokens (report codes, URLs) get soft break points so tables shrink to the page.
  7. Fetching. WeasyPrint runs with no base URL and a fetcher (_ReportFetcher) that allows data: URLs and file: URLs only when they resolve inside backend/app/assets/fonts, after path traversal is resolved. Nothing else, local or remote, can be loaded.

Drift: specs/017-proper-pdf-generation/research.md R6 says the fetcher allows data: only. The file: exception for the bundled fonts came with the chat-style redesign (sc-169). The module docstring of pdf_report.py still says data: only and that the caller uses asyncio.to_thread; it now runs on the pdf-render pool.

The look

What it does, and where it lives

  • The chat's dark theme. The page background, cards, tables and text use the chat's "Tavern Hearth" colours, converted once from the frontend's oklch() tokens to hex in backend/app/services/report_theme.py (so the renderer doesn't depend on CSS Color 4). They have to be kept in step with frontend/src/index.css by hand.
  • Fonts. Cinzel (headings and title) and Alegreya Sans (body: regular, italic, medium, bold) ship with the app in backend/app/assets/fonts with their OFL licences, so host and container render alike. Fallbacks: DejaVu Sans and Noto Sans CJK SC for body text, DejaVu Serif for headings, DejaVu Sans Mono for code. Emoji come from fontconfig fallback to Noto Color Emoji: naming an emoji font in the stack makes Pango 1.56 draw digits, # and * as keycaps.
  • Container. backend/Dockerfile installs Pango and HarfBuzz for WeasyPrint, freetype and libpng for matplotlib, and fonts-dejavu-core, fonts-noto-cjk and fonts-noto-color-emoji.
  • Page. A4, 20/18/18 mm margins; the report title runs in the header from page 2; "Page X of Y" bottom right; headings stay with what follows; table header rows repeat; rows, figures, KPI cards and timeline rows never split. The title block shows the title, "Whole conversation" or "Single answer", the UTC generation time, the question (single answer) and an "Interrupted — partial answer" note when it applies.

Charts in the PDF

What it does, and where it lives

  • Two sources. Captured WCL graphs (captured_graphs, stored when get_report_graph succeeded in a turn) are drawn by graph_to_svg; the agent's charts (artifacts.spec_json, from create_chart) by chart_spec_to_svg. The same ChartSpec also feeds chart_spec_to_plotly for the browser, so one spec has two renderers.
  • Drawing. matplotlib's object-oriented Figure API (never pyplot, so threads share no global state), saved as transparent SVG and embedded as a data: URI. Each series differs by colour, line style and marker (or hatch for bars), so series stay apart without colour. Large y values get thousands separators. At most 12 series and 500 points per series.
  • Layout. A "Charts" section starts on a new page after the findings; each figure is captioned "Figure N — title" with a "source" link when it has an http(s) source URL (a WCL report link for captured graphs). Figures past 20 are counted in "N more charts not shown".
  • No re-fetch. The PDF draws from the stored graph JSON; it never calls Warcraft Logs at export time.

Drift: the plotly Python package is declared in pyproject.toml, and specs/005-guild-context-artifacts/plan.md (Complexity Tracking) justifies it for building the figure JSON, but no module imports it: chart_spec_to_plotly builds the dict by hand, and the browser draws it with plotly.js-dist-min.

equations300 characters each, 60 per reportpdf_report.py
chart series / points12 / 500charts.py
  • Fail closed. A rewrite error, timeout or empty output, a failure of the chart step as a whole, or a render failure returns 500 pdf_generation_failed. A partial file is never sent.
  • One bad chart is not fatal. A spec that doesn't validate, a drawing error or the chart budget running out gives that figure "Chart unavailable".
  • Work that overruns its wait can't be killed and keeps the render thread until it ends; the input caps bound how long that can be.

Why

WeasyPrint supports CSS Paged Media (running headers, "page X of Y", headings kept with their content, repeating table headers) with no layout code of ours, adds no browser process and rendered in 0.21 s in the spike. Alternatives: headless Chromium via Playwright (about 300 MB, a subprocess per request, weaker paged media); patching the ReportLab parser (failed three times); xhtml2pdf (weak CSS).specs/017-proper-pdf-generation/research.md R1; plan.md (Complexity Tracking)

markdown-it-py follows CommonMark and GFM tables, and dollarmath leaves "$5 and $10" alone. Alternatives: Python-Markdown (unused and poor at nested lists and maths, so removed); mistune.specs/017-proper-pdf-generation/research.md R2

nh3 with an allow-list keeps basic tags and drops the rest with their content; model images never reach the renderer. Alternatives: html=False (tags would print as text); bleach (deprecated upstream).specs/017-proper-pdf-generation/research.md R3

Locking the fetcher matters for file: as much as for the network: without it, an <img src="file:///etc/passwd"> in model output could pull server files into a PDF.specs/017-proper-pdf-generation/research.md R6

Equations and charts as matplotlib SVG: WeasyPrint runs no JavaScript (no KaTeX) and renders no MathML, and matplotlib was already a dependency. Alternatives: latex2mathml; a TeX toolchain; KaTeX through Node; Plotly static export via kaleido (bundles Chromium).specs/017-proper-pdf-generation/research.md R4, R5

The PDF looks like the chat, dark page included: the owner's choice on 2026-10-20.backend/app/services/report_theme.py (module docstring)

The chat fonts are bundled so host and container render alike; emoji come from fontconfig fallback because naming an emoji font made Pango draw digits as keycaps.backend/app/services/pdf_report.py (comment above _FONT_DIR)

CJK and emoji fonts are system packages so no glyph renders as a box, at about 120 MB of image size; fonts-noto-cjk is the one line to drop if size matters more.specs/017-proper-pdf-generation/research.md R7, R8

One render thread: chart drawing and layout hold the GIL, so parallel renders only slow each other down (four renders: 1.8 s one at a time, 2.7 s two at a time), and queued reports must not take threads the chat path needs.backend/app/api/reports.py (comment above _RENDER_POOL)

A findings document instead of a transcript: the owner asked for reports on what was discovered, not what was said, for both the chat and the single answer.todo.md (Phase 5, "Improve PDF report downloads")

The PDF draws captured graph JSON instead of re-calling Warcraft Logs at export time, which would spend rate budget and might miss the exact filters used.backend/app/services/graphs.py (module docstring); specs/002-agent-enhancements/research.md §6
