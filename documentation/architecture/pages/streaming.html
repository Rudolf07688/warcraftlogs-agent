Architecture · User-facing

Stream protocol

One WebSocket carries every chat turn: the browser sends the question, the backend streams back the answer as typed JSON frames, with tool cards, charts, follow-ups and errors along the way. A handful of REST endpoints load and manage the conversations around it.

The socket

Techfastapi>=0.115.0uvicorn[standard]>=0.30.0pydantic (via fastapi)browser WebSocket API

What it does, and where it lives

  • Endpoint. /ws/chat, the chat() handler in backend/app/api/ws.py. The browser opens it once (ChatSocket in frontend/src/api/wsClient.ts) and keeps it for the whole session, across chats.
  • Handshake. Before accept() the handler checks the Origin header against SITE_URL (origin_matches in backend/app/auth/csrf.py) and validates the __Host-session cookie (authenticate_session). Either failing closes the socket with code 1008. No token is ever read from the query string or a frame.
  • Every turn re-checks the session. A revoked session, disabled user or missing tenant gets an error frame (unauthorized) and a 1008 close, even mid-connection.
  • One turn at a time per socket, and per chat. The receive loop awaits each turn to the end, so turns on one socket never race. Each turn runs as its own task (_start_turn) so that a newer turn on the same chat, from another socket, can cancel it without closing this socket (see Errors and interruption). When telemetry is on, each turn runs inside chat_turn_span(), a span of its own trace (the root, or the child of the browser's "chat send" span when the message carries a valid traceparent), so the agent, model, tool, SQL and Redis spans of one turn belong together while the connection itself is not traced (see Observability). All sends go through _TurnSocket.send_json, which holds a per-socket lock, because the follow-up and title tasks send after the turn has ended.
  • Model resolution. The requested model is mapped to the active provider's form; a model that is no longer served continues on the default (resolve_chat_model in backend/app/model_state.py, feature 032). The turn also gets its same-class sibling for a rate-limit fallback (fallback_model_for). See Models & providers.
  • Per-turn context. For the turn's duration the backend sets the WCL refresh actor (the per-user forced-refresh limit) and the agent identity used by backend tools; both are cleared when the stream ends, so later tasks on the socket never act as that user (sc-276, sc-222).

A turn, in order

What it does, and where it lives

_handle_turn in ws.py drives the turn; stream_response in backend/app/agent_runner.py runs the ADK agent in a producer task and yields records (tool_start, tool_end, token, grounding, plus model_retry and model_fallback pushed in by the model wrapper). ws.py turns each record into frames. The setup, each capture and the final save each use their own short tenant-scoped transaction, so no database connection is held while the model streams.

  1. The browser sends a ChatTurn. With Faro on, ChatSocket first opens a "chat send" span and adds its traceparent and the Faro session id to the message; the span ends on the done or error frame, or when the socket closes. ws.py re-checks the session, validates the body (an invalid or empty one gets empty_message) and resolves the model.
  2. For an existing chat, one short transaction checks that the chat belongs to the workspace (a foreign or unknown id gets not_found). The turn then claims the chat (_ChatTurn.claim), which supersedes a turn still running on it, with no database connection held. In a second short transaction it reads the chat again, or creates a new one, saves the user message and commits.
  3. It sends meta with the conversation id and the user message's seq.
  4. It builds the turn preamble from stored rows: the profile, tracked raids, recently seen players, encounters and guilds, recent raids and Mythic+ runs, and the published coaching briefs for the profile's specs. The preamble rides on the turn and is never saved.
  5. It calls stream_response() with a per-turn scratch folder for large tool results.
  6. Each tool round: the model returns function calls; tool_start goes out once per call; the tools run; tool_end goes out per result; then the captures are stored and their frames sent (next sections).
  7. In the last round the model streams text, sent as token frames. Text after a tool round starts a new paragraph. If the model gives no answer text after its last tool result, the runner ends the turn with a fixed "I couldn't put an answer together this time…" message instead (sc-302).
  8. The answer is saved; this turn's charts, graphs and confirmation cards are linked to it by seq.
  9. The saved exchange is offered to the knowledge-base indexer (enqueue only; see Knowledge base), then done goes out and the composer unlocks.
  10. In the background: conversation_title for the first answer of an auto-named chat, and suggestions. A no-answer turn gets neither and is not indexed.

Tool cards

What it does, and where it lives

  • One tool_start per call. _run_turn skips function-call parts on partial events and announces each call from the model's final event, which always carries the complete args and call id; a call id seen before is skipped (sc-289). Before this, Anthropic models (one partial event per argument chunk) could start several cards for one call.
  • User-safe payload. tool_start forwards only the tool name and a string report_code if the args have one. tool_end adds ok (the result's status == "success"), a one-line summary from backend/app/services/tool_summary.py (cut to 140 characters) and the elapsed ms.
  • Correlation. The frames carry no call id. The browser resolves the oldest still-casting card with the same name, so parallel calls of the same tool resolve in FIFO order.
  • Full results stay on the server. Each result is also written to the turn's scratch folder (backend/app/scratch.py), removed when the stream ends.
  • How the cards look (labels, "spells") is on the Frontend page.

  • Charts and cards wait for done. The browser holds artifact and proposal frames and attaches them to the answer when it is committed, so no chart renders mid-stream. A proposal whose turn failed still shows as a standalone card in the chat that made it.
  • Every way a turn ends links its captures. On a normal end they go to the answer's seq. On an interruption they go to the partial answer, or to the user message when nothing streamed; on a rate-limit failure, to the user message. A capture left unlinked would otherwise show up under a later answer (sc-213).
  • Reload. GET /api/conversations/{id} returns the chat's charts (Plotly figures rebuilt from the stored spec) and proposals, which the client attaches to messages by message_seq. Tool cards, the web-search note, the fallback note, the boss picker and follow-ups are not stored; they exist only for the session that saw the turn.

After done

What it does, and where it lives

  • Follow-up suggestions (backend/app/suggestions.py): one non-streaming call to the fast-role model, thinking off, one attempt, at most 256 output tokens and a 4 s cap. The output is parsed to at most three clean questions. It runs as a task that the socket's next turn cancels; any failure means no suggestions frame.
  • Generated titles (backend/app/services/conversation_titles.py, feature 019): only for a chat whose title_source is auto. The chat is claimed first (auto → generated), so a failed attempt is never retried; the fast-role model gets 15 s. The next turn does not cancel it. The frame is best-effort: the title is already saved, so the next list load shows it anyway.
  • Knowledge base (feature 043): the saved question and answer are queued as a chat chunk for the workspace (kb_indexer.offer_exchange). Only the streamed answer goes in, never tool results.

  • No internal details reach the player. Provider, database and WCL errors can carry project ids or SQL, so agent_error always has the fixed text plus an 8-character reference that is also on the logged exception (QA SEC-001).
  • Interruption. There is no stop button and no client-to-server cancel frame. A turn is interrupted when the socket goes away (tab closed, reload, network loss). The server notices on its next send: the reply streamed so far is saved with status="partial" and the runner's producer task is cancelled. The chat shows "Interrupted — partial response" under such a message on reload.
  • Superseding. Only one turn runs per chat at a time, across all sockets, so a player who asks again after a drop does not get two answers racing into one chat. _ChatTurn in ws.py keeps a registry keyed by (workspace, chat) taken from the row the ownership check returned, never from the id in the frame. A newer turn cancels the old one while it is in setup or streaming, then waits up to 5 s for it to end. The old turn saves its partial answer first, so messages stay in turn order, then best-effort sends superseded (1 s cap) and stops. A turn already saving its final answer is not cancelled; the newer one waits. Past the 5 s wait the newer turn goes on and the old one, no longer holding the chat, saves nothing: both save paths check, under the chat's row lock, that the turn still holds the chat and roll back if not.
  • Failed setup. If the turn's setup (preamble, commit or scratch folder) fails or is cancelled, the WCL cache's open turn is closed without being counted and its user is cleared (abandon_turn, sc-357).
  • Turn metrics. Every turn, whatever the outcome, logs one turn stats line (requests, rounds, retries, tokens, tool calls, fallback); see Agent runtime & tools.

Reconnection

What it does, and where it lives

  • ChatSocket reconnects 1.5 s after any close, with no backoff and no attempt limit, and reports the connection to the header's "connected / disconnected" badge. The composer is disabled while disconnected.
  • A 1008 close (rejected handshake or revoked session) stops reconnecting and sends the browser to /login.
  • A send while the socket is not open fails at once: the turn is not started and the chat shows "Not connected to the server. Retrying…".
  • Nothing is replayed after a reconnect: an interrupted turn is not resumed. A drop mid-turn ends that turn in the browser at once (handleStatus in App.tsx): the text received so far stays as a message, the chat shows "Connection lost, the answer may be incomplete." and the composer unlocks. When the socket is back, the open chat is reloaded from the backend, which shows the saved partial answer after a network blip (a backend restart saved nothing, so the local partial text stays). Late token, tool_start, tool_end and done frames that arrive while no turn is streaming are ignored. Details on Frontend.

Why

WebSocket rather than SSE or polling: the owner asked for WebSockets; it is bidirectional, fits incremental token delivery, and one long-lived connection avoids per-chunk HTTP overhead, with room for client-to-server control frames later. Alternatives: Server-Sent Events (simpler, one-way); HTTP polling (no real streaming).specs/001-streaming-chat-frontend/research.md §1

The socket was kept when the UI moved to the "spellcasting" design: the existing frames map one to one onto that design's events, so an SSE-over-POST rewrite would be pure rework. Only tool_end.summary/ms and the optional tool_progress frame were added.specs/004-raid-sourcing-ux/research.md R6

The handshake checks the session cookie and Origin before accept(): one session model for HTTP and WS, the Origin check is the WebSocket analogue of CSRF, and the per-turn re-check makes a revoked session take effect mid-connection. Alternatives: a query-string token (leaks into logs); a separate auth message (reinvents the cookie).specs/006-multi-tenancy/research.md R6

Follow-ups come from a separate, non-streaming call after the answer: the streamed answer stays clean, the shape (at most three) can be enforced, and first-token latency is unaffected. Alternatives: an in-band trailing block; structured output on the main turn.specs/003-chat-followups-ux/research.md R1

done goes before suggestions, the suggestions run as a cancellable background task and all sends share a per-socket lock, so the composer is never held up.documentation/ai_guide.md §17

Generated titles reach the browser as a typed frame on which it refetches the list, so the list stays the one source of truth. Alternatives: polling after done; patching state from the frame.specs/019-sidebar-conversations/research.md R8

A failed turn shows a fixed message with a log reference, because provider, database and WCL errors can carry internal details such as project ids or SQL.backend/app/api/ws.py (AGENT_ERROR_MESSAGE comment, QA SEC-001)

A newer turn supersedes the old one instead of being refused, because a dropped socket is noticed only when a send fails: the player is already asking again while the old turn still runs a tool round. The old turn saves its partial first so the chat stays in turn order. Alternative: reject the new turn until the old one ends (the player would wait on a turn nobody is reading).backend/app/api/ws.py (_ChatTurn docstring, sc-511)

A tool card starts from the model's final event only, because partial events carry fragments of a call (Anthropic: one per argument chunk; Gemini: a copy the final event repeats), while the final event always has every call with its complete args and id.backend/app/agent_runner.py (_run_turn, sc-289 comment)

Frames crossing the boundary are meant to be explicit typed models..specify/memory/constitution.md Principle IV

InferredCharts and proposal cards wait for done rather than rendering mid-stream, which keeps the message layout stable while text streams and gives each answer one place where everything that belongs to it is attached.
