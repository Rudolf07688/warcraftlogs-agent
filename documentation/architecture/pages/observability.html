Architecture · Runtime

Observability

Traces, logs and metrics from two sources: the backend API (the runtime layer) and the Claude Code sessions that build the app (the build layer). Both send OpenTelemetry to one always-on collector, Grafana Alloy, which redacts secrets, sorts prompt and answer content into its own short-lived stream and queues everything on disk until the storage backends (Loki, Tempo, Mimir) and Grafana are running. This page follows the data from each source to Grafana. The compose wiring is on Deployment & config.

The pipeline

TechOpenTelemetry (OTLP http/protobuf)grafana/alloy:v1.21.3loki:3.7.9tempo:2.10.10mimir:3.2.4grafana:13.2.5

What it does, and where it lives

  • Two layers, one stamp. Every signal carries app.layer: runtime for the backend (service.name=api) and build for Claude Code (service.name=claude-code). Both also carry service.namespace=wcl-agent and deployment.environment.name.
  • Alloy is always on. docker compose up starts it with the app; it holds its queues on the alloy-data volume. Loki, Tempo, Mimir and Grafana only start with docker compose --profile observability up -d. Until then nothing is lost: Alloy retries from its disk queue.
  • Where the code is. backend/app/telemetry/ (runtime layer), bin/claude-otel (build layer), observability/ (Alloy, Loki, Tempo, Mimir and Grafana config, its README and its test scripts), the alloy and profile services in docker-compose.yml.

Why

One always-on collector with disk queues, and storage backends that can be off: the owner asked for persistence before dashboards, and the transcripts and the team board remain the backfill sources.specs/telemetry_spec.md §14.1 (decisions 8 and 11)

The runtime layer goes over HTTP, not gRPC, so the backend avoids the grpcio wheel on Python 3.14.specs/telemetry_spec.md §14.1 (decision 12) · specs/054-backend-telemetry/research.md R2

Build layer: Claude Code

TechbashClaude Code OTel env vars

What it does, and where it lives

  • bin/claude-otel [claude arguments...] sets the telemetry environment and then execs claude with the arguments unchanged. It is scoped to the wrapper: nothing is written to ~/.claude/settings.json.
  • Signals: metrics, logs (events) and traces, all otlp over http/protobuf to http://localhost:${ALLOY_OTLP_HTTP_PORT:-4318}. The port must be a number (else exit 2). Metrics are cumulative (Mimir wants that; Claude Code defaults to delta) and exported every 10 s instead of 60 s.
  • Content is on: user prompts, assistant responses and tool content, plus real names for tools, subagents, skills and MCP servers (OTEL_LOG_TOOL_DETAILS). Version, entrypoint and repository are added to metrics.
  • Resource attributes are fixed: service.namespace=wcl-agent,app.layer=build,deployment.environment.name=dev.
  • If nothing listens on the Alloy port the wrapper prints a warning and starts Claude Code anyway; the exporters then drop their data. It never blocks.
  • Every process started inside such a session inherits these variables. A backend started there still exports as the runtime layer (its own app.layer wins), but any other OTel-aware tool exports as app.layer=build, so its logs go to the content stream (observability/README.md).

Why

A project wrapper instead of the global settings file: scoped and reversible.specs/telemetry_spec.md §14.1 (decision 6)

Content capture is on in dev only, and Alloy redacts secrets whatever the setting.specs/telemetry_spec.md §14.1 (decision 7)

Runtime layer: the backend

Techopentelemetry-exporter-otlp-proto-http>=1.39,<=1.42.1opentelemetry-instrumentation-{fastapi, sqlalchemy, redis, httpx}==0.63b1

What it does, and where it lives

  • Bootstrap. configure_telemetry() in backend/app/telemetry/__init__.py is the first thing backend/app/main.py runs, before FastAPI and ADK are imported, because global instrumentation must exist before the app and the database engine are created. The package reads its own environment and .env (it cannot import backend/app/config.py, which imports ADK).
  • On or off. Telemetry is on only when OTEL_EXPORTER_OTLP_ENDPOINT is set. Unset, nothing is installed and the test suite and bare runs are untouched. Compose sets it to http://alloy:4318 for the backend, with no depends_on on Alloy, so the backend starts with Alloy down.
  • Resource. service.name=api, service.namespace=wcl-agent, service.version and vcs.ref.head.revision from WCL_GIT_SHA (else git rev-parse --short HEAD, else unknown; the image has no .git, so bin/01_start_app.sh exports it), deployment.environment.name from WCL_ENVIRONMENT, app.layer=runtime.
  • What is instrumented. FastAPI (health paths and the chat socket's connection are excluded; server spans are named by route template, never by raw path), SQLAlchemy, Redis and httpx. ADK adds its own invoke_agent, generate_content and execute_tool spans with GenAI semantic-convention names. Each chat turn on /ws/chat is the root of its own trace (chat_turn_span around _start_turn in backend/app/api/ws.py), so the model and tool spans of one turn belong together; see Stream protocol. One-shot model calls get a chat or embeddings client span with token usage (see Models & providers). The fetch writer and knowledge-base indexer run in tasks started at boot, so their spans start their own traces.
  • Logs. main.py adds an OTLP log handler to the root logger after the log-redaction filter is installed. The handler carries RedactionFilter itself and ignores records from the exporters' own loggers (opentelemetry, urllib3, requests), so a dead collector cannot feed itself. Records carry their span's trace and span id.
  • Metrics. A view keeps only an allowlist of attributes on every instrument (HTTP method, status, route template, outbound host, pool state, GenAI operation, provider, model, agent and tool names). No ids, no raw paths, no Host header. Histograms are exponential and temporality is cumulative.
  • Bounded cost. Batch processors with bounded queues keep export off the request path. One export attempt waits at most 2 s. At exit one hook shuts all three providers down in parallel and waits 3 s in total; whatever is not sent is dropped.

Content policy per environment

WCL_ENVIRONMENT is dev, ci or prod; any other value, unset included, becomes unknown and is treated like ci and prod. Compose sets dev for the backend.

App-side redaction

backend/app/telemetry/redaction.py wraps the span and log exporters, so it runs in the SDK's export thread and sees every record, ADK's own events included. In every environment it masks: string values under sensitive keys (the logging filter's key list plus secret, API and private keys, dsn, credential), bearer and Basic credentials, user:password@ in URLs, sensitive query parameters, key: value pairs in text, and known key shapes (sk-, AIza, ya29., JWTs). Values are cut to 16,384 characters, which is also the span attribute limit. Numeric values under such keys, like gen_ai.usage.input_tokens, survive. This is the first of two redaction layers; Alloy is the second and the only one for the build layer.

Why

Telemetry starts first in main.py because global FastAPI instrumentation swaps fastapi.FastAPI and SQLAlchemy's wraps create_async_engine before the modules that bind them are imported.specs/054-backend-telemetry/research.md R1

ADK captures message content by default, so the lockdown must be explicit outside dev, and the exporter wrappers enforce it a second time.specs/054-backend-telemetry/research.md R3 · specs/telemetry_spec.md §14.2

The OTLP log handler needs its own RedactionFilter, because _install_log_redaction in main.py only filters handlers that exist when it runs.specs/telemetry_spec.md §14.2

The chat socket is excluded from ASGI tracing because its connection lasts the whole session; a root span per turn gives usable trace lengths.specs/054-backend-telemetry/research.md R5

Alloy: the collector

Techgrafana/alloy:v1.21.3otelcol.* componentsOTTL--stability.level=public-preview

What it does, and where it lives

All of it is in observability/alloy/: config.alloy wires the components; stamp.ottl and redact.ottl hold the statements shared by several signal types (one per line, so each works in any context). Alloy's UI is on 127.0.0.1:12345; OTLP ports 4317 (gRPC) and 4318 (HTTP) are published on loopback only.

  1. Receive OTLP on 4317 and 4318, then the memory limiter (80 % limit, 20 % spike limit).
  2. Stamp defaults on the resource when missing: service.namespace=wcl-agent, deployment.environment.name=unknown, app.layer=build for claude-code and runtime otherwise.
  3. Redact, for both layers and every signal (resource, span, span event, log record, datapoint attributes, and log bodies, as string or map). The values of access_token, refresh_token, client_secret, authorization, api_key and password become their SHA-256. These shapes are masked to <redacted>: PEM private keys, JWTs, Bearer and Basic credentials, sk-, AIza, ya29. and GitHub tokens, the password in any scheme://user:pw@ URL, and the value of NAME=value, NAME: value and "name": "value" pairs whose name contains secret, password, token, key, credential, dsn, auth, cookie or session. The pair rule also hides harmless values like primary_key: id; that is the intended trade. Not covered: values nested in lists or nested maps, and secrets with no recognisable shape.
  4. Metrics: delete the per-session, per-user and per-account identifiers (session.id, prompt.id, user.id, user.email, organization.id, client_request_id and similar) from datapoints and from the resource, so they never become labels or land in Mimir's target_info. They stay on spans and logs.
  5. Logs: classify. A log record is content when it has app.content="true", an event name starting gen_ai., or comes from the build layer (service.name=claude-code or app.layer=build) and is not one of 13 known content-free Claude Code events (such as api_request, api_refusal, skill_activated, mcp_server_connection, auth). The build rule fails closed: an event a new Claude Code version adds, or a record without an event name, is content. Content records get the resource attribute content="true"; every other record has any incoming content attribute removed, so the Loki label stays bounded.
  6. Batch, then three exporters: Tempo over gRPC (traces), Loki over OTLP HTTP (logs), Mimir over OTLP HTTP (metrics).

Persistence. Each exporter has a persistent sending_queue on the file-storage component, in /var/lib/alloy/data/queue on the alloy-data volume, with caps of 256 MiB (traces), 256 MiB (logs) and 64 MiB (metrics), and retries forever (max_elapsed_time = "0s"). When a queue is full, Alloy refuses new data for that signal with a retryable error; senders are never blocked, their SDK retries briefly and then drops the data. Queued data drains first when the backends start. File-backed queues are public preview in Alloy, which is why the container runs with --stability.level=public-preview on a pinned image.

Why

Redaction is OTTL transform statements, not Alloy's redaction processor: the processor is experimental in v1.21 and does not cover span events or resource attributes. Claude Code's tool output arrives as a span event.specs/053-telemetry-stack/research.md (Redaction engine)

The build layer is classified as content unless proven content-free, because Alloy is its only redaction step and a new event type must not leak into the 30-day stream by default.observability/alloy/config.alloy (comment on classify)

Prompt, response and tool content gets its own 7-day Loki stream (and traces are kept 7 days because Tempo cannot keep content-bearing traces shorter than the rest).specs/telemetry_spec.md §14.1 (decisions 7 and 9)

  • Grafana access. Anonymous visitors are Viewers who may use Explore. The admin login uses GRAFANA_ADMIN_PASSWORD; observability/grafana/entrypoint.sh sets it again on every start, so an old volume created with admin/admin is fixed too. Unset or empty means a random password nobody knows, i.e. no admin login. No plugins are preinstalled, and Grafana's update checks, analytics and news feed are off.
  • Correlations. The Mimir datasource (the default) links metric exemplars to Tempo by trace_id. Loki turns trace_id into a "View trace" link. Tempo links a span to the logs of the same service and trace (a custom query on the structured-metadata trace_id, span time plus or minus 2 s) and to metrics (plus or minus 2 min).
  • Memory. Every service in this stack, Alloy included, has mem_limit: 512m, except Mimir with 1g. All services have restart: unless-stopped.
  • Ports. Only Alloy (4317, 4318, 12345) and Grafana (3000) are published, on loopback; each host port can be overridden (ALLOY_OTLP_GRPC_PORT, ALLOY_OTLP_HTTP_PORT, ALLOY_UI_PORT, GRAFANA_PORT) so a second stack can run.

Why

Mimir monolithic on the filesystem, no object store: cheaper to run locally, and the move later is possible.specs/telemetry_spec.md §14.1 (decision 10)

Named volumes with retention for every backend, and Grafana holds nothing, so any container can be recreated without losing history.specs/telemetry_spec.md §14.1 (decision 8)

The admin password is reset on every start so that leaving GRAFANA_ADMIN_PASSWORD unset never leaves a known default login behind.observability/grafana/entrypoint.sh (header comment)

Checks

Techbashdocker compose (throwaway project)

What it does, and where it lives

The scripts in observability/test/ each start their own compose project (COMPOSE_PROJECT, default wcl-obs-test) on non-default ports, print PASS and FAIL lines and a RESULT, and remove the project and its volumes at the end (KEEP=1 keeps it). They need Docker and are not part of pytest. The backend side is covered by backend/tests/test_telemetry*.py in the normal suite.
