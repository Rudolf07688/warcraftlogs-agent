Architecture · Runtime

Observability

Traces, logs and metrics from four sources: the backend API and the React app in the browser (the runtime layer), and the Claude Code sessions and the agent team's board that build the app (the build layer). Alloy also scrapes the data stores the app runs on (Postgres, Redis, the containers and the telemetry stack itself) and tails Postgres's slow-statement log. They all reach one always-on collector, Grafana Alloy, which redacts secrets, sorts prompt and answer content into its own short-lived stream, derives request-rate and latency metrics from traces and queues everything on disk until the storage backends (Loki, Tempo, Mimir) and Grafana are running. Mimir turns the metrics into stable recording-rule names that the dashboards query. CPU profiles of the API's requests go straight to Pyroscope, and Grafana links them from the trace. This page follows the data from each source to Grafana. The compose wiring is on Deployment & config.

What it does, and where it lives

  • Two layers, one stamp. Every signal carries app.layer: runtime for the backend (service.name=api) and the browser (service.name=web), build for Claude Code (service.name=claude-code) and the team board (service.name=team-board). All also carry service.namespace=wcl-agent and deployment.environment.name.
  • Alloy is always on. docker compose up starts it with the app; it holds its queues on the alloy-data volume. Loki, Tempo, Mimir, Grafana, Pyroscope and cAdvisor only start with docker compose --profile observability up -d. Until then nothing is lost: Alloy retries from its disk queue.
  • Where the code is. backend/app/telemetry/ (backend), frontend/src/telemetry/ (browser), bin/claude-otel and .claude/team/board.py (build layer), observability/ (Alloy, Loki, Tempo, Mimir and Grafana config, recording rules, the price table, the Postgres exporter's custom queries, build-runtime/commits.py, dashboards and alerts, its README and its test scripts), the alloy and profile services in docker-compose.yml.

Why

One always-on collector with disk queues, and storage backends that can be off: the owner asked for persistence before dashboards, and the transcripts and the team board remain the backfill sources.specs/telemetry_spec.md §14.1 (decisions 8 and 11)

The runtime layer goes over HTTP, not gRPC, so the backend avoids the grpcio wheel on Python 3.14.specs/telemetry_spec.md §14.1 (decision 12) · specs/054-backend-telemetry/research.md R2

Build layer: Claude Code

TechbashClaude Code OTel env vars

What it does, and where it lives

  • bin/claude-otel [claude arguments...] sets the telemetry environment and then execs claude with the arguments unchanged. It is scoped to the wrapper: nothing is written to ~/.claude/settings.json.
  • Signals: metrics, logs (events) and traces, all otlp over http/protobuf to http://localhost:${ALLOY_OTLP_HTTP_PORT:-4318}. The port must be a number (else exit 2). Metrics are cumulative (Mimir wants that; Claude Code defaults to delta) and exported every 10 s instead of 60 s.
  • Content is on: user prompts, assistant responses and tool content, plus real names for tools, subagents, skills and MCP servers (OTEL_LOG_TOOL_DETAILS). Version, entrypoint and repository are added to metrics.
  • Resource attributes are fixed: service.namespace=wcl-agent,app.layer=build,deployment.environment.name=dev.
  • If nothing listens on the Alloy port the wrapper prints a warning and starts Claude Code anyway; the exporters then drop their data. It never blocks.
  • These OTEL_* settings configure Claude Code itself. They do not reach the commands its Bash tool runs: Claude Code passes only CLAUDE_CODE_ENABLE_TELEMETRY, CLAUDE_CODE_ENHANCED_TELEMETRY_BETA and TRACEPARENT (its tool span) to Bash. A backend started from inside a session therefore exports only when its endpoint is set explicitly (compose sets it for the container), and board.py stores that TRACEPARENT on each board entry.
  • The team board. .claude/team/board.py writes one JSONL file per sprint in the git common directory (team-board/). Alloy tails them, so hand-offs, blockers and decisions become Loki log records next to the telemetry of the session that wrote them (see Alloy). The records carry the posting tool span's trace and span id, so Grafana's "View trace" link opens that span. .claude/team/teamstats.py separately pushes the per-sprint and per-seat gauges the improvement dashboard reads.

Why

A project wrapper instead of the global settings file: scoped and reversible.specs/telemetry_spec.md §14.1 (decision 6)

Content capture is on in dev only, and Alloy redacts secrets whatever the setting.specs/telemetry_spec.md §14.1 (decision 7)

Runtime layer: the backend

Techopentelemetry-exporter-otlp-proto-http==1.42.1google-adk==2.10.0opentelemetry-instrumentation-{fastapi, sqlalchemy, redis, httpx}==0.63b1pyroscope-io==1.4.0 (opt-in)

What it does, and where it lives

  • Bootstrap. configure_telemetry() in backend/app/telemetry/__init__.py is the first thing backend/app/main.py runs, before FastAPI and ADK are imported, because global instrumentation must exist before the app and the database engine are created. The package reads its own environment and .env (it cannot import backend/app/config.py, which imports ADK).
  • On or off. Telemetry is on only when OTEL_EXPORTER_OTLP_ENDPOINT is set. Unset, nothing is installed and the test suite and bare runs are untouched. Compose sets it to http://alloy:4318 for the backend, with no depends_on on Alloy, so the backend starts with Alloy down.
  • Resource. service.name=api, service.namespace=wcl-agent, service.version and vcs.ref.head.revision from WCL_GIT_SHA (else git rev-parse --short HEAD, else unknown; the image has no .git, so bin/01_start_app.sh exports it), deployment.environment.name from WCL_ENVIRONMENT, app.layer=runtime.
  • What is instrumented. FastAPI (health paths and the chat socket's connection are excluded; server spans are named by route template, never by raw path, even when the method is not allowed on it), SQLAlchemy (one tracer per engine, so a statement is one span), Redis and httpx. ADK adds its own invoke_agent, generate_content and execute_tool spans with GenAI semantic-convention names. Each chat turn on /ws/chat is a span of its own trace (chat_turn_span around _start_turn in backend/app/api/ws.py), so the model and tool spans of one turn belong together; it is the root, or the child of the browser's "chat send" span when the message carries a valid traceparent (see Browser and Stream protocol). One-shot model calls get a chat or embeddings client span with token usage (see Models & providers). The fetch writer and knowledge-base indexer run in tasks started at boot, so their spans start their own traces.
  • Logs. main.py adds an OTLP log handler to the root logger after the log-redaction filter is installed. The handler carries RedactionFilter itself and ignores records from the exporters' own loggers (opentelemetry, urllib3, requests), so a dead collector cannot feed itself. Records carry their span's trace and span id.
  • Metrics. A view keeps only an allowlist of attributes on every instrument (HTTP method, status, route template, outbound host, pool state, GenAI operation, provider, model, agent and tool names, and six enums of the app's own metrics: app.cache.name, app.cache.result, app.rag.index, app.rag.strategy, app.llm.finish_reason and app.embedding.task). No ids, no raw paths, no Host header. Histograms are exponential (native histograms in Mimir) and temporality is cumulative.
  • App metrics. Things the instrumentation libraries do not measure, each a no-op while telemetry is off. backend/app/telemetry/metrics.py holds the knowledge-base search (app.rag.retrieval.duration, app.rag.retrieved_chunks, app.rag.top_score, app.rag.empty_results; recorded by record_retrieval() in kb/search.py) and the time from the start of a turn to its first answer text, tool rounds included (app.llm.stream.ttft; record_ttft() in agent_runner.py). Three more come from the same file and the embedder: why each model response ended (app.llm.finish_reasons, by model; the reason is a fixed set of names, anything else is other), how many turns a conversation has had at the end of each chat turn (app.agent.turns_per_conversation, by agent) and each provider embedding request, a failed one too with its error class (app.embedding.duration and app.embedding.batch_size, by model and by document or query; record_embedding() in kb/embedder.py). A query embedding that the search's own 3 s budget cancels is not recorded: the cancel is not an Exception, so the embedder's failure branch never runs (found in the live check of 2026-11-05). The search metrics are labelled with the kind searched (kb.search.searched_kinds, shared with the SQL: a report code alone counts as wcl) or all. The WCL cache counter app.cache.requests lives in wcl_agent/cache/cache.py, because that package never imports the backend; it counts each key lookup once, by its final outcome, while the admin counters keep every step. The database pool gauge comes from the SQLAlchemy instrumentation. Dashboards read them through the recording rules.
  • SQL comments. With telemetry on, the SQLAlchemy instrumentation appends the statement's W3C traceparent to every statement as a comment (sqlcommenter; nothing else: no driver or framework version, no tracestate or baggage). Postgres's slow-statement log therefore carries the trace id, which is how a slow statement links to its trace (see Alloy). It costs one extra prepare per statement, about 0.5 ms.
  • Span profiles. Off unless telemetry is on and PYROSCOPE_SERVER_ADDRESS is set; compose sets it only when WCL_PROFILES is, for runs with the observability profile up. Then setup.add_span_profiles() starts the Pyroscope CPU profiler, which pushes straight to Pyroscope (no Alloy hop), and SpanProfiles gives every server root span (a request, a chat turn) the attribute pyroscope.profile.id and tags the CPU samples taken meanwhile with the same span_id and a span_name. The name is bounded: the route template from the start of the span, a bare method for an unknown path, or a fixed name such as chat turn; never an id, never the trace id. The tags removed at the end are exactly those added at the start. SQL, Redis and httpx calls outside a request are not tagged. Tempo's "Profiles for this span" opens the flame graph. Limits: samples are tagged per OS thread and every asyncio request shares the event-loop thread, so two requests running at once share samples; a span shorter than a few sampling intervals (100 Hz) can show an empty graph.
  • Browser context. backend/app/telemetry/browser.py validates what the browser sends: a W3C traceparent (at most 128 characters, well formed, non-zero ids, sampled) and the Faro session id (1 to 64 of [A-Za-z0-9._:-]). On the chat socket anything unusable is ignored: the turn is a fresh root and has no session.id. REST calls are not checked like that: FastAPI's own instrumentation takes the browser's traceparent (and baggage) as it comes, so a client can pick its trace id or switch tracing off with an unsampled parent. FaroSessionMiddleware copies x-faro-session-id on REST calls to the server span's session.id. The id is a span attribute only, never a metric label.
  • Bounded cost. Batch processors with bounded queues keep export off the request path. One export attempt waits at most 2 s. At exit one hook shuts all three providers (and the profiler, when on) down in parallel and waits 3 s in total; whatever is not sent is dropped.

App-side redaction

backend/app/telemetry/redaction.py wraps the span and log exporters, so it runs in the SDK's export thread and sees every record, ADK's own events included. In every environment it masks: string values under sensitive keys (the logging filter's key list plus secret, API and private keys, dsn, credential), bearer and Basic credentials, user:password@ in URLs, sensitive query parameters, key: value pairs in text, and known key shapes (sk-, AIza, ya29., JWTs). Values are cut to 16,384 characters, which is also the span attribute limit. Numeric values under such keys, like gen_ai.usage.input_tokens, survive. This is the first of two redaction layers; Alloy is the second and the only one for the build layer.

Why

Telemetry starts first in main.py because global FastAPI instrumentation swaps fastapi.FastAPI and SQLAlchemy's wraps create_async_engine before the modules that bind them are imported.specs/054-backend-telemetry/research.md R1

ADK captures message content by default, so the lockdown must be explicit outside dev, and the exporter wrappers enforce it a second time.specs/054-backend-telemetry/research.md R3 · specs/telemetry_spec.md §14.2

The OTLP log handler needs its own RedactionFilter, because _install_log_redaction in main.py only filters handlers that exist when it runs.specs/telemetry_spec.md §14.2

The chat socket is excluded from ASGI tracing because its connection lasts the whole session; a span per turn gives usable trace lengths.specs/054-backend-telemetry/research.md R5

The span profiler is our own processor, not pyroscope-otel's: that one tagged every root span (background SQL, Redis and httpx work too), tagged the trace id (a new label value per request) and removed tags by the span's final name, so they piled up.backend/app/telemetry/setup.py (SpanProfiles docstring)

Profiling is opt-in because without a Pyroscope to receive them the profiler would sample and upload to a missing host for nothing.docker-compose.yml (comment on PYROSCOPE_SERVER_ADDRESS)

The browser's trace context travels in the WebSocket message, because a browser WebSocket cannot set headers; there is no baggage.specs/057-browser-telemetry/spec.md

Browser layer: the React app

Tech@grafana/faro-react 2.13.0@grafana/faro-web-tracing 2.13.0Alloy faro.receiver

What it does, and where it lives

  • Sender. Grafana Faro in frontend/src/telemetry/ reports Web Vitals, errors, route changes, chat events and browser traces, as app web. It starts only when VITE_FARO_URL is set (compose sets it for the dev server; see Frontend).
  • Receiver. faro.receiver in observability/alloy/config.alloy, on port 12347 (published on loopback as ALLOY_FARO_PORT). Logs enter the pipeline through their own otelcol.receiver.loki bridge and traces directly, both at the memory limiter after a Faro-only transform, so they pass the same stamp and redaction steps; nothing goes to Loki directly. Logs are logfmt lines (kind=measurement type=web-vitals lcp=...) under service_name=web.
  • The payload is not trusted. The key ships in the bundle, so it only keeps casual posts out. The receiver checks x-api-key, allows CORS only from http://localhost:5173 and http://127.0.0.1:5173 (literals in the config: change them with VITE_FARO_* when the app moves), caps a body at 64 KiB and limits the whole receiver to 5 requests per second (burst 10), about 0.3 MiB/s at most. The limit is global, not per app, because the app name comes from the payload. Source maps are never downloaded, because the receiver would fetch any URL a stack frame names. A transform overwrites the resource on logs and traces (service.name=web, app.layer=runtime, environment dev) and removes the content flags and event.name, so a payload cannot pose as the API or the build layer or reach the 7-day content stream. Known gap in Alloy 1.21.3: the size cap reads Content-Length, so a chunked body without one is not capped.
  • Privacy. The user is a salted hash of the account id, query strings and fragments are cut from every URL before sending, and console output is not captured. Faro's session_id= in a log line is masked by the general pair rule; the session id survives as the session.id attribute on spans.
  • Click to Postgres. The browser's traces carry traceparent on same-origin REST calls, and the chat socket carries it in the message (Stream protocol). One trace then runs from the "chat send" span in the browser through the backend's "chat turn" and invoke_agent spans to the PostgreSQL and Redis spans. The backend side is in Runtime layer.
  • Route as the view. The matched React Router template (/app/*, never a raw path) is Faro's view, so every line the browser sends carries it as view_name and the frontend dashboard can group by route.
  • Error boundaries. A boundary around the app shell and one around each chat panel (sidebar, message list, composer) catches a render error, shows a plain "Something went wrong" with Retry (never the error text, which can carry model or WCL text) and reports it to Faro as React ErrorBoundary <type> with the component stack, the route and the boundary's name. A panel starts clean when the conversation changes. A route render error never reaches the shell boundary, because the data router catches it first, so the route tree has a root errorElement that reports the same way (a retry reloads the page). With Faro off a boundary only shows the fallback. Details on Frontend.
  • Chat events. Once per turn: agent_message_sent, agent_first_token_rendered (ttft_ms, once the first token is on screen), agent_response_completed (duration_ms) and stream_aborted (reason connection_lost or closed). They carry the model and whole milliseconds, never text or ids. There is no feedback event: the app has no feedback feature.
  • Span metrics. Browser spans are kept out of the request-rate metrics (below): their names and attributes are browser-controlled.

Why

The receiver's resource is overwritten rather than filled in, because the stamp step only adds what is missing and a browser could otherwise claim any service, layer or content flag.observability/alloy/config.alloy (comment above otelcol.processor.transform "faro")

The throughput limit is global because the receiver shares the memory limiter and the export queues with the backend's and the build layer's telemetry.specs/057-browser-telemetry/spec.md (clarifications)

Alloy: the collector

Techgrafana/alloy:v1.21.3otelcol.* componentsOTTL--stability.level=public-previewprometheus.exporter.{postgres, redis, self}

What it does, and where it lives

All of it is in observability/alloy/: config.alloy wires the components; stamp.ottl and redact.ottl hold the statements shared by several signal types (one per line, so each works in any context). Alloy's UI is on 127.0.0.1:12345; OTLP ports 4317 (gRPC) and 4318 (HTTP) and the Faro port 12347 are published on loopback only.

  1. Receive OTLP on 4317 and 4318, the Faro receiver on 12347 (Browser) and the team board's files (below), then the memory limiter (80 % limit, 20 % spike limit). Faro records are re-injected at the limiter. Board records join later, at the redaction step, because the stamp step would strip their path marker; both pass every later step.
  2. Stamp defaults on the resource when missing: service.namespace=wcl-agent, deployment.environment.name=unknown, app.layer=build for claude-code and runtime otherwise.
  3. Redact, for both layers and every signal (resource, span, span event, log record, datapoint attributes, and log bodies, as string or map). The values of access_token, refresh_token, client_secret, authorization, api_key and password become their SHA-256. These shapes are masked to <redacted>: PEM private keys, JWTs, Bearer and Basic credentials, sk-, AIza, ya29. and GitHub tokens, the password in any scheme://user:pw@ URL, and the value of NAME=value, NAME: value and "name": "value" pairs whose name contains secret, password, token, key, credential, dsn, auth, cookie or session. The pair rule also hides harmless values like primary_key: id; that is the intended trade. Not covered: values nested in lists or nested maps, and secrets with no recognisable shape.
  4. Metrics: delete the per-session, per-user and per-account identifiers (session.id, prompt.id, user.id, user.email, organization.id, client_request_id and similar) from datapoints and from the resource, so they never become labels or land in Mimir's target_info. They stay on spans and logs. Claude Code exports one cumulative stream per session and prompt; with those ids gone the streams of one export would share labels and timestamp, and Mimir would keep the first and silently discard the rest, so for claude-code they are then summed into one series per process.
  5. Logs: accept window. Every log record dated more than 6 days back or more than 10 minutes ahead (its time, else its observed time) is dropped here (otelcol.processor.filter.log_window, counted in otelcol_processor_filter_logs_filtered_total). Loki refuses such records anyway, and the old ones used to get a retryable error that held a whole batch in the disk queue.
  6. Logs: classify. A log record is content when it has app.content="true", an event name starting gen_ai., or comes from the build layer (service.name=claude-code or app.layer=build) and is not one of 13 known content-free Claude Code events (such as api_request, api_refusal, skill_activated, mcp_server_connection, auth). The build rule fails closed: an event a new Claude Code version adds, or a record without an event name, is content. Content records get the resource attribute content="true"; every other record has any incoming content attribute removed, so the Loki label stays bounded. The team board is the one build-layer source exempt from content, and the exemption follows the path, not the payload: only records from the board branch carry the marker attribute alloy.board (the stamp step deletes it from every other source), so an OTLP sender that names itself team-board still lands in the content stream.
  7. Batch, then three exporters: Tempo over gRPC (traces), Loki over OTLP HTTP (logs), Mimir over OTLP HTTP (metrics).

Request metrics from traces. After redaction, spans from api and claude-code only (an allowlist by service.name, so a browser or spoofed source stays out) also feed Alloy's spanmetrics and servicegraph connectors. Span metrics (traces_spanmetrics_calls, traces_spanmetrics_duration_bucket, in seconds, with exemplars that link a latency point to its trace) use bounded dimensions only: route, status code, the GenAI operation, agent, tool and model names, and the database system and operation. Never a URL, SQL text or session id. The service graph counts calls and latency per client and server pair. Both go through the same identifier-dropping step as every metric, then to Mimir. One aggregate is kept per promoted resource (service name, namespace, environment, layer), so a new service.version continues the same series, and an aggregate idle for 5 minutes expires instead of being re-exported with frozen values. An aggregate keeps the resource of its first span, so a transform right after the connector deletes service.version and vcs.ref.head.revision from it: otherwise, after a restart with a new version, the old version stayed on its target_info beside the app's own for as long as spans kept coming. The running version is the app's own resource alone; no spanmetrics series changes, because neither is a promoted label. Tempo's own metrics generator stays off.

Team board. local.file_match and loki.source.file tail /var/lib/team-board/sprint-*.jsonl and selftest-*.jsonl, mounted read-only from the git common directory (any other file there is ignored). A loki.process step drops lines that lack text or kind and maps each remaining JSON entry to one record (body = text, timestamp = the entry's ts, fields as attributes, the stored TRACEPARENT as trace and span id), and the record enters the pipeline at the redaction step (marked alloy.board), so board text is redacted like everything else. The records stay in the 30-day stream. How far each file has been read is kept on the alloy-data volume; observability/board-backfill.sh resets it after Loki lost its data. That restores only recent history: Loki refuses an entry more than about an hour behind the newest in its stream, and all boards share one stream, so older sprints' entries are lost (they are in meta/sprints/; backlog 055-board-history). Alloy's log window also drops anything older than 6 days; widening Loki's limit for the board alone is not possible (it is per tenant), so that stays as it is.

Data stores and infra. The last section of config.alloy. Metrics: prometheus.exporter.postgres (the default collectors plus six more, and the custom queries in observability/postgres/queries.yaml for the knowledge base's vector indexes and tables), prometheus.exporter.redis (INFO-based series only, no key checks, because key names carry account ids), Alloy's own exporter, and scrapes of Loki, Tempo, Mimir and cAdvisor every 30 s. They are remote-written to Mimir under the exporters' own names (jobs postgres, redis, alloy, loki, tempo, mimir, cadvisor), not through the OTLP path, and wait in the remote-write WAL on alloy-data while Mimir is down. One relabel step fixes job and instance names and keeps only the series the dashboards and alerts read (the spec's 50,000 active series budget), with no SQL text, key names, DSNs or container ids as labels. cAdvisor reports every container on the Docker host, so only this compose project's containers (WCL_COMPOSE_PROJECT; unset keeps none) and the host's root cgroup stay, labelled by compose service alone (host for the machine). The Postgres exporter logs in as the monitoring role from the DSN compose builds, which Alloy treats as a secret, and lists statements by queryid with include_query = false.

Postgres log. Postgres writes its slow statements (over 250 ms), lock waits and autovacuum runs to files on the pglog volume (postgresql-<hour>.log, each overwritten a day later), with a line prefix of time, pid, query id and SQLSTATE; bind values are never logged. Alloy tails the files read-only (it has no Docker access, and Docker's own logs are not a path for this), joins multi-line messages, takes the last traceparent comment as the record's trace and span id and sets the resource (service.name=postgres, runtime layer, dev). Before the shared redaction it masks: quoted strings, dollar-quoted bodies and numbers everywhere except known operational messages (autovacuum, lock waits, checkpoints, start and stop), double-quoted values in records without SQL, and a DETAIL, CONTEXT or HINT line unless it has a known shape (key and row details have their values masked whole; any other is withheld). The records then pass the memory limiter, stamp, redaction, log window and classification like OTLP logs, never straight to Loki. In Loki they carry pg_duration_ms, pg_query_id, pg_severity, pg_sqlstate, pg_pid and trace_id as structured metadata, and the trace id opens the trace.

Persistence. Each exporter has a persistent sending_queue on the file-storage component, in /var/lib/alloy/data/queue on the alloy-data volume, with caps of 256 MiB (traces), 256 MiB (logs) and 64 MiB (metrics). Tempo and Mimir exports retry without limit (max_elapsed_time = "0s"); Loki exports retry for 24 hours, so a refusal that can never succeed frees its queue consumer instead of holding it and its batch for good. In an outage longer than a day the batches being retried at that moment (at most one per consumer) are dropped, and the rest of the queue lands when Loki is back. When a queue is full, Alloy refuses new data for that signal with a retryable error; senders are never blocked, their SDK retries briefly and then drops the data. Queued data drains first when the backends start. File-backed queues are public preview in Alloy, which is why the container runs with --stability.level=public-preview on a pinned image.

Why

Redaction is OTTL transform statements, not Alloy's redaction processor: the processor is experimental in v1.21 and does not cover span events or resource attributes. Claude Code's tool output arrives as a span event.specs/053-telemetry-stack/research.md (Redaction engine)

The build layer is classified as content unless proven content-free, because Alloy is its only redaction step and a new event type must not leak into the 30-day stream by default.observability/alloy/config.alloy (comment on classify)

cAdvisor and Postgres's log stay out of Alloy's reach on purpose: Alloy takes browser input, so it has no Docker or containerd socket (root-equivalent on the host) and reads Postgres's log from a read-only volume. Statement text is never a metric label.docker-compose.yml (comments on cadvisor and the db command) · specs/telemetry_spec.md §9.3

The Postgres log is masked in Alloy and the database writes no bind values, because a statement's text is partly user input and the redaction rules look for secret shapes, not for personal data.observability/alloy/config.alloy (comment above otelcol.processor.transform "postgres")

Prompt, response and tool content gets its own 7-day Loki stream (and traces are kept 7 days because Tempo cannot keep content-bearing traces shorter than the rest).specs/telemetry_spec.md §14.1 (decisions 7 and 9)

All three build dashboards mark sprint ends.
  • Build vs Runtime (D12). Puts the build layer next to the runtime: annotations for each API version while it ran; p95 latency, error ratio and LLM cost per request by commit; and a table commit, seat, estimated build cost and runtime deltas. The running version is read from the API's target_info (service.version is not a promoted label), preferring a known version over unknown or none, so one process is one version. The seat that authored a commit comes from build_commit_info, which observability/build-runtime/commits.py pushes at sprint wrap-up beside teamstats.py (--dry-run prints the table). A commit belongs to the seat of the latest hand-off on the same feature, from the board entries that name the commit (a ref, or "head <sha>" in the text), the roster and each sprint's usage.txt; a version no board entry names is unattributed. The build cost is left out, never zero, while no usage file exists yet.
  • Alerts. Two Grafana-managed rules in folder "WCL alerts", provisioned as code (edits in the UI are not saved): Telemetry pipeline failures or drops (Alloy export or enqueue failures or receiver refusals for any signal in the last 2 minutes) and Build spend per day above threshold (Claude Code's estimate over 24 hours against alert:build_spend_usd_per_day:threshold in datastores.yaml, now 200 USD, set by the owner on 2026-11-05). No contact point is configured: the state shows in Grafana's alert list, which is what a local stack needs.
  • Correlations. The Mimir datasource (the default) links metric exemplars to Tempo by trace_id. Loki turns trace_id into a "View trace" link. Tempo links a span to the logs of the same service and trace (a custom query on the structured-metadata trace_id, span time plus or minus 2 s), to metrics (plus or minus 2 min) and, for a server root span, to its CPU profile in Pyroscope; its service map reads Alloy's service-graph metrics from Mimir.
  • Memory. Every service in this stack, Alloy included, has mem_limit: 512m, except Mimir with 1g and cAdvisor with 256m. All services have restart: unless-stopped.
  • Ports. Only Alloy (4317, 4318, 12345 and the Faro receiver 12347), Grafana (3000) and Pyroscope (4040) are published, on loopback; each host port can be overridden (ALLOY_OTLP_GRPC_PORT, ALLOY_OTLP_HTTP_PORT, ALLOY_UI_PORT, ALLOY_FARO_PORT, GRAFANA_PORT, PYROSCOPE_PORT, and DB_PORT and REDIS_PORT for the data stores) so a second stack can run.

Why

Mimir monolithic on the filesystem, no object store: cheaper to run locally, and the move later is possible.specs/telemetry_spec.md §14.1 (decision 10)

Alerts are a minimal local set with no contact point, and their thresholds live in a recording rule, so changing a number is a rules edit that Mimir reloads within a minute.observability/grafana/provisioning/alerting/rules.yaml (header comment)

Named volumes with retention for every backend, and Grafana holds nothing, so any container can be recreated without losing history.specs/telemetry_spec.md §14.1 (decision 8)

The admin password is reset on every start so that leaving GRAFANA_ADMIN_PASSWORD unset never leaves a known default login behind.observability/grafana/entrypoint.sh (header comment)

Recording rules and cost

TechMimir rulerPromQLnative histogramsPyYAML (generator)

What it does, and where it lives

  • Aliases, not raw names. Dashboards query recording rules with short stable names, so a rename in OpenTelemetry's semantic conventions or in Claude Code touches one rule file, not every panel. The files are in observability/mimir/rules/anonymous/, one per owner, in groups evaluated every minute. Because rules run every minute, an amount over a range (tokens, cost) is sum_over_time(<alias>[range]) * 60. A ratio divides two such totals. A count of discrete events (D1's sessions started, lines of code, commits and pull requests, and the turn, call, search and lookup counts on D6 to D8) is the one exception to "aliases only": the panel takes increase() of the raw counter and rounds it, because a rule's copy of a counter loses its created-time zero sample (a short session's first increment would vanish) and a rate alias summed over a range gives fractions.

  • Price table. observability/pricing/pricing.yaml lists list prices in USD per million tokens, per model and token type (input, output). observability/pricing/generate.py turns it into cost.yaml: one rule per model and token type that records llm_price_usd_per_token every minute as a constant, so the price history is a time series and cost already recorded keeps the price of its time. A test fails when the two files differ, and a price change is a commit to pricing.yaml plus a run of the generator.
  • Runtime cost. genai:cost_usd:rate5m (USD per second, by model and agent) joins the backend's token usage (histogram_sum of gen_ai_client_token_usage) to the price series on model and token type. A dated model id (@20260101 or -20260101) is priced as its undated row; a model without a price row has no cost series rather than zero. Cached input is priced as input, because the backend reports input and output only: an overestimate on cache-heavy turns. Cost per hour is 3600 * sum(genai:cost_usd:rate5m). Gemini 3.6, 3.7 and 3.8 Flash carry Google's introductory Vertex price ($0.75 input, $3.75 output per million tokens) through 2026-12-31; the standard $1.50 and $7.50 start 2027-01-01 and need a price commit on that day. Flash-Lite and 3.1 Pro are not verified.
  • Build cost. Claude Code reports its own cost estimate, which D1 and D2 use as cc:cost_usd:*. Cost per board seat comes per sprint from .claude/team/teamstats.py, priced at Opus 5.5 rates; D12's per-commit build cost comes from commits.py with the same pricing.

Why

Dashboards and alerts query aliases so that a metric rename is absorbed in one rules file.specs/055-build-telemetry/contracts/aliases.md

Prices are recorded as a series by the ruler instead of being a static label join, so a price change applies from its commit onward and history keeps the old price, with no restart.observability/pricing/pricing.yaml (header comment) · observability/pricing/generate.py
