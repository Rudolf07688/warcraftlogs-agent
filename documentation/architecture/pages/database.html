Architecture · Data

Database & migrations

One PostgreSQL 17 database, with the pgvector extension, holds all app state: accounts and workspaces, chats, profiles, guides, the raw Warcraft Logs store and the knowledge base. The backend reaches it through async SQLAlchemy over asyncpg as a non-privileged role that row-level security constrains. Alembic owns the schema and runs as a separate owner role.

Postgres and the two roles

Techpgvector/pgvector:pg17-trixiePostgreSQL 17pgvector ≥ 0.8 (extension)citext (extension)pgvector>=0.5.1 (Python)

What it does, and where it lives

  • docker-compose.yml service db: image pgvector/pgvector:pg17-trixie, which is Postgres 17 plus the pgvector extension. It uses the same major version and on-disk format as postgres:17, so an existing pgdata volume starts as it is. The -trixie tag matches postgres:17's Debian 13 glibc. The plain pg17 tag is built on bookworm and would leave a collation-version mismatch. The port is published on loopback only (127.0.0.1:5432), with a pg_isready healthcheck that the backend waits on.
  • Owner role (POSTGRES_USER, DATABASE_OWNER_URL): owns the tables and runs Alembic. Settings.owner_database_url in backend/app/config.py falls back to the runtime URL when DATABASE_OWNER_URL is empty, for single-role dev setups.
  • Runtime role (APP_DB_USER, default wcl_app, DATABASE_URL): what the app connects as. It is not a superuser or a table owner and has no BYPASSRLS, so the RLS policies bind it. Migration 0004_rls creates it if it is missing, so there is no init script. The DATABASE_URL default is postgresql+asyncpg://wcl:wcl@localhost:5432/wcl.
  • ADK's DatabaseSessionService (agent session history) lives in the same database. It reuses the app's engine (backend/app/main.py) and creates its own tables with prepare_tables(), outside Alembic. 0004_rls grants the runtime role CREATE on public for that reason.

Why

PostgreSQL 17 was the owner's call: "We will spin up a backend postgres 17 database to keep track of app state over time".specs/001-streaming-chat-frontend/spec.md (Input)

The vectors live in the same Postgres through the pgvector image, not in a separate vector database, which the owner's design rejected. The -trixie tag avoids a collation mismatch on the existing volume.specs/043-kb-store-embed/research.md R1

Two roles exist so RLS really constrains the app. A single superuser role could bypass RLS and defeat it. The owner role is used only by Alembic.specs/006-multi-tenancy/research.md R4

Engine, sessions & repositories

Techsqlalchemy[asyncio]>=2.0.0asyncpg>=0.29.0

What it does, and where it lives

  • backend/app/db/session.py: one module-level engine (create_async_engine, pool_pre_ping=True) and SessionLocal (async_sessionmaker, expire_on_commit=False). The pool is set by DB_POOL_SIZE (10), DB_MAX_OVERFLOW (20) and DB_POOL_TIMEOUT (10 s). get_session() is the FastAPI dependency: it commits on success and rolls back on error.
  • backend/app/tenancy/context.py: tenant_session (per request), tenant_scope (background jobs) and set_scope. They open a transaction and set app.tenant_id and app.user_id transaction-locally in one set_config(…, true) statement (sc-270). commit_and_rescope re-applies them after a mid-handler commit. How a request gets its identity is on Auth & multi-tenancy.
  • backend/app/db/repository.py: data access for conversations, messages, artifacts, graphs, tracked and recent raids, M+ runs, known entities, characters, guild and guides. Every tenant-owned function takes a keyword-only tenant_id and puts it in the SQL, so a row is never fetched by id alone.
  • backend/app/repositories/: users, tenants, invitations, sessions, reset_tokens, audit (auth), profile_proposals and raw_fetches (the raw WCL store). The knowledge base reads and writes through backend/app/kb/store.py and search.py.

Row-level security

TechPostgres RLSset_config(…, true)

What it does, and where it lives

  • Each of the 17 tenant tables has RLS enabled and forced, so the table owner is bound too. Each has one policy, applied with USING and WITH CHECK: 
    tenant_isolation:       tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid
tenant_user_isolation:  the tenant predicate AND
                        user_id = NULLIF(current_setting('app.user_id', true), '')::uuid
  • tenant_user_isolation exists only on profile_proposals (0017, feature 036). It replaced the tenant-only policy, which was dropped rather than kept: Postgres ORs permissive policies together, so keeping it would have let any user in the tenant through.
  • If the setting is missing, NULLIF turns it into NULL and the predicate matches no rows. A forgotten scope reads nothing; it never reads everything.
  • The settings are transaction-local (set_config(…, true)), so a pooled connection never carries one tenant's scope into the next transaction. The raw store sets only app.tenant_id (raw_fetches.scope_tenant), because no raw-store policy reads the user.
  • kb_chat_chunks names its conversation through a composite FK (conversation_id, tenant_id) → conversations (id, tenant_id). FK checks bypass RLS, so this is what stops tenant B's chunk from pointing at tenant A's conversation. The unique key leads with tenant_id, so a foreign id fails on the FK and never reveals that the row exists.
  • Grants: 0004_rls grants the runtime role DML on all tables and sequences, plus ALTER DEFAULT PRIVILEGES for tables the owner creates later. Each later migration also grants DML on its new tables explicitly.
  • The global tables have no RLS. Code scopes them instead: the raw store serves a row only by its visibility rule (WCL client, cache & store), and the knowledge base joins WCL chunks through that same rule (Knowledge base).
  • Tests: backend/tests/test_rls.py and the *_pg.py tests run only when TEST_DATABASE_URL points at a migrated Postgres. Otherwise they are skipped. The default suite runs on SQLite and checks app-level scoping.

Why

RLS is defence in depth: if an app-level WHERE tenant_id is ever missed, the database still blocks cross-tenant reads and writes. Settings are transaction-local because pooled connections must never keep a session-level SET. Alternatives: app scoping only (a single point of failure for the worst risk), or one superuser role (bypasses RLS).specs/006-multi-tenancy/research.md R4

User-level RLS on proposals: the rule is "same user", and before 0017 only the app enforced it.backend/migrations/versions/0017_proposal_user_rls.py (docstring)

The composite conversation FK on chat chunks closes the hole that FK checks skip RLS.backend/migrations/versions/0019_kb_chunks.py (docstring)

Migrations

Techalembic>=1.13.021 revisions, linear

What it does, and where it lives

  • backend/alembic.ini and backend/migrations/. env.py runs async, injects settings.owner_database_url so no credentials sit in alembic.ini, uses Base.metadata as the target, and excludes ADK's tables from autogenerate.
  • The app never creates or alters tables at startup (main.py lifespan). The schema is set up with uv run python -m backend.cli.init_db, which runs upgrade 0002_auth_tenancy, creates the founder if there is none, then runs upgrade head. It is idempotent and safe on every deploy. The steps are separate because 0003 backfills existing rows to the founder's tenant and fails loudly if no platform admin exists. The backend container does not run migrations itself.
  • Revision ids must fit alembic_version.version_num (varchar(32)), so two ids are shorter than their file names (marked below).

Rules for new migrations

  • Lock rule, written in backend/migrations/script.py.mako (sc-359), so every new revision starts with it: on an existing busy table, never hold a lock for longer than one short statement. Work in op.get_context().autocommit_block(). Add columns with a constant default (a metadata-only change) and if_not_exists. Backfill in short batches that commit one by one. Drop any leftover index (if_exists, concurrently) before you create_index(…, postgresql_concurrently=True). Every step must be safe to re-run.
  • Conventions the existing revisions follow: RLS, grants and Postgres-only types sit behind if bind.dialect.name != "postgresql": return. A new tenant table gets ENABLE and FORCE RLS, the tenant_isolation policy and an explicit DML grant to APP_DB_USER. A data UPDATE on a forced-RLS table lifts FORCE around the statement, as in 0012 and 0015, because the owner is bound by its own policy.

Why

Alembic replaced create_all plus hand-written ALTER … IF NOT EXISTS. Multi-tenancy needed phased NOT NULL backfills, FKs, per-tenant unique constraints, RLS and grants, all reversible and in order. Alternatives: more hand-written ALTERs (no phased backfill, no downgrade), drop and recreate (destroys the founder's data), or SQLModel (needless churn).specs/006-multi-tenancy/research.md R1

0001_baseline still matters only for databases that existed before feature 006: it lets Alembic adopt their tables without recreating them. A fresh install simply creates them.backend/migrations/versions/0001_baseline.py (docstring)

SQLite tests & timestamps

Techaiosqlite>=0.22.1 (test)

What it does, and where it lives

  • The default test suite builds the schema with Base.metadata.create_all on SQLite (backend/tests/conftest.py), not through Alembic. So the models are written to work on both databases:
    • JSON columns use JSON().with_variant(JSONB(), "postgresql").
    • Ids use the generic Uuid type.
    • Vector(768) is accepted by SQLite's loose typing.
    • The generated tsv column compiles to to_tsvector(…) on Postgres and NULL on SQLite (_TsVector with @compiles).
  • Postgres-only behaviour (RLS, FOR UPDATE, advisory locks, citext, set_config) is skipped on SQLite through dialect checks. The *_pg.py tests cover it against a real Postgres.
  • The model declares users.email as String(320), but migration 0002 creates it as citext, so uniqueness is case-insensitive in Postgres. The app also lowercases emails.
  • backend/app/db/timestamps.py: as_utc(value). All timestamp columns are DateTime(timezone=True) and the app stores UTC. SQLite returns them without a zone, so a naive value read back is treated as UTC (feature 029, decision D15).

Why

One set of portable models backs both production and fast unit tests. RLS can't run on SQLite, so a separate Postgres-only test covers it.specs/006-multi-tenancy/research.md R1, R4

The knowledge-base columns keep the models honest about the schema on both databases, rather than leaving tsv out of the metadata.specs/043-kb-store-embed/research.md R3
