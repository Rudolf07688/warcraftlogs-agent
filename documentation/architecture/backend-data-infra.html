Configuration and secrets

  • All secrets and settings come from the root .env (gitignored). .env.example is the tracked template, with every setting commented.
  • backend/app/config.py reads them into one typed Settings(BaseSettings) from pydantic-settings. It also calls load_dotenv(), because wcl_agent/ and ADK read os.getenv directly.
  • Google auth is ADC everywhere. No API key or key file is in the repo or in .env.

Start and database-init scripts

  • bin/00_init_migrate_db.sh: uv sync --all-extras (it creates .venv if that fails), starts only db, then runs alembic upgrade head. If the upgrade fails, it tries the fresh-database path: upgrade to 0002_auth_tenancy, run backend.cli.bootstrap_admin, then upgrade to head.
  • bin/01_start_app.sh [--build]: runs the init script, then docker compose up -d, prints docker compose ps and follows the logs.
  • backend/cli/init_db.py does the same migrate → founder → migrate sequence as one idempotent Python command (uv run python -m backend.cli.init_db).

Why

One docker compose up gives a full local stack, and secrets come only from the root .env through env_file. The owner asked for exactly this: "locally testable with a docker compose file that injects our root .env file".specs/001-streaming-chat-frontend/research.md §6 · specs/001-streaming-chat-frontend/spec.md (Input)

ADC is mounted read-only rather than shipping a key, so the same code path works unchanged on Cloud Run with an attached service account.specs/001-streaming-chat-frontend/research.md §6 · documentation/deployment.md

Config is read from environment variables, so only the secret source changes between local .env and Secret Manager in production.specs/001-streaming-chat-frontend/research.md §9 · backend/app/config.py (module docstring)

Postgres and Redis bind to loopback only (QA finding SEC-001). Redis has no auth, so it must not face the LAN.docker-compose.yml (comments on db and redis ports)

Redis runs without persistence and with LRU eviction. It is a disposable cache, so recreating the container just empties it.specs/014-redis-wcl-cache/research.md R11 · docker-compose.yml

There are two database roles. The owner runs migrations, and the app connects as a runtime role without BYPASSRLS, so row-level security actually constrains it.specs/006-multi-tenancy/research.md R4

The founder must exist before 0003_tenant_columns backfills existing rows to the founder's tenant, which is why init is a three-step sequence.backend/cli/init_db.py (docstring) · specs/006-multi-tenancy/research.md R8

The frontend image uses a glibc Node base, not Alpine. Tailwind v4's native binaries crash on musl. The prod target exists so production serves a minified, code-split bundle (PERF-011).frontend/Dockerfile (header comment)

InferredReason not recorded for the bin/ scripts (added in commits 025343b and dc48c83, with no spec). Plausible trade-off: they wrap the quickstart steps into one command for local bring-up. They duplicate the logic of backend/cli/init_db.py, and any upgrade failure triggers the bootstrap path.

Backend (FastAPI)

Techfastapi>=0.115.0uvicorn[standard]>=0.30.0pydantic-settings>=2.4.0asyncio

What it does, and where it lives

  • backend/app/main.py builds the app. The lifespan starts the fetch writer (see caching), then runs the boot sequence as a background task: genai serializers, ADK session tables, the live class roster, the guide loader, model discovery and greeting priming. A ReadinessGate middleware returns 503 to everything except /api/health until boot finishes, and the frontend shows the boot progress. On shutdown it drains the fetch writer, closes the WCL HTTP pools and Redis clients, and disposes the database engine.
  • The code is layered: routers in backend/app/api/ → logic in backend/app/services/ → queries in backend/app/db/repository.py and backend/app/repositories/ → ORM in backend/app/db/models.py. Boundary types live in backend/app/schemas.py.
  • The standalone wcl_agent/ package holds the WCL client, the cache, the agent tools and the model helpers. It has no database imports. The backend plugs persistence in through a callback.
  • Background work runs in the same process: backend/app/services/background.py (spawn) holds task references and skips duplicate keys.

Why

FastAPI with asyncio is a constitution rule: all endpoints are async def, and request-path I/O is non-blocking. "A single async framework keeps I/O-bound work (the dominant cost in this app — external API calls) efficient and the backend consistent." The owner also asked for it in the first feature..specify/memory/constitution.md Principle V · specs/001-streaming-chat-frontend/spec.md (Input)

Blocking or CPU-heavy work (password hashing, model probes, PDF rendering) is pushed to threads, not run on the event loop..specify/memory/constitution.md Principle V · specs/002-agent-enhancements/research.md §7

Pydantic models are for data that crosses a boundary (API bodies, messages, external payloads such as cached WCL values). Frozen dataclasses are for internal value objects and config, such as RequestIdentity, FetchedResponse, ReportDocument and the cache's FamilyConfig. Pydantic itself is not listed in pyproject.toml; it comes in through FastAPI and pydantic-settings..specify/memory/constitution.md Principle IV

Boot runs in the background so the port opens at once and /api/health can show which step failed instead of a dead port. After boot, gc.freeze() moves the startup heap out of the garbage collector's reach. This cut a measured ~80 ms event-loop stall per large WCL payload to ~3 ms.backend/app/main.py (_boot docstring and comments, feature 013 SC-008)

Background jobs are in-process tasks, with a database row as the lock where several instances could race. This needs no job queue (Principle III). An in-memory set alone would break on restart and with several instances, and Cloud Tasks was rejected in clarification.specs/013-welcome-recent-raids/research.md R4, R5

InferredReason not recorded for uvicorn as the server (it comes with the FastAPI choice). Plausible trade-off: it is the default ASGI server for FastAPI. The [standard] extra brings the WebSocket and fast-loop support the chat needs. It runs a single worker today, which the in-process rate limiter and background tasks assume.

Auth & multi-tenancy

Techpwdlib[argon2]>=0.2.1PostgreSQL row-level securitysqlalchemy[asyncio]>=2.0.0

What it does, and where it lives

  • Invite-only accounts. A platform admin invites by email. The link is shown once to the admin to share by hand, because no email provider is configured (backend/app/services/link_delivery.py). The first admin is created only from the command line (backend/cli/bootstrap_admin.py). No HTTP endpoint can do it.
  • Passwords (backend/app/auth/passwords.py): Argon2id via pwdlib, run in a thread under a bounded semaphore. A minimum length of 15 is checked before hashing. Unknown emails are checked against a dummy hash, so timing doesn't reveal which accounts exist.
  • Sessions (backend/app/auth/sessions.py, backend/app/auth/tokens.py): a random opaque token in a __Host- cookie (Secure, HttpOnly, SameSite=Lax). Only its sha256 digest is stored, in auth_sessions. Sessions have an idle and an absolute expiry, and last_seen_at writes are throttled.
  • CSRF (backend/app/auth/csrf.py): every unsafe request needs an X-CSRF-Token header, computed as HMAC(SECRET_KEY, session id), plus an Origin/Referer check against SITE_URL. The WebSocket handshake checks the same cookie and Origin before accepting.
  • Request identity (backend/app/auth/dependencies.py, backend/app/tenancy/context.py): require_session builds a frozen RequestIdentity from the session only. get_tenant_db opens a transaction and sets app.tenant_id and app.user_id transaction-locally with set_config(…, true). Every tenant-owned repository function also takes a keyword-only tenant_id.
  • Row-level security. Policy tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid is enabled and forced on 14 tenant-owned tables. The list is in Data. spec_guides, guide_inaccuracy_reports and raw_fetches are global by design. ADK's own session tables are isolated by ADK user_id = tenant id, not by RLS.
  • Login rate limit (backend/app/auth/rate_limit.py): an in-process limiter behind a RateLimiter protocol. Progressive delay starts after 5 consecutive failures and is capped at 30 s. It is never a permanent lockout. Counts are kept per account (users.failed_login_count, users.login_blocked_until) and per source in memory. Public token endpoints get fixed-window caps.
  • Audit and redaction. auth_audit_events is append-only. backend/app/auth/redaction.py strips values of password, token, cookie and csrf keys from logs.

Why

documentation/multi_tenancy_guide.md is the governing contract. Feature 006 adopts it and records only app-specific adaptations.specs/006-multi-tenancy/research.md (preamble)

pwdlib's recommended Argon2id hasher is what the guide prescribes. Running it off the event loop under a semaphore keeps the backend non-blocking and bounds CPU and memory during a login flood. Alternatives: passlib (less aligned with current FastAPI guidance); hashing on the event loop; a new dummy hash per request.specs/006-multi-tenancy/research.md R2 · documentation/multi_tenancy_guide.md (Password hashing)

Opaque server-side sessions in a __Host- cookie, with a header CSRF token. Same-origin deployment through the Vite or nginx proxy makes this the simplest correct design, with no credentialed CORS. Alternatives: JWT (the guide forbids it, and JWTs can't be revoked server-side); double-submit CSRF cookie (weaker); tokens in localStorage (readable by XSS).specs/006-multi-tenancy/research.md R3

RLS plus a separate non-owner runtime role is defence in depth for the feature's worst risk, cross-tenant leaks. The tenant id is set transaction-locally, because session-level SET leaks across pooled connections. Alternatives: app-level scoping only (a single point of failure); one superuser role (bypasses RLS).specs/006-multi-tenancy/research.md R4

An explicit tenant_id argument on every repository function, with one combined id-and-tenant lookup that returns 404 for a foreign row. Alternative: a global SQLAlchemy event that injects filters, rejected as too implicit and easy to bypass.specs/006-multi-tenancy/research.md R5

The rate limiter is in-process at single-process scale, behind an interface so a shared backend can replace it. Alternative: Redis at the time (speculative infrastructure, YAGNI).specs/006-multi-tenancy/research.md R7 · specs/006-multi-tenancy/plan.md (Constitution Check)

tenants and tenant_memberships are kept although v1 is one user per tenant. This matches the guide's RLS contract and avoids a second painful migration later.specs/006-multi-tenancy/plan.md (Constitution Check, Principle III)

Guides are a global library without RLS, because they are generic class advice, not user data. This is the one deliberate deviation from tenant scoping.specs/008-profile-class-pages/research.md Decision 1

Drift from research: R3 planned a stored sha256 of a random CSRF token. The code instead derives it statelessly with HMAC, so a reload or another tab recovers the same token. The reason is recorded in the backend/app/auth/csrf.py docstring. Also, the guide recommends shared limits in Redis once there are several workers. Redis now exists (feature 014), but the limiter is still in-process.

Caching (Redis) & fetch persistence

Techredis>=6 (redis.asyncio)redis:8-alpinefakeredis>=2.30 (test)

What it does, and where it lives

  • wcl_agent/cache/cache.py: get_or_load(family, key, model, loader, ttl=…, force_refresh=…) is the only way code touches Redis. Values are Pydantic models (wcl_agent/cache/cache_models.py), stored as JSON. TTLs get random jitter. A per-key SET lock NX PX guards against stampedes. "Not found" answers are cached briefly. A corrupt value is deleted and treated as a miss. Same-process lookups of one key share one call.
  • There are 14 families. Seven are WCL data: char_id 24 h, char_overview 10 min, char_reports 5 min, report_summary and report_player 24 h (2 min while a report is still being logged), oauth_token (token expiry − 60 s) and world_zones 1 h. The others hold guide-pipeline sources and the model catalog. char_id, world_zones and game_classes also have a short in-process memo.
  • A report counts as finished when its end time is at least 2 h old (wcl_agent/cache/normalize.py, FINAL_AFTER).
  • Fail-open: there is one Redis client per event loop, with 250 ms socket timeouts and a 5 s circuit after a failure. Without REDIS_URL, or with WCL_CACHE_ENABLED=false, the loader is simply called.
  • Daily per-family counters in Redis (wcl:metrics:v1:{family}:{YYYYMMDD}) feed GET /api/admin/cache-stats (backend/app/api/cache_stats.py).
  • Fetch persistence (backend/app/services/fetch_persistence.py, backend/app/repositories/raw_fetches.py): the backend registers FetchWriter.offer with wcl_client.set_fetch_sink. Every successful network response is queued, up to 500 items and 64 MB; when full, the newest is dropped and a throttled warning is logged. One consumer task upserts it into raw_fetches by query_key, and only a newer fetched_at replaces a row. Postgres decodes the JSON (CAST(:p AS jsonb) #- '{data,_cost}'), so the event loop never parses multi-MB bodies. On shutdown the queue drains for up to 5 s.
  1. A tool (or a background job) asks get_or_load for a typed family and key.
  2. It reads the key from Redis.
  3. On a hit it decodes the model and returns it. The flow ends here.
  4. On a miss it takes a short per-key lock. Losers poll for the winner's value for up to 2 s.
  5. It calls the loader, which calls AsyncWCLClient.query.
  6. The client joins an identical in-flight request if there is one. Otherwise it waits for a lane slot and gets an OAuth token from memory, Redis or the token endpoint.
  7. It POSTs the GraphQL query, with a cost field injected.
  8. On 429 or 5xx it backs off and retries, up to 2 times.
  9. The raw bytes are offered to the fetch writer. This never blocks: when the queue is full, the response is dropped.
  10. The payload is turned into the family's Pydantic model.
  11. The model is written to Redis with TTL and jitter, the counters are updated, and the lock is released.
  12. The model goes back to the tool.
  13. Later, the writer's own task upserts the response into raw_fetches.

Planned, not builtA cache → DB → API read order is not built yet. Today raw_fetches is write-only, and the read path is Redis → API. "Nothing reads from the table yet (DB-first reads are sc-129)." (specs/020-fetch-persistence/spec.md, Input)

Why

Redis was the owner's choice, with documentation/redis_cache_spec.md as the design. The goals: fewer Warcraft Logs calls and less latency on repeat lookups, staying under the API rate limit, and a visible hit rate per key family.specs/014-redis-wcl-cache/spec.md (Input) · documentation/redis_cache_spec.md §1

A shared Redis replaces the old in-process, tenant-scoped cache, which was per process, lost on restart and had no cross-process stampede protection. The new service is logged as justified complexity.specs/014-redis-wcl-cache/plan.md (Complexity Tracking)

Keys carry no user or tenant ids, because the data is public and users share entries. This reverses feature 006's tenant-prefixed cache keys.documentation/redis_cache_spec.md §2 · specs/014-redis-wcl-cache/research.md R10

Typed Pydantic values rather than raw dicts (Principle IV); validation failure is the "corrupt" path. Same-process lock losers re-send the same GraphQL, which the client's single-flight joins, so it costs no second request. Alternatives: raw dicts; an extra in-process single-flight around the lock.specs/014-redis-wcl-cache/research.md R3

One client per event loop, short timeouts and a circuit, so a dead Redis costs at most 250 ms and then nothing. Redis is never a hard dependency, and wcl_agent stays usable without it (the CLI needs no Redis). Alternatives: one global client (breaks multi-loop tests and the CLI); no circuit (every call pays the timeout during an outage).specs/014-redis-wcl-cache/research.md R4 · specs/014-redis-wcl-cache/plan.md (Constraints)

Only some families are cached. Event-level data, whole-raid tables and arbitrary rankings are large and rarely repeated. world_zones was added as a seventh WCL family because current_patch() runs on every chat turn. Alternatives: caching all report tables (unbounded key space); keeping lookups by name with no char_id (no negative cache).specs/014-redis-wcl-cache/research.md R1 · specs/014-redis-wcl-cache/plan.md (Complexity Tracking)

The write-through hook sits at the end of AsyncWCLClient._fetch. That code runs exactly once per network call, sees raw responses and covers uncached callers too. Alternatives: hooking get_or_load (misses uncached queries and sees typed models); hooking query() (runs once per single-flight waiter).specs/020-fetch-persistence/research.md R1

A bounded queue with one consumer and drop-newest: it never slows the chat, uses one DB connection, and keeps ordering trivial. Alternatives: batching rows per transaction (one bad row would fail the batch); a bounded task set (N connections, unordered writes).specs/020-fetch-persistence/research.md R4

The database decodes the JSON, because parsing in a thread would still leave SQLAlchemy's JSON bind running json.dumps on the loop. Feature 013 measured stalls of about 80 ms from that kind of work.specs/020-fetch-persistence/research.md R3

One row per query key, upserted. The product owner chose this because no history is needed yet, and judging finality at write time would cost a lookup per write.specs/020-fetch-persistence/research.md R2

Warcraft Logs API client

Techhttpx>=0.27.0asyncioGraphQL v2

What it does, and where it lives

  • wcl_agent/client/wcl_client.py: AsyncWCLClient on a shared httpx.AsyncClient (timeout 60 s, connect 5 s, max 16 connections), one per event loop (get_async_client()). Query strings live in wcl_agent/client/queries.py.
  • Single chokepoint. query() handles single-flight: a shared task per sha256(query + sorted variables), cancelled only when no waiter is left. _fetch handles the 75 s overall timeout (WCL_QUERY_TIMEOUT_S), the lane slot, OAuth, retries, cost logging and the fetch sink.
  • OAuth client credentials: process memo first, then the shared oauth_token Redis entry, then the token endpoint. A 401 refreshes once and retries.
  • Lanes. LaneLimiter caps requests in flight at WCL_MAX_CONCURRENCY (6). Background work (guides, patch lookup, recent raids) runs inside background_lane(). It may hold at most WCL_BACKGROUND_CONCURRENCY (2) slots and never takes one while a chat lookup is waiting.
  • Retries and backoff. 429 and 5xx get up to 2 retries with 0.5 s · 2^n plus jitter, or Retry-After capped at 10 s. Backoff waits outside the slot and never outlasts the query timeout. A 429 with a longer Retry-After means the hourly budget is spent: the client fails fast for every call until it resets.
  • Cost. Every query gets _cost: rateLimitData { … } injected into its top-level selection. Points spent are logged per operation, and the latest snapshot answers rate-limit checks for 30 s without a request of its own.

Why

A native async httpx client replaced requests plus threads. That gave real cancellation and removed GIL contention: QA measured 35 ms average and 157 ms worst-case loop lag. httpx was already a dependency. Alternatives: aiohttp (a new dependency); keeping threads and adding cancel flags (doesn't fix contention, and requests can't cancel cleanly).specs/013-welcome-recent-raids/research.md R7

Lanes stop background work from taking chat slots, in about 40 lines with no dependency. What it does, and where it lives

The class-guide pipeline needs the exact live game build and the newest hotfixes, so a guide never targets the wrong patch. Both come straight from Blizzard. Warcraft Logs only knows the patch as major.minor.

  • backend/app/services/guide_pipeline/briefing.py: fetch_live_version() and fetch_hotfix_feed(). Each uses a short-lived httpx.AsyncClient (10 s timeout, its own User-Agent). They are not part of the shared WCL client, its lanes or OAuth.
  • Live build. GET https://us.version.battle.net/v2/products/wow/versions (WOW_VERSION_URL, backend/app/config.py). This is the launcher's unauthenticated, pipe-separated versions file. parse_versions() reads only the us row of product wow (VersionsName, BuildId, ## seqn), so a PTR build can never leak into a guide. It is cached in the live_version family for 15 minutes (wcl_agent/cache/cache.py).
  • Hotfixes. GET https://worldofwarcraft.blizzard.com/en-us/news (WOW_NEWS_URL) finds the newest "Hotfixes:" article. parse_hotfix_article() reads its JSON-LD date and walks the body with the stdlib html.parser into per-class/per-spec entries, so only the touched specs' guides go stale. It is cached in the hotfix_feed family for 30 minutes.
  • Best effort. Any failure returns None and logs a warning. The briefing then falls back to the last cached value, then to WCL's major.minor patch. Blizzard being down never blocks guide generation.
  • Grounded research. Blizzard's official sites are also tier 1 (fetchable) in the research step's SOURCE_TIERS (backend/app/services/guide_pipeline/research.py). See Agent & frontend → class guides.
  • Not Blizzard. The class/spec roster comes from Warcraft Logs game data (wcl_agent/game/roster.py), not the Blizzard Game Data API.

What it does, and where it lives

  • Endpoints (backend/app/api/reports.py): GET /api/conversations/{id}/report.pdf (whole chat) and GET /api/conversations/{id}/messages/{message_id}/report.pdf (one answer). Both require a session and use the tenant-scoped DB session.
  • Findings rewrite (backend/app/services/report_synthesis.py): one-shot Vertex AI call with WCL_REPORT_MODEL (the same Vertex client the agent uses, installed with google-adk), run in a thread and capped at 60 s. It turns the chat into a findings document. It runs in parallel with chart drawing.
  • Charts (backend/app/services/charts.py): one ChartSpec has two renderers. chart_spec_to_plotly builds the figure dict that the browser draws with plotly.js. chart_spec_to_svg and graph_to_svg draw vector SVG with matplotlib for the PDF. At most 20 figures per report.
  • Render (backend/app/services/pdf_report.py): markdown-it-py (commonmark plus table and strikethrough; tasklists and dollarmath plugins), then maths as matplotlib mathtext SVG, then nh3 sanitising with an allow-list, then remote images swapped for their alt text, then HTML plus print CSS, then WeasyPrint. WeasyPrint uses a URL fetcher that allows only data: URLs. Colours come from backend/app/services/report_theme.py, the chat's "Tavern Hearth" dark theme.
  • Threading. Charts and the render run on a single pdf-render thread pool (60 s for charts, 90 s for the render). The report fails closed: any synthesis or render failure returns 500 pdf_generation_failed, never a partial file.

  2. require_session and get_tenant_db resolve the identity and set the RLS tenant.

  4. Rows come back. A foreign or missing chat returns 404.
  5. In parallel with step 7, synthesize_findings starts.
  6. It calls the report model on Vertex AI in a thread, with a 60 s cap.
  7. Each chart is a separate job on the render thread, so one bad chart becomes "Chart unavailable" instead of failing the report.
  8. The findings Markdown comes back from Vertex AI.
  9. It is returned to the endpoint. Empty output or an error fails closed.
  10. SVG figures come back, capped at 20.
  11. The endpoint builds a typed ReportDocument and sends it to the render thread.
  12. Markdown → HTML, maths → SVG, nh3 sanitising, then WeasyPrint with data:-only fetching.
  13. The PDF bytes come back.
