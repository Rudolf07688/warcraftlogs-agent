Architecture · WCL Agent app

How the WCL Agent fits together

The WCL Agent is a World of Warcraft coaching chat. Its agent, Barnaby, answers questions about raids and Mythic+ runs. It takes the facts from the Warcraft Logs API, reasons over them with Gemini or Claude models, and streams the answer into a React chat. Every Warcraft Logs response is kept in PostgreSQL and read back before the API is asked again. Stored data, guides and past chats are also embedded into a searchable knowledge base. A shared Redis cache sits in front of everything.

Whole-system overview

One browser tab talks to one FastAPI process. Chat turns run over a WebSocket; everything else is REST under /api. The agent and all background work (fetch writer, knowledge-base indexer, guide pipeline, recent raids, kickoff pre-fetch) run inside the backend process; there is no separate worker service. Docker Compose runs four app containers: frontend, backend, db and redis. A fifth, alloy, is the always-on telemetry collector (it also takes the browser's Faro reports and tails the agent team's board); an optional observability profile adds Loki, Tempo, Mimir and Grafana.

One question, end to end

  1. The browser sends the question as a chat frame over /ws/chat; the frontend's nginx (or Vite in development) proxies it to the backend. Stream protocol
  2. The backend checks the session cookie, sets the workspace for row-level security and the turn's identity, and numbers the message. Auth & multi-tenancy
  3. It builds Barnaby's instruction (profile, recent raids and runs, known names, playbooks) and runs the Google ADK agent on the active model provider. Rate limits are retried and may switch to a sibling model. Agent · Models
  4. The model calls tools. Warcraft Logs tools read Redis, then the raw store, then the API; knowledge search queries pgvector and full-text indexes; profile changes are only ever proposed for the user to confirm. WCL data · Knowledge base
  5. Text tokens, tool start and end, charts and follow-ups stream back as frames and render in the React chat. Frontend
  6. The answer is saved, indexed for later search and given a title; the whole chat can be exported as a PDF report. PDF reports

How to read these docs

  • Same shape per layer. What it does and where it lives (paths from the repo root), the technology with the version range from pyproject.toml, frontend/package.json or docker-compose.yml, then why it was built that way.
  • Reasons are sourced. A green bar means the reason is written down in the repo, and the path under it says where: usually the constitution (.specify/memory/constitution.md), a feature's specs/NNN-*/research.md or plan.md, or documentation/. An amber bar with an Inferred badge means nobody wrote the reason down; the text is our best reading of the trade-off.
  • Code wins. Every page names the commit it was checked against. Where a spec and the code disagree, the page describes the code, and the drift is listed on the open-points page.
  • Kept current. The pages are re-checked at every sprint close-out; see Keeping these docs current.
  • Diagrams animate their arrows to show which way data flows. Pause them with the button at the top, or with your system's reduced-motion setting. Sequence diagrams have a numbered text version for small screens.
  • Feature designs (one feature's design rather than the whole system) live in documentation/designs/, for example the self-aware agent.
