Participants & in-chat confirmation

This page covers how Barnaby works out which run "the dungeon" or "the raid" means and who was in it (for sc-206), and how the user approves the resulting profile change on a card in the chat (for sc-207). Its example is the owner's own request: "Add the characters from the dungeon to my friends, except the shaman." The shape of a change proposal and the server side that stores and executes it belong to part 1. This page only links to them. The general architecture is on the architecture pages, and this page doesn't repeat it.

End-to-end flow for the example request

"Add the characters from the dungeon to my friends, except the shaman": user request → resolve run → participants → filter → proposal → card → approve → refresh. The proposal tool, its service and the stored proposal are part 1's design (capabilities & tools). They appear here only as one lifeline.

  1. The browser sends the message as a normal ChatTurn over /ws/chat.
  2. ws._handle_turn saves it and builds the per-turn preamble (profile, known raids, and the new Recent runs line), then streams the agent.
  3. Barnaby resolves "the dungeon" to one report and fight (see run resolution). If that isn't possible, he asks a question and the turn ends there.
  4. He calls get_report_participants(report_code, fight_id).
  5. The tool sends one GraphQL request through AsyncWCLClient.query, so single-flight, rate-limit lanes and raw_fetches persistence all apply.
  6. WCL returns the playerDetails JSON (players grouped as tanks, healers and dps) and the report region.
  7. The tool returns compact rows: name, realm, region, class, spec and role.
  8. Barnaby drops the shaman and the user's own characters (listed in KNOWN PLAYER CONTEXT).
  9. He calls part 1's propose_profile_changes with the remaining rows (target friend, raid_role null).
  10. Its service validates each item and stores a pending proposal. Nothing is written to the profile.
  11. The tool result carries the proposal id.
  12. _handle_tool_end re-reads the stored proposal by id (tenant-scoped) and sends a proposal frame.
  13. Barnaby ends with one short line ("approve it on the card"). done saves the agent message, which a reload uses to place the card.
  14. The user clicks Approve, and the browser calls POST /api/profile/proposals/{id}/approve.
  15. The route calls 029's execute_proposal, which goes through the same shared profile service as the profile REST API.
  16. The service adds the valid friends and schedules their guide tasks, exactly like a manual add.
  17. The response carries the applied proposal (per-item results) and the follow-up line, which is already saved as an agent message.
  18. The card switches to Applied, the line is appended to the chat, and notifyProfileChanged() makes the profile views refetch.

Decision

Barnaby resolves the run himself, from his context, following the flow below. To give him candidates when the chat has no run yet, 030 adds a compact "Recent runs" line to the preamble and adds report codes to the existing "Raids:" line. Both are read from tables that are already stored, so this adds no WCL request. The format, at most 5 runs of each kind with the newest first, trimmed to about 600 characters:

- Recent M+ runs: Ara-Kara +12, 2026-10-25, timed (report a1B2c3, fight 7); …
- Recent raids: Nerub-ar Palace, Heroic, 2026-10-24 (report x9Y8z7); …
- Raids: <label> (report x9Y8z7); …

Kind matters: "the dungeon", "the key" and "the run" mean an M+ run, and "the raid" means a raid. A generic "the log" means either. A report with several keys and no fight id counts as several candidates.

D5 is the product rule: use the run in the chat context, otherwise ask with a short list, and pick the newest only on "last" or "latest". A wrong guess would write the wrong people into the profile, and one question is cheap.sprints/2026-10-26/decisions.md D5

Decision: a new slim tool in its own module

Newwcl_agent/tools/participants.py → async def get_report_participants(report_code: str, fight_id: int = 0) -> dict, registered with one line in TOOLS (wcl_agent/agent.py).

Filters: "except the shaman", "only the healers"

Decision: the model applies filters to the structured rows. The participants tool has no filter arguments. Each row carries canonical values (class as WCL's class name, role ∈ tank | healer | dps, the same vocabulary as RaidRole in backend/app/schemas.py), so a filter is a plain equality check over at most 40 rows.

  • Several matches ("the shaman" when two shamans played): all of them are excluded, and Barnaby names them in his reply ("left out both shamans, Zul'kar and Rainsong"). The card shows exactly who will be added.
  • No match ("except the shaman" with no shaman in the run): Barnaby asks before proposing ("No shaman was in that run. Add all 4?"). A filter that matches nothing usually means the run or the class is wrong.
  • The user's own characters are always left out of an "add friends" proposal. They are listed in KNOWN PLAYER CONTEXT, and the proposal validation would mark them as skipped anyway.

The model filters because filter phrasing is open-ended ("everyone but me", "the two DPS warriors", "not the pug healer"). Covering that with arguments would need a small query language, and the list is small. The approval card is the safety net: nothing is written until the user has seen the exact rows (D4, D6). Alternatives: exclude_classes/roles/exclude_names arguments (deterministic, but they keep growing and still need the model to map words to values); filtering inside the proposal tool (mixes two jobs).sc-212 ("by the model on structured data, or by tool arguments") · decisions.md D4, D6 · constitution III

InferredModel filtering can't be unit-tested without a model. 030 AC 4 is met by a test showing that the structured output supports both example filters exactly (see Tests). The model's own choice is checked by the owner's live run of the example request.

Hand-off to the proposal (shape owned by part 1)

The change-proposal contract (v1) is defined once, in part 1: proposal contract, with items, validation codes and the service API. This page doesn't redefine any of it. The proposal frame, the card and the REST responses all carry part 1's wire model, ProfileProposalOut, unchanged. The names below are part 1's.

What this page uses from it:

  • The proposal: id, conversation_id, message_seq (null until the turn's answer is saved), status (pending | applied | cancelled | expired; expired is computed), expires_at (30 min after creation), applied_at, and items (at most 30).
  • Each item: index, action, target (own | friend), name, realm, region, class_name, spec, raid_role, played_role (display only, never stored, D9), previous_raid_role, validation {ok, code, message}, and result {status: applied | skipped | failed, code, character_id}, which stays null while pending.
  • The service (backend/app/services/profile_proposals.py, owned by 029): get_proposal, list_proposals (by conversation), execute_proposal (idempotent, re-validates every item) and cancel_proposal, each called as (identity, proposal_id) in its own tenant-scoped transaction. Failures raise ProposalError(code) with not_found, proposal_expired, proposal_cancelled or proposal_applied.

Mapping one participant row to an "add friend" item: name → name, realm → realm, region → region, class → class_name, spec → spec, role → played_role, target = friend, and raid_role = null (inferred) unless the user asked for a role ("add them as healers"), per D9. Part 1's validation compares realm slugs (in the shared repo.find_character_identity), so "Tarren Mill" and "tarren-mill" are the same realm. It turns a missing or unknown realm (invalid_realm), an unknown region (invalid_region), an existing friend or own character, the friend limit, a repeated row (duplicate_item) or a hostile name (invalid_name) into the item's validation result.

Behaviour

  • Approve N: N counts the valid items. With N = 0, Approve is disabled and the description says "Nothing to apply". Only Cancel is offered.
  • Double click: the first click disables both buttons and shows the spinner until the response arrives. The server is idempotent anyway.
  • Expiry: shown as a time in CardDescription, with no live countdown. A pending card whose expires_at has passed renders as Expired without a request. The server's 409 proposal_expired is the authority.
  • Hostile names: names and realms render as plain text nodes (React escapes them), never through StreamMarkdown.
  • Accessibility: the card is a labelled group (aria-labelledby the title). A polite live region announces the state change ("Applied: 3 added, 1 skipped"). Focus stays on the card after Approve or Cancel.

D4 sets the card's two buttons and the skipped-row rule. D6 makes it the only way an agent change is applied. What Barnaby says (before and after the decision)

  • When proposing (the proposal turn): one or two lines that name the run and anything left out, and say nothing changes until approved. He never says "added" before approval. The wording rule belongs to part 1's prompt guidance. This page needs only that the turn ends after the proposal.
  • After Approve: a server-built line, saved as an agent message in the proposal's conversation and returned as follow_up: 
    Done. Added 3 friends: Kazrok, Brightmane and Velyra. Skipped 1: Nightpaw (already a friend).
Done. Removed 1 friend: Nightpaw. Set Velyra's role to healer.
Added 2 friends: Kazrok and Brightmane. Couldn't add Velyra (realm unknown). Nothing else changed.
  • After Cancel: Cancelled. Your profile is unchanged.

Profile page and friend lists refresh without a reload

Where profile data shows today: the profile page (/profile, ProfilePage → CharactersTab, which loads getProfile() on mount and after its own mutations), and the welcome panel in a new chat (WelcomePanel: recent raids and M+ runs of the user's own characters). The chat sidebar has no friend list. It lists conversations and tracked raids.

Decision: Newfrontend/src/lib/profileEvents.ts with two functions:

  • notifyProfileChanged(detail) posts {proposal, targets: ["friend" | "own"]} on a BroadcastChannel("wcl-profile") and dispatches the same event in the current tab.
  • useProfileChanged(callback) subscribes to both, and unsubscribes on unmount.

The card calls notifyProfileChanged after a successful approve. Subscribers: CharactersTab calls its existing refresh(), which also covers a profile page open in another tab. WelcomePanel calls its existing load() when own characters changed. A ProposalCard showing the same proposal id in another tab takes the broadcast proposal as its new state.

Same-tab navigation needs nothing: /profile is its own route and refetches on mount. The live update matters for a profile page in another tab, for the welcome panel, and for the same card open twice. A browser-side channel covers all three without server work. Alternatives: a server push frame to every socket of the tenant (needs a connection registry, and across workers a Redis pub/sub, which is a lot for this); polling the profile (wasteful); a full page reload (what the story rules out).frontend/src/main.tsx (routes) · frontend/src/components/profile/CharactersTab.tsx refresh() · frontend/src/components/WelcomePanel.tsx load() · constitution III

Edge cases

CaseBehaviour
Expired proposalThe card renders Expired as soon as expires_at has passed (on load, or on a click after expiry), and Approve becomes unavailable. The server answers 409 proposal_expired to a late approve or cancel, and nothing is written. The text reads "This proposal expired. Ask Barnaby again." There is no follow-up message. The time-to-live is part 1's (30 min), and expired is computed by the service whenever a pending proposal is read past expires_at.
Reload mid-confirmationGET /api/conversations/{id} returns the proposals with their message_seq, and the card renders in its real state (pending, applied, cancelled or expired). A pending, unexpired card is still actionable. If the turn never reached done (the socket dropped mid-turn), the proposal has no message_seq and renders as a standalone card at the end of the chat.
Two tabsBoth show the card. The first Approve wins. An Approve in the second tab gets 200 with the stored result (idempotent: no second write, no second follow-up line). A Cancel there gets 409 proposal_applied. Either way the card shows Applied. Inferred Two clicks landing in the same few milliseconds could each see "pending" before executing, and then both save a follow-up line. That's harmless (the profile is written once) and not worth a lock. With the broadcast channel, the second tab's card and profile page usually update before the user clicks.
Approval after the conversation moved onThe proposal stays actionable until it expires, whatever was said since. The card stays on its original message. On execution, part 1's service re-validates every item against the current profile, so a friend added by hand in the meantime becomes result.status failed with duplicate_friend ("Failed · already a friend"). The follow-up line is appended at the end of the chat (latest seq). A newer proposal never cancels an older one in v1.
Character already a friendThe item's validation marks it at proposal time, and the row shows "Skipped · already a friend". It doesn't count toward Approve N and is never applied. The same goes for the user's own character ("Skipped · your own character"), though Barnaby already leaves those out.
Cross-realmNormal in M+. Each row carries its own realm from WCL, and the identity is name + realm + region, so two players with the same name on different realms are two rows. The card always shows the realm.
Unknown realm or regionThe tool returns realm: null (or region: null) rather than guessing. Part 1's validation marks the item invalid_realm or invalid_region ("Skipped · realm unknown, add by hand"). The rest of the proposal still applies.
More than 30 players after filteringOver part 1's MAX_PROPOSAL_ITEMS (30), for example a raid with many swaps. propose_profile_changes returns {"status": "error"} with no proposal, so no card appears. Barnaby says how many players there are and asks the user to narrow it down ("only the healers", "only last night's kill").
Friend limitAn add over MAX_FRIENDS (50, D8) is "Skipped · friend limit (50) reached" at proposal time, or "Failed · …" if the limit was reached by the time it executed.
Socket drops before the frame arrivesThe proposal is stored, and the next load of the chat shows the card.
Approve while another answer streamsAllowed. REST doesn't wait for the socket's turn loop.
The turn fails after the proposal was madeOn error, App.tsx keeps the turn's pending proposals and shows them as a standalone card, so a stored proposal is never invisible.
