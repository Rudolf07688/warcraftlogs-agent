Self-aware agent

Barnaby learns what the app around him can do, and he can change the user's profile safely: he proposes, the user approves on a card in the chat, and only then is anything written. This page shows the whole flow for the owner's example. The two detail pages hold the decisions.

The example, end to end

"Add the characters from the dungeon to my friends, except the shaman."

Barnaby works out which run is meant and who was in it. He drops the shaman, proposes the exact change, and the user approves it on a card. The profile then updates without a page reload. Each step below is tagged with the design part that owns it: part 1 is capabilities & tools (this author, sc-211), and part 2 is participants & confirmation (sc-212).

Product rules both parts follow

These are the product owner's decisions for sprint 2026-10-26 (sprints/2026-10-26/decisions.md) that shape this feature.

RuleWhat it means here
D4 · Approve all valid items, or cancelNo per-item toggles in v1. Invalid items are on the card, marked as skipped, and never applied. In the contract: validation.ok and result.status = "skipped".
D5 · Ambiguous "the dungeon / the raid"Use the run in the chat context. If there's none, or several, Barnaby asks which one. He picks the latest only when the user says so. Owned by part 2.
D6 · Every agent write needs approvalAdds, raid-role updates and removals, for own characters and friends alike, all go through a proposal and the card. The tool has no write mode.
D8 · At most 50 friendsMAX_FRIENDS = 50 in the shared write path, for REST and agent adds alike. Profiles already over the cap keep their friends; only new adds are refused (friend_limit).
D9 · Raid role on adds from a runLeft empty (inferred from spec) by default; the card shows the role played in the run for information. An explicit role only when the user asks for one.
